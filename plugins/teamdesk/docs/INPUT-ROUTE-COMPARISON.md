# TeamDesk 按需输入路线比较

历史架构取舍记录。后续 MVP 已采用并集成共享 App Server；现行安装与验证边界见 [README](../README.md) 和 [VERIFICATION](VERIFICATION.md)。

日期：2026-09-17。状态：技术推荐，尚非稳定交付结论。

## 结论

优先采用共享 App Server 作为 TeamDesk 的原生输入与事件接入层。原因是它直接对应“选定员工、选择 FIFO/steer、取得原生回执、更新团队 metadata”的确定性操作，符合持续管理多个现有 Codex 员工的工作台需求。

托管界面在沿用默认桌面启动方式、宿主内交互和减少底层连接维护方面有优势。当前共享接法仍依赖实验性传输与临时桌面适配器，不能宣称比托管界面更稳定或安装更省心。稳定连接、人工审批回传和生命周期恢复是共享路线的交付条件。

## 比较对象与证据边界

- 已测托管路线：Codex 内的 visualize 按钮 → 宿主消息桥 → 既有接入任务的新一轮执行 → 原生 send_message_to_thread → 已有员工 → metadata。完整 TeamDesk MCP App、任意员工绑定、FIFO/steer、重启恢复尚未通过这一入口验证。
- 已测共享路线：本地 GUI → 本地接入器 → 桌面实际使用的同一个 App Server → 已有员工 → 原生事件和 hook → metadata。FIFO、steer、原生技能交接、人类结构化问答、hook 和运行中客户端重连已经验证；人工权限审批回传和完整桌面回退尚未验证。
- 两者都保留现有 Codex 员工和原生业务流程；都可以按需触发；都不要求定时唤醒模型检查收件箱；都不能自动提高模型吞吐或消除账户限额。
- UI 放在哪里和执行通道用什么是两个决定。未来可以让 Codex 托管的 TeamDesk 界面调用同一个 App Server 接入器；那是两者组合，不是纯宿主消息桥替代执行协议。

MCP Apps 的官方 UI 桥同时支持发送消息和调用工具。不能将本次 visualize 消息转发原型等同于托管 UI 的能力上限；也不能据此认为托管组件已经能够调用 codex-app-tools、指定任意现有任务或控制原生队列，这些需要具体能力和实测证据。[UI 桥文档](https://developers.openai.com/plugins/build/chatgpt-ui)

## 优劣势

| 维度 | 共享 App Server | Codex 托管界面／已测消息桥 |
| --- | --- | --- |
| 工作台入口 | 保留现有本地 GUI，按员工 ID 投递，不依赖某个接入会话的对话进度 | 用户留在 Codex 内；需要把稳定入口、宿主上下文和目标员工关联设计好 |
| 复杂界面 | 现有页面、表格、筛选和团队视图可以继续使用 | 可以开发复杂组件；需处理宿主资源、布局、状态与网络能力；不能简单断言只能做小卡片 |
| 指定员工 | 协议直接接收明确的 threadId | 已测桥将输入交给承载界面的任务，再由原生任务转交 |
| FIFO/steer | 当前版本的原生队列和 steer 均已实测，轮次可核对 | 尚未在托管入口实测。桥接消息本身不等于任意目标的队列或 steer 控制 |
| 是否多一轮模型 | 技术投递由本地代码完成，无需接入任务先理解再转发 | 当前原型多一轮接入任务；UI 直接调用合适的 MCP 工具可能避免，不能推广为所有托管 UI 都多一轮 |
| 32 员工规模 | 多员工投递与订阅可以由接入器管理，不增加业务统筹角色 | 也能管理 32 员工；若所有输入经过一个模型任务，接入任务本身的排队和上下文需要处理 |
| metadata 来源 | 直接订阅原生事件，以任务、轮次、请求 ID 关联；仍需持久记录和重连核对 | 本次通过文件观察器和 hook 投影；消息桥本身不是全团队原生事件订阅 API |
| 人类问题／审批 | 问答已通过，权限审批仅路由通过；还需处理双客户端决定和清理 | 更贴近原生交互，但托管桥不自动把所有员工问题汇总到工作台；正式聚合仍需实现 |
| 技能、插件、hook | 同实例的测试员工能力已验证。原生 Trust 的 App Server 调用路径已由桌面实现确认，可把人工确认纳入 TeamDesk；完整 GUI 信任闭环待测 | 原生员工天然沿用环境。单独的宿主消息桥尚未证明可直接更新信任；若工具接入同一配置接口，也可呈现确认。两条路线都要保留用户的审查决定 |
| 安装和默认运行 | 当前复杂：要管理连接、原生环境、退出、升级和回退 | 沿用默认桌面启动方式；插件 UI 本身仍需打包、安装、兼容和数据服务 |
| 故障影响 | 接入器作为独立客户端断线已测可恢复；启动适配器故障可能影响桌面及其他原生任务 | 在不介入底层连接的前提下，组件或消息桥问题通常影响入口，原生桌面启动不受本接法影响 |
| 权限边界 | 需要用本地受限接口隔离强大的原生控制协议，只向页面提供业务所需操作 | 可借助宿主的组件和工具边界；仍需验证来源、目标、工具权限和数据访问 |
| 持久化与防重 | 应用必须负责；同一 clientUserMessageId 的重复入队已经产生两条记录 | 同样需要处理重复点击、结果不明和重放；宿主桥没有证明业务操作恰好执行一次 |
| 维护与测试 | 协议动作便于独立测试；同实例连接、版本变化和双客户端行为增加维护成本 | 宿主默认生命周期减少启动维护；组件宿主能力和模型转发流程仍要做真实集成测试 |

上表关于未来开发成本、故障范围和产品适配的比较属于基于当前架构的工程判断；没有做两条完整产品的公平性能基准，也没有完成 32 员工满载测试。

## 选择共享路线的主要原因

1. **入口操作能直接落实为明确的原生动作。** 给正在工作的员工追加独立任务走 FIFO；补充当前任务走 steer 并携带当前轮次 ID。员工如何处理业务、何时联系同事，继续由 skill 和原生工具决定。
2. **全团队工作台无需依赖一个接入任务的模型执行状态。** 管理 32 名员工时，技术接入服务可以处理多目标请求和事件关联，业务上不引入统筹 thread。
3. **证据链更直接。** 可以区分应用收下输入、原生队列接收、轮次开始、等待人类、轮次结束；这些技术状态仍不能替代业务完成或人类验收。
4. **保留现有产品体验和业务模型。** 员工、分组、任务、决定和工作记录不需要变成某一会话的附属状态；UI 日后也可以放到 Codex 内。

## 共享路线的主要代价与交付条件

官方将 App Server 定位为自定义客户端的深度集成协议，但当前 TCP WebSocket 传输明确标记为实验性且不受支持。公开协议可用，不等于我们用于让现有桌面共享连接的启动适配方式获得稳定支持。[App Server 文档](https://learn.chatgpt.com/docs/app-server)

本次实测使用 Desktop 26.911.61220 / CLI 0.155.0-alpha.2.6。原生队列方法有当前版本 schema 和运行证据；不能将其表述为已经获得长期兼容承诺。

交付前需要完成：

- 安装、打开、升级、退出和回退可自动管理；不能让用户长期手配启动变量、找端口或处理辅助进程故障。
- 不改变现有员工的权限、插件环境与 hook 信任；连接故障不能启动第二个实例执行同一任务。
- 真正的人工审批响应、双方决定同步、已结束请求清理及“需要你的决定”归属验证。
- 持久防重、结果不明核对、重连恢复，以及 TeamDesk 支持规模内的并发验证。

若无法可靠满足这些条件，就不应为了保留推荐而交付临时适配器。应重新选择无需介入桌面启动连接的托管路线，并完成它缺失的目标投递和 FIFO/steer 验证。

## 参考证据

### Hook 信任补充调查

2026-09-17 只读检查本机桌面实现，确认原生设置页的 Trust 回调将 hook 的 `key` 与 `currentHash` 交给配置更新逻辑。该逻辑调用 `config/batchWrite`，对 `hooks.state` 使用 `upsert` 写入相应键的 `trusted_hash`，并设置 `reloadUserConfig: true`。列表来自 `hooks/list`，包含来源、定义摘要、当前哈希、是否受管理及信任状态。当前用户配置中的已有信任记录与此结构一致。

因此，“必须由人类审查并信任”不等于“必须在 Codex 设置页点击”。MVP 可以在入职页面显示具体 hook 来源、用途、定义和信任适用范围，在真实用户确认后沿用原生接口，再读取状态并验证一次真实 hook 触发。若共用插件 hook 的定义和信任键一致，可复用已有信任，不按员工人数重复确认；定义变化后重新审查。

本次仅确认实现路径，没有修改信任，也没有把 TeamDesk 内点击到实际生效记为通过。配置写入接口本身公开；`hooks.state` 的具体用法来自本机实现，仍需做版本兼容和实际行为验证。此前“只能回到原生设置页”的限制已修正。
