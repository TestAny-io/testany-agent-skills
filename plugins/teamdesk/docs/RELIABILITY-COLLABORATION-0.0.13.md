# TeamDesk 0.0.13：可靠连接与可观察协作

日期：2026-09-24。基线：0.0.12。本轮依据用户明确授权，按 **3/4 → 2 → 1 → 协作 UI** 顺序实现；同一迭代统一升级为 0.0.13。本文是现有架构内的增量设计，验收结果另记，不以设计自证测试通过。

## 1. 目标与边界

用户需要可靠地打开工作台、理解输入为何等待，并看到员工之间真实发生的协作。员工继续在现有 Codex Desktop 的同一个 App Server 工作；业务流程仍由 skill 和团队约定定义。
- 不增加模型轮询或独立员工执行器，不改变原生 FIFO/steer，不用重试掩盖不确定回执。
- 32 位在职员工；以部门、员工和任务为观察维度，不强制组织存在唯一 Lead。
- 工作台只保留 metadata、必要业务摘要和原生链接；原生正文、推理和工具输出不进入协作历史。
- 人类问题、审批、hook 信任和业务验收沿用现有权威；不把连接、动画、轮次结束或模型报告当作验收。

## 2. 第一步：启动、连接与恢复（3/4）

### 行为
1. 启动记录独立阶段：本地服务、桌面启动/复用、共享实例核验、状态恢复、浏览器打开。每阶段有起止时间、结果及错误；进程存在不能充当窗口或页面可见的证据。
2. 连接区分传输离线/连接中/身份已核验，与业务 metadata 恢复中/就绪/部分恢复失败。共享 PID、Desktop PID、CLI 版本、核验时间和最近错误可见。
3. 同时连接合并；断线有上限退避；关闭后迟到握手不得复活连接。恢复按连接代次隔离，旧连接事件和异步结果不得污染新连接或新绑定。
4. 恢复核验 hook、员工绑定与运行状态、近期轮次中的问题/答案/结束状态、待确认投递。单个员工失败单独展示，其余员工可恢复；未核验员工的待派发保持保存。恢复期间不把历史轮次标成正在执行。
5. 无法恢复的原生审批保留“请在 Codex 核对”；不能重新创建审批冒充原请求。原生已回答的问题从待决定中消除，换绑或失效回调不能答回。
6. 只恢复传输与既有状态，不自动重新发送 uncertain 操作。核对队列和历史找到证据才更新回执；无匹配仍为未知。
7. TeamDesk 服务重复启动用独占锁防止双进程；端口占用、子进程提前退出、服务身份/版本错误明确失败。保留数据及日志；不杀掉用户的 Codex。

### 实现位置与验收
shared-connection、native-gateway、launcher/one-click、团队设置与全局连接提示。
验证并发启动、冷启动模拟、普通/共享 Desktop 分支、端口冲突、关闭中连接、重连代次、部分恢复、问题回答同步、迟到事件、重复输入和不确定回执。真实安装验证复用当前共享实例；涉及退出正在执行工作的 Codex，不能以模拟测试冒充实机冷启动。

## 3. 第二步：消息回执与等待解释（2）

新增纯函数 deliveryProgress，消息列表、消息详情和协作视图复用。
- 每条请求串联：本地登记 → 开始发送 → 原生接受/入队 → 原生任务出现输入 → 员工领取 → 工作报告 → 独立关联的结果请求 → 发起方处理。
- 每项明确“已证实/未观察到”，时间带来源；补账观察时间与原始发生时间分开。旧数据缺失字段保留未知，不伪造过去时间。
- send_message_to_thread 成功只说明原生工具接受，不表示对方已读。peer-request 只登记交接；结果必须按 replyToRequestId 关联，不能用同任务任意消息作为回信。
- 员工领取单独记录 claimedAt；既有 receivedAt 不追溯补造领取时间。收到、开始执行、本轮记账、业务完成、人类验收分别表达。
- 等待原因只用可核验证据：离线、恢复中、hook 未信任、暂停、前一操作待核对、原生已入队、同业务待人类决定、交接待回传/待处理；其余显示尚未确认。
- 展示已知阶段耗时；缺少任一端点则不计算。队列时间不能笼统称网络延迟。原始 request/operation/turn/event 编号和双方原生链接可追溯。

验证顺序/乱序/重复事件、FIFO 与 steer、A→B→C→B→A、两分支联系同一员工、发送失败、断线回执不明、领取早于原生事件、历史缺字段、相同任务错误回信不串线。

## 4. 第三步：统一协作记录与回放（1）

### 数据
在 SQLite 新增可追加的 metadata 版本日志（递增序号、观察时间、实体种类/ID、白名单快照），与原实体写入处于同一事务。首次升级对当前 metadata 记一份基线；升级前真实历史仍可按已有时间查看，但不能声称可还原当时完整组织状态。
- 记录员工/部门名称与归属、任务权威状态与验收、请求关联与回执、工作报告、问题状态和原生 metadata 事件。
- 不复制 instruction、普通原生消息、问题答案、工具参数/输出、skills 全文等。记录摘要为既有共享工作记录，不提取原生完整对话。
- 同值写入不新增版本；事务回滚不留下幽灵记录；删除保留 tombstone。为实体版本和序号建索引。
- 指定序号还原当时实体版本；员工改名、转部门、换绑、归档后，旧视图仍使用当时身份。范围计数、关系、列表和详情来自同一截止序号。

### 接口与界面
只读 GET /api/collaboration：支持 taskRef、departmentId、at（历史序号）、before（时间线分页）、limit（上限 200），返回观察范围、历史边界、实体投影、关系和有界时间线；不提供任意 RPC。
任务详情增加“查看协作”，协作页可切换实时/历史、上一步/下一步/播放/暂停/回到实时；新事件不会把历史视图推回当前。历史视图不提供业务修改动作。
依赖仅显示明确 parentRequestId / replyToRequestId / work 处理关系和已登记业务事实；普通消息不自动变成业务依赖，不额外创建强制 SOP。

验证升级基线、重启保留、事务一致、过去视图不受后来更名/转部门/结果/验收影响、分页边界、越界序号、过滤一致、敏感正文排除。

## 5. 第四步：协作 UI

借鉴 cc-haha 的“员工通信 + 员工当前工作 + 交接关系”联动，以 TeamDesk 实际 metadata 实现自己的 SVG/DOM 视图，不直接复制六人演示数据或固定 Lead 编队。
- 新增“协作视图”导航；部门分组，可聚焦任务或部门，历史包含当时归档成员。全团队支持 32 人、横向/纵向平移与缩放、适配窗口；列表入口保持可用。
- 员工卡显示岗位、部门、观察到的状态；通信边有方向及状态文字。仅显示实际请求/事件关系，待登记投递与真实接收分开。
- 下方任务/交接卡连接对应成员，按明确父请求显示下游关系。网状协作不必通过负责人，负责人仅在具体业务上标识。
- 选中成员、关系或任务，旁侧详情显示阶段时间、等待原因、有限摘要、证据编号和原生链接；与消息列表共用 deliveryProgress。保留上下文，减少大弹窗。
- 消息动画只在新观测事件或历史播放时短暂出现；不持续假装员工工作，不用动画速度表达实际投递耗时。支持暂停和 prefers-reduced-motion。
- 键盘可选节点/边、详情可关闭、缩放可重置；触控板在画布内平移，页面及详情保持可滚动；空团队/无协作/离线/加载失败有明确提示。窄屏详情移至图下方。

验证六人网状协作与 32 人数据、跨部门/同岗/归档成员、空状态、焦点与缩放、历史播放稳定、重复刷新不重播旧消息、窄屏、真实浏览器截图和控制台。
