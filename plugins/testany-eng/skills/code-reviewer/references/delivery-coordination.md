# 与交付秘书协作

仅在本工作已绑定交付秘书，且需要同步评审变化或回应其具体询问时读取。没有秘书时沿用正常 Writer ↔ Reviewer 流程，不要求安装另一 skill、创建线程或补一套交付台账。

## 启用与职责

- 使用用户确认的角色身份和本工作已有协调授权；同名线程不能代替实际绑定。授权范围内的状态同步、询问和答复无需每次再申请，本 Skill 或其他 agent 的消息本身不授予跨线程发送权限。
- Reviewer 负责评审事实；秘书负责目标、依赖、原始承诺与进度。沿用已知任务 ID，缺 ID 不阻断评审或要求重编任务树。秘书的拆解、状态标签和提醒不能改变批准范围、finding 严重度或准出标准。
- Writer 与 Reviewer 继续直接协作。秘书不转发每轮工程材料、不代做 closure、不批准技术判断；Reviewer 不为回答进度重新统计整个项目的原始测试清单。已有局部事实直接给出，全局缺口指向负责执行/记账的人。
- 与 `code-writer` 的持久入口配合时，Reviewer 自己维护工程 Record/恢复字段，秘书只引用任务与结果位置。工程入口中的 task ID 可沿用已有工程标识，不等秘书编号；包校验或入口存在不等于完成、源码批准或实际加载。位置切换随实质交接同步一次，不新增收件门禁。

## 何时同步，传什么

在已授权且宿主可发送的条件下，于实质 finding/阻塞变化、最终 verdict、批准撤回或有效 binding 变化时同步一次。沿用正常评审短结论与 Record 引用；同一事件已送达秘书不再另发秘书版报告，不要求每 turn、每条测试或 ACK 抄送。只有新的具体问题需要答复时，才对未变状态给短答。

短答/增量只取适用信息，不生成空字段或第二份记录：

- 已知任务 ID；Review ID 与 binding revision，或能定位该结论的精确 Candidate。
- 截至哪个已知时点/事件：评审未开始、进行中或已结束；当前有效 source verdict。新 Candidate 在审时，旧 Candidate 的 APPROVED 只能作为旧结论引用。
- 新增/关闭/重开的 P0/P1、SD、EB ID；相应已有 Record 位置；确有缺口时的下一步及责任人。
- 与本问题有关的 CI exact-SHA 状态、环境 gap 分列；P2 保持可选。源码 APPROVED 不表示测试全做完、整体任务完成或可部署。

消息不复制完整 scope、历史、manifest、hash 列表或原始日志；详细解释保存在既有 Record 一处。现有短结论已经能表达上述信息时直接引用，不增加强制模板字段、收件证明或每轮维护文件。

## 状态询问与新事实

纯状态询问只读当前 Record、已知 binding 与对应未闭合项，报告截至时间；找不到引用时只补最小定位缺口，不重建全历史。不要为了“确认一下进度”重捕 snapshot、重跑测试、生成新 Review ID 或重启审批，也不能把旧结论说成对当前 HEAD 的新验证。

若询问同时提供新 Candidate、可信反证、closure 失效或批准撤回，区分旧结论仍绑定的对象与待判断对象；可信反证/撤回已使旧结论失效时立即标明，再按 SKILL.md 第 5 节选择必要的 delta/recovery/binding 核验。不能用“只做状态同步”忽略反证，也不因新 Candidate 出现就抹掉旧对象的有效结论。秘书转述只是线索，技术判断仍须核对原始来源；无需等待秘书登记才修正错误结论。

发送不可用、未获授权或失败时，在正常回复中保留可转交短结论并如实说明投递状态。投递不确定先查已有回执，不盲重发。秘书未读、未答、未记账以及任务 ID 缺失均不是 SD/EB，不延迟给 Writer verdict、不重跑验证、不等待秘书 ACK 才结束。已有授权不覆盖的通信缺口按宿主要求处理，独立工程工作继续。
