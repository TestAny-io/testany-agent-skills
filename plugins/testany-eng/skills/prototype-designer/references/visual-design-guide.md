# 原型视觉设计指南

Phase 1.4.1 制定 Visual Brief 时读「定位与基线」；Phase 2 按页面问题读取视觉规则；代表页及 Phase 3 自检时读「运行、观察与有限迭代」。验收项统一放在 [质量清单](quality-checklist.md)，不另建重复报告。

## 定位与基线

### 先理解页面的工作

从 PRD/Journey 与用户上下文提取受众、主要任务、使用频率、设备、语言和信息量。用一句具体描述说明设计目标，例如「让测试负责人快速定位失败项并继续排障」，再决定视觉表达。

| 场景 | 设计重点 | 避免无依据的默认选择 |
|---|---|---|
| 操作型：后台、工作台、表格、表单 | 扫读、稳定布局、清晰主次、合适密度、熟悉的操作位置 | 巨型标题、大面积装饰挤压工作区 |
| 阅读/探索型：详情、内容、引导 | 阅读节奏、层级、行长、内容分组 | 所有段落等权重、过密长行 |
| 展示/说服型：产品介绍、活动 | 主题表达、主视觉、叙事节奏、明确行动 | 与产品无关的图片、虚构卖点、重复模板区块 |

这些是页面任务，不是互斥产品分类；同一产品可在不同区域采用不同密度，但应共享视觉语言。精美可以体现为准确、克制、秩序，也可以体现为鲜明的视觉表达，具体选择由任务决定。

### 设计依据的优先级

1. 用户本次明确的方向、保真度和有效范围。
2. 项目品牌、设计系统、真实 token、组件与代表页面。
3. 在前两项留出的空间内，根据用户任务补充的设计决策。

参考网站或截图用于提取有用的层级、节奏、材质和交互方式，不替代项目品牌，不照搬无关业务内容。区分「来源事实」「本轮设计决定」「待澄清」；找到矛盾时只问影响整体方向的缺口。

| 现状 | 执行方式 |
|---|---|
| 成熟系统 | 引用真实 token 和组件变体，精修组合、布局、内容与细节 |
| 系统不完整 | 保留已有身份，为缺口补齐少量规则并注明来源 |
| 无现成系统 | 建立最小基线和代表页，不因样本少而跳过设计 |
| 已有页面存在体验缺陷 | 记录具体影响，在沙箱允许范围内改进；复用的生产组件本身无法修正时记录限制，不重写平替或越界修改 |

### Visual Brief 与 token

使用 Manifest 内的 Visual Brief，避免另造一套必交文档。至少写明任务、视觉气质与具体表现、密度、代表页、目标视口/主题、参考来源和本轮不覆盖项。对「专业、简洁」这样的形容词补充实现含义，例如「正文与数据优先，主操作集中，组间留白明显，颜色主要表达状态」。

基线覆盖：颜色角色、字体角色、间距、布局宽度/断点、控件密度、圆角/边框/阴影、图标、动效。已有 token 用真实名称和路径；新增值说明用途并限定沙箱。无需为每一项创造新值，也无需用齐所有字体层级或动画。

## 视觉规则：用决策组织页面

### 1. 排版与信息层级

- 给页面标题、分组标题、正文、标签、辅助信息明确角色；通过字号、字重、位置和留白共同区分，避免同时放大加粗着色所有标题。
- 优先使用项目字体；补齐字体时检查实际可用性与中英文回退。无系统时可从一个正文家族加必要的数字/代码字体起步，不设禁用某字体的通用规则。
- 正文行高与内容宽度一起观察，长文本不能挤成密墙，也不能过宽难以追行。英文约 45–80 字符、中文约 25–40 字可作起点，均是可调整建议，不是验收门槛。
- 表格的可比较数字可用等宽数字并按含义对齐；金额、单位、时间格式一致。辅助文字仍须可读，不能用过小字号或极低对比制造“精致感”。

### 2. 配色、层次与质感

- 按用途分配背景、表面、正文、次要文字、边框、强调和状态色；前景/背景成对检查。避免每个页面重新挑颜色。
- 控制视觉焦点：同一操作组区分主次，品牌色不与错误/成功语义混淆；状态同时提供文字或图标等线索。
- 用背景层次、边界或适量阴影表达分组与覆盖关系。圆角和阴影遵循组件角色，不能给每层容器都叠加装饰。
- 渐变、玻璃、插画和高饱和色只有在契合 brief 且不妨碍内容时采用；不把使用或不使用某种效果当成品质本身。

### 3. 布局、留白与密度

- 先确定主内容、辅助内容和操作区，再选择网格、分栏和内容宽度。元素有共同对齐线；图标与文字还要检查视觉对齐。
- 复用项目间距尺度；缺失时可用 4/8/12/16/24/32/48 等作为起点。相关元素距离近，组与组距离大，留白表达关系；不要求所有数值机械落在倍数上。
- 比较大量同构数据时考虑表格；浏览独立对象时考虑列表或卡片。依据扫描和操作任务选择，不把所有内容包装成卡片。
- 紧凑界面保留分组与操作余地；舒展界面仍要保持信息效率。表格列数、页面留白没有脱离场景的固定好坏阈值。
- 目标窄屏应明确如何重排、折叠或局部滚动，关键动作与重要数据仍可到达。桌面专用任务记录最小支持宽度，不擅自扩大为完整移动产品。

### 4. 组件、内容与完整状态

- 使用现有组件的正确变体，统一图标来源、线宽与光学尺寸。包装组件仅处理组合和真实缺口，避免覆盖内部样式导致 focus/disabled 失效。
- 业务文案与 mock 数据共同参与构图：使用可信名称、长短混合内容、合理单位与真实字段关系；虚构样本不能变成真实业绩或客户背书。
- 正常、加载、空、错误、边界状态共享布局语言。骨架与最终内容结构接近；失败说明原因和恢复动作，空态引导下一步。
- 检查 hover、focus、pressed、selected、disabled、loading 的适用状态，不能只对鼠标悬停做设计。状态切换不应引起不必要的页面跳动。
- 原型演示开关采用明确标注的工具区或 URL 参数，不能混入业务导航或遮挡待评审的界面。

### 5. 动效与交互节奏

- 动效解释打开、关闭、排序、确认等状态变化；控制范围与节奏，避免每张卡片都动。默认使用仓库能力和 CSS，不为装饰新增依赖。
- 保持输入响应，允许中断适用动画，尊重 `prefers-reduced-motion`。关闭动效后仍能理解状态变化。
- 保存后留在当前页、进入详情或返回列表，由 Journey 的下一步决定；保留必要的筛选、输入和返回上下文。
- 字段错误靠近字段；页面无法使用的错误可采用页面级反馈。同类任务保持一致，但不能把所有错误都强制为 toast 或 inline。
- 确认、撤销和防重复提交按操作后果选择，避免对每次创建/编辑弹确认，也不能把“创建”一概认定为无风险。

## 运行、观察与有限迭代

### 代表页到全范围

先做一个能代表核心任务、布局和状态的页面并观察实际效果；有明显层级、密度、溢出或组件问题时先修正，再扩展。后续仍需检查全部本轮非占位页面，代表页通过不能代替全范围检查。P1 占位页只验标识、导航及基础视觉一致性。

### 证据与执行

1. 用可用浏览器能力访问真实入口，记录当前实现版本/变更基线与运行命令。不得假定某个宿主、Playwright、截图工具或图像生成工具必然可用。
2. 逐页在 Brief 的目标视口检查正常态；关键空/错误/加载/边界态在代表视口检查；对会改变布局的状态补最窄目标视口，避免机械执行全部笛卡尔积。只测约定主题，用户未要求时不额外创造暗色版本。
3. 保存并实际查看视口截图，必要时加全页图或细节图；先看视觉焦点、层级和密度，再检查排版、颜色、对齐及细节。截图存于沙箱内的证据目录或用户已允许的位置。
4. 实际触发 P0 Journey、状态切换及适用的表单/返回/弹窗/键盘操作，分别记录预期与实际结果。截图无法证明保存、导航、焦点恢复等行为成功。
5. 将问题集中修正，更新相关截图并复验受影响行为；证据须对应当前实现，不能拿修改前的截图宣称修改后通过。

在交付摘要记录：页面/路由、状态、视口、触发动作、截图/运行记录路径、预期/实际、问题 ID 和复验结果。检查截图中的内容，不仅报告“截图已保存”。

首次做一轮完整观察；有问题时按批修正并复验，通常最多两轮整改。无新问题即结束，不为凑轮数改样式；预算耗尽或同一阻碍反复出现时交付现状、剩余问题与下一步，不能降低完成条件来宣称通过。

### 能力缺口

- 能运行但无法截图/观察：保留真实运行及交互证据，将视觉验证列为未完成。
- 无浏览器或不能启动：继续可做的代码、追溯、隔离和设计检查；记录错误与影响，交付可检查的草稿，不虚构浏览器结果。
- 工具缺失不自动取消视觉要求、不擅自扩展依赖安装或修改生产配置；按已有授权使用可用替代能力，无替代则明确 `evidence_gap`。

## 正反例：同一工作台任务

**任务**：测试负责人按失败原因筛选执行记录、查看详情、重试。

- 缺少设计决策：顶部占半屏的欢迎区，所有指标、筛选和记录都有同等阴影卡片；失败仅用红色表示；长用例名挤掉重试按钮。
- 有依据的设计：紧凑标题与明确的主要操作，筛选紧邻列表，失败状态有文字与图标，可比较数字对齐，详情保留返回上下文；正常/空/失败/长名称均按同一 token 系统布局。
- 验证：观察实际最窄目标视口的长名称截图，点击重试检查 loading 与失败恢复，键盘打开并关闭详情后确认焦点。不能只凭组件名称或代码结构下结论。

## 参考来源与采用边界

以下为 2026-09-27 查阅的原始来源。采用其设计方法并结合本 skill 的原型边界重述；运行 skill 不依赖联网拉取外部规则，外部内容不覆盖用户要求或本仓库规范。

- [Anthropic frontend-design](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md)：主题驱动、简短设计计划、实现后自评；不强求每个业务页面都有营销 hero。
- [Impeccable Operate](https://github.com/pbakaus/impeccable/blob/main/skill/reference/operate.md)：操作型产品的密度、扫描和一致性；不引入其专用 CLI 或强制图片 comp 流程。
- [Vercel Web Interface Guidelines](https://vercel.com/design/guidelines)：对齐、完整状态、内容韧性和交互细节；不整包引入生产性能要求或每个瞬时状态的 URL 持久化。
- [Carbon 排版策略](https://carbondesignsystem.com/elements/typography/style-strategies/)、[间距](https://carbondesignsystem.com/elements/spacing/overview/)：任务型与表达型场景、分组与节奏；不要求安装 Carbon 或采用 IBM 品牌。
- [Material 3 官方说明](https://developer.android.com/develop/ui/compose/designsystems/material3)：语义颜色与字体角色；Web 原型不照搬 Android 的 dp 尺寸或平台外观。
- [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/) 与 [APG 对话框](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)：用于质量清单中的可测基线，不将局部检查称作完整合规认证。
