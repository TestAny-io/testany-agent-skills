# BRD 访谈问题库

按 [访谈模式与事实标准](../../../references/interview-modes.md) 使用。本文件是缺口检查和候选问题，不是必须全部提问的脚本。复用已知信息；开放回答无法合理离散化时不强制选择题。

## 原始意图与现状

- Stakeholder 想解决什么问题，为什么现在做？保留原话和来源。
- 谁受到影响，在什么情境下，现有流程和痛点是什么？
- 效率：耗时、频率、涉及人数；成本：成本构成与口径；质量：错误及影响；体验：反馈、投诉、满意度。只补当前相关缺口，不为了填表追问所有数字。
- 没有历史基线：记录未知项、可执行测量方法、负责人和时间/触发点。不猜数值，不拒绝草稿；纯定性痛点可作为意图，但不是最终验收条件。

## 目标类型与人群

目标可并存；发生冲突才让有权限 stakeholder 做取舍，不强迫所有需求只有一个目标。

| 目标 | 常见缺口 |
|---|---|
| 收入增长 | 获客/转化/客单价/复购的具体环节、目标客群、来源证据 |
| 成本下降 | 人力/获客/运营/技术成本构成、可控与不可控部分 |
| 风险合规 | 适用义务、适用范围、负责人、截止点、验收证据；法规细节需最新可靠来源 |
| 用户体验 | 发现/使用/售后/推荐哪个环节，用户可观察的改善 |
| 运营效率 | 当前业务链、等待/返工点、哪些步骤在本次范围内 |
| 战略需求 | 为什么必要、与既有目标的关系、如何识别价值或止损 |

记录新增、替代、修复、优化或合规变化，以及直接受影响的人群。不要把内部判断写成已取得的用户调研。

## 用户画像

需要足以识别角色与痛点的人群描述；已知项直接使用。不是每个项目都必须问人口统计学全表。

- B2B：企业类型/规模（有依据时）、使用者与采购/决策者、业务职责、采购或审批链、核心工作场景。
- B2C：使用情境、行为、需求及约束；年龄/收入等仅在与需求相关且有来源时记录。
- 痛点来源：反馈、数据、访谈或内部估计；后者明确标记来源与待验证性。
- 画像尚未确定可保留待定，但其对范围和验收的影响必须显式记录。

## 成功定义

按目标选择可验证方式，不给所有需求套同一数字表：

| 方式 | 需要整理的信息 |
|---|---|
| 量化改善 | 指标口径、当前值及来源状态、目标及依据、时间窗口、数据来源 |
| 当前无基线 | 测量计划、Owner、采集范围与时间、何时据此确认目标 |
| 离散验收 | 哪个能力/限制成立，观察场景、通过/不通过条件、验收人及证据 |
| 合理估算 | 由谁估算、依据与区间、不确定性和后续验证方式 |

“更快/减少/提升”需要补可观察标准或测量计划，不代表必须当场给出未知数字。数据来源可有多个；分别说明埋点/报表、拟建采集、人工统计、第三方材料或尚未确定。

## 范围与约束

- In-scope：本次解决哪些具体业务能力或问题？
- Out-of-scope：已明确不做什么及原因？未有排除决定可写待定或暂无已确定排除项，不编一个排除项凑数。
- 约束：法规、安全、预算、时间、品牌、现有系统、技术既定限制、组织职责，按实际相关性记录。
- 风险容忍：哪些风险不能接受，哪些可经有权限 Owner 决定接受？不要把抽象“零风险”当可执行规则。

技术建议可以原样保留到附录；不得从“用缓存”等实现建议自行推导响应时间阈值。后续分别由 API/HLD/LLD 处理契约、架构和实现问题。

## 依赖、假设与终止条件

- 数据、系统权限、其他团队、供应商、预算、高层、法务、可行性验证：只列真实依赖及负责人/状态。
- 假设记录来源、置信度、验证方式与状态。未决项是否阻塞取决于影响，而不是数量。
- 终止或重评条件记录真实的预算、时间、核心效果、合规等决定。未定阈值保留待定，不补造 X% 或周数。
- 用户不确定或要求停止访谈时，把缺口及影响记入草稿，不无限追问。

## 交付检查

1. 原始意图、目标人群、业务范围与约束是否可追溯且不自相矛盾？
2. 成功定义是实测/估算/待测计划/离散验收中的哪类？是否有未标明的猜测？
3. 未决项及依赖影响是否真实列出，是否有人负责补齐（未知则明确未知）？
4. 用户要求草稿还是正式基线？仅完成内容不能自动批准；批准需对应版本/范围的真实决定。
5. 已知阻塞不妨碍交付透明草稿，但不得将其推荐为已经锁定的下游基线。
