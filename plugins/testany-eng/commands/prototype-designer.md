# Prototype Designer

执行前读取 [工作流执行约定](../references/workflow-execution.md)：先取证再提问、按实际工具能力回退，并从本次安装位置定位资源。

在前端仓库中基于 PRD/User Journey 或口述需求生成视觉精美、可运行、可交互的隔离原型，验证流程、页面状态和数据需求；有 ui-designer 设计包时照设计包实现，没有时由 skill 从需求中判读设计并说明依据。只想先定界面设计时用 `/testany-eng:ui-designer`。默认高保真，用户明确要求线框稿时遵循其保真度；执行细则见 [prototype-designer](../skills/prototype-designer/SKILL.md)。

## 为什么在 HLD 之前做原型？

文字描述的需求到前端实现之间存在巨大鸿沟。原型将交互问题提前到设计阶段暴露：
- 交互死角（Journey 中遗漏的状态和路径）
- 导航断点（页面间跳转不通顺）
- 状态遗漏（空态、错误态、边界态未考虑）
- 数据需求不明确（页面需要什么数据，为 API Contract 提供输入）

## 核心特点

- **设计依据清楚**：有 ui-designer 设计包时照设计包实现并补全流程与状态；没有时从需求中读出使用频率、设备、任务、数据形态、行业语境等信号，写出带依据的判读单后直接动手
- **有立场的视觉方向**：先定构图再选组件，逐页明确主轨、构图和三轴；六层视觉语言逐层独立决定，生成默认样式须事前声明，并用测量证据核对
- **交互编排**：招牌时刻和提交/撤销/拖拽等 P0 动作写完整链路（触发、反馈、过渡、结果、恢复、焦点、减少动效），其余步骤一行，再实际操作复验
- **组件优先复用**：使用仓库现有组件和样式，缺口可在沙箱新增，不引入额外依赖
- **100% 遵循仓库规范**：目录结构、代码风格、lint 规则全部对齐
- **Mock 数据驱动**：不接后端，数据结构对齐 PRD 业务实体
- **可追溯**：每个页面映射到 Journey 步骤和 PRD 需求

## 工作流程

1. **前端仓库探查**：扫描技术栈、组件库、设计规范
2. **原型规划**：建立需求基线（正式文档或需求推断卡）、设计判读、需求→页面映射、状态矩阵、视觉方向与逐页构图、按构图匹配组件、P0 交互编排
3. **原型实现**：代表页构图门槛（含测量与模板默认项核对）+ 逐页面扩展 + 导航与状态
4. **自检交付**：实际页面/截图观察、交互走查、修正复验、覆盖与工程隔离检查；缺失证据如实记录
