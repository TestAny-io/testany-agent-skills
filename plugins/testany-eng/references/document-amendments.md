# 文档的正式设计与有限增量

供 API 及相关需求、设计、测试、运维文档的 writer/reviewer/guide 使用。HLD/LLD/Code 的分层与专用协议仍见 [review-boundaries.md](review-boundaries.md)，本文不改变 Code Reviewer 的精确对象、授权或状态机。

## 选择入口

- `formal_design`：完整新功能、全量设计或用户明确要求正式全量准出，保留该层级适用的完整前置条件、追溯和评审覆盖。不能借“增量”绕过已要求的完整设计。
- `bounded_change`，别名 `amendment`：已有工件和有效行为依据，本轮目标/改动范围明确。可在既有批准边界内修改，也可只读评估尚待决定的提案；后者不得标为已获批准。
- 按职责、信任、所有权、权限人群、契约兼容性、数据生命周期、失败语义及运行负担判断影响，不按代码行数、文件数、安全关键词或“只是小修”判断。

## 有限增量的执行闭环

1. **读取真实基线和授权**：既有契约/文档、相关需求/ADR/Owner 决定、当前变更及必要实现事实。写清谁在什么范围内批准了什么。代码现状、测试通过、作者 note 或 Reviewer 自己的旧意见不能独立授予新范围。
2. **识别影响与保持项**：列出改变的行为及不变的认证、授权、错误、数据/调用者兼容等边界。影响跨越层级时只将相应增量交对应 Owner/评审，不把整个修复升级为全流程。
3. **仅修改获授权部分或只读评审**：遵守当前写入权限和用户指定路径，保留无关内容、已有格式与稳定 ID。原生 OpenAPI/YAML/GraphQL/Proto 等仍用其原生格式，不为模板或 metadata 强行包成另一份 Markdown。
4. **验证实际差异**：逐项核对授权变更及保持项；运行当前可用且获准的解析、lint、兼容性或既有测试。已有机器追溯须维护并核验受影响关系；不伪造历史 artifact ID，不为有限更新强制迁移全库格式或补齐所有历史文档。组织明确要求的必要证据仍不可豁免，缺口如实阻止相关准出。
5. **交付有边界的结果**：说明对象/版本、批准来源、差异、实际验证、未验证项、已审/未审范围和最小下一步。可复用现有请求、diff 或文档，无须新建全量证书、Manifest 或全生命周期工件。写作完成、自检通过、有限增量评审与正式发布许可分别表达。

## 专业边界

- API：校验受影响请求/响应、required、枚举、错误、认证/授权、消费者与版本兼容。即使新增可选字段，也核查旧消费者约束，不一概保证兼容。一个可选字段获准不代表取消认证或跨租户读取也获准。
- PRD/HLD/LLD：只承接本轮有效需求与决策；HLD 引用契约，不重新定义 wire/错误语义；LLD 不凭实现便利新增职责或权限。真实新增产品可见行为交有权产品 Owner，纯架构变化须有工程授权。
- 测试策略/测试包：更新受影响风险、测试与追溯，保留当前阶段范围；不得把必要 QA 黑盒契约验证误降为开发前置条件，也不把设计准出说成执行通过。
- Runbook：更新已批准的运行/恢复说明与相关验证，不自动执行命令，不因缺全套历史 PRD/HLD/Test Spec 让局部更新重走项目启动；必要发布/回滚规则缺失仍不得宣称生产就绪。
- Guardrails：仅在项目级默认规则真实改变或当前结论依赖必要缺口时触发；缺整份历史文件不自动触发，既有规则与事实冲突不能通过把事实抄成标准来消除。

有限范围的**首次审查**仍要完整覆盖该增量及直接影响。整改 `delta` 是另一维度，只有可验证的完整初审及有效旧证据才可复用；缺证或未审区域必须补审，见 [review-assurance.md](review-assurance.md)。

例：Owner 仅批准给既有 200 响应增加可选 `request_id`。读取原生契约与批准记录，改该字段，验证其他字段、认证和错误语义保持不变即可；不补写完整 PRD/HLD，也不把这一批准扩大到发布或匿名读取。
