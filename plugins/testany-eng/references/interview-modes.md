# 访谈、材料整理与缺口补问

适用于 BRD / User Journey。先读取用户指定材料和已有决定，再按本次任务选模式；模式不是新的必填表单。

| 模式 | 触发 | 工作方式与停止点 |
|---|---|---|
| `interview` | 只有模糊想法，或明确要求交互访谈 | 每轮问最重要的 2-3 个缺口；按用户检查点等待，不擅自确定范围或指标 |
| `synthesis` | 已有足够材料，要求整理/生成草稿 | 直接复用事实并生成；已知 baseline、用户、步骤、优先级不逐条再确认 |
| `gap_followup` | 已有材料，只剩局部歧义/冲突 | 仅问会影响当前决定的真实缺口，引用来源；其他部分继续整理 |
| 局部编辑 | 明确只改文档片段、格式或名称 | 只改指定范围并检查差异，不重开访谈、全量问卷或正式准出 |

问题组织服从真实工具能力。只有信息足以形成可信候选时用选择题；开放问题可直接用文本。不要为了工具必填选项编造候选，不把工具缺失当业务阻塞，不把默认选中视为用户已回答。

## 事实与成功定义

| 类型 | 至少记录 | 不得混淆 |
|---|---|---|
| 实测 `measured` | 数值/口径、时间范围、可追溯来源 | 文档中的估计数字不自动成为实测 |
| 估算 `estimated` | 提供者、依据、区间/不确定性、验证方式 | 不把估算写成基线事实或已批准目标 |
| 待测 `measurement_plan` | 当前未知项、测量口径/方法、负责人、时间或触发点 | 测量计划不是已经达到效果；缺字段如实待定 |
| 离散验收 `discrete_acceptance` | 可观察的通过/不通过条件、验收人或证据方式 | 不为合规、权限或能力有无等目标硬造百分比 |

“提高效率”不能直接当可执行验收，但可以先记录业务意图，再补测量计划或具体观察条件。缺少历史基线不阻止产出草稿；不要建议随意猜数字填门禁。目标值、预算和截止日期也需真实来源，未知用待定而不是自造。

## 草稿与批准

- 生成完整内容、脚本检查通过、用户曾批准上游，均不等于本次工件已批准。
- 草稿可以含明确待定项，并继续收集事实；可进入评审的质量条件与正式批准条件分开记录。用户只要求 draft 时保持 draft，不能因自检通过擅自提升状态。
- 正式基线必须有对应版本/范围的 Owner 或有权限 stakeholder 批准依据。无证据时保留待批准；不能由 agent 补造审批人、日期、意见或把“材料已给”当批准。
- 以未决项对范围、验收、权限、关键流程和交付风险的影响判定阻塞，不按假设数量、待定项个数统一通过/阻塞。测量计划可支持受限探索，不自动替代项目正式准出标准。
- Journey 的 metadata、图、跳转与步骤级边界质量继续按其 checkpoint 规则检查。lint 缺失/失败如实列为证据缺口，既不伪称通过，也不阻止用户索要的草稿。

完成本次整理后返回实际工件、来源、待决事项和真实检查结果。没有授权不自动锁定下游基线、扩展范围、实施或发布。
