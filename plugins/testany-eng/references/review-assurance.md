# 证据、准出与复审规则

适用于 PRD、API、Guardrails、Test Strategy、Test、Prototype 评审，以及 Runbook 的审查/自检记录。HLD/LLD/Code 的专业对象与授权协议保持独立，不以本文替换。

## 分开记录问题类型与严重度

| kind | 含义 | 严重度与准出影响 |
|------|------|------------------|
| `defect` | 当前工件中有证据证明的错误或遗漏 | 按实际风险定 P0/P1/P2，不由工具日志级别机械决定 |
| `evidence_gap` | 必要基线、运行结果、覆盖或独立审查证据不可得 | 记录缺什么、为何必要、影响哪些结论；可阻止正式准出，但不是已证实的产品 P0 |
| `scope_decision` | 范围、所有权、信任、批准或标准需要有权者决策 | 标明责任层级与未批准范围，不自行作决定或用“小改动”豁免 |
| `optional` | 没有必要正确性/安全影响的可选改善 | P2，记录但不按数量阻断 |

同一症状不能重复计数。若证据不可得和已证实缺陷同时存在，可分别列项并解释关系。脚本 `error`/blocking issue、运行失败、lint warning 不直接等于产品 P0/P1；检查实际输入、规则及影响。必要机器追溯、执行或批准条件仍须满足，不得以重新分类偷换成通过。

## 准出与完成

- 默认通过条件：当前范围内无未关闭 P0/P1；必要基线、覆盖、执行与批准证据充分。P2 不按数量阻断；不要把真实严重缺陷降成 P2 以凑通过。
- 只剩必要证据不足时，报告“待补证据，未准出”；有明确缺陷或范围冲突时报告不通过。本轮调查与报告可以完成，工件不必被批准。
- 不默认接受一个 P1，不发明有条件通过、例外审批人或风险接受权。组织已有正式例外制度时，只能核验真实记录的有权主体、对象、范围、期限与适用规则；缺一则仍未批准，不能仅凭计划或作者承诺关闭问题。
- 测试设计准出、发布前测试门禁、独立评审和发布/部署许可分别表达。文档准出证书不授予外部操作权限；作者自检不冒充独立评审。

## 检查依赖

前一道门失败只暂停依赖该证据的判断，不取消其他可独立开展的检查。对 Prototype，即使 PRD/Journey/Manifest 缺失，仍根据已有批准范围、精确 diff 和真实入口/import/依赖检查工程隔离；不得为了对齐而补造产品需求。对 API/测试策略，继续有事实依据的安全、兼容性或风险检查。若对象本身不可访问，明确哪些检查无法进行，绝不把未审写成通过。

## 稳定记录与有限复审

1. 每轮绑定对象路径与版本（可取得时附摘要）、批准范围、采用标准及其版本、`initial`/`delta`/`closeout` 模式、实际执行证据与已审/未审覆盖。报告与准出证书都不能省略未审范围。
2. 首次评审覆盖全部适用维度；受阻项保留为未审。问题使用稳定 ID，记录 kind、严重度、来源位置、影响、状态、关闭证据；复审不重新编号、不悄悄改变判据。
3. 只有可靠的完整首次覆盖、未变的范围/标准和仍有效的证据都可核实时，才复用旧结论并只检查整改 delta、影响面与回归。上轮只审部分范围时，可复用那部分，但必须补未审范围后才能给全量准出。
4. 对象、范围、标准或依赖发生漂移时，重新评估受影响及相关边界；无法界定影响才扩大为完整评审。不要因为“文件未改”就默认旧证据有效，也不因任何文本变动一律从头重做。
5. `closeout` 仅判断用户提供的收尾记录时，明确是记录级结论，不伪称重新运行或独立完整评审。可以依据明确有效的完整证据给收尾通过，但不得扩大批准范围。
6. Reviewer 默认只读工件，只输出发现与修复建议。若另获写作/修复授权，在该范围内修改并重新验证。预算到达、无新证据或重复同一阻断时，交付当前报告与具体下一步，不为拿到通过无限循环。Runbook 每阶段最多两轮修复及一次委派失败重试，不因此降低准出条件。

例：三个纯措辞建议不阻断完整证据支持的准出；一个未关闭租户隔离 P1 仍不通过；lint 未执行但未发现产品错误应记 evidence_gap，评审报告可完成，准出保持未批准。
