# 设计判读指南：从需求读出设计决策

建立需求基线和设计判读时读取；逐页决定和用户改条件时回读。ui-designer 与 prototype-designer 共用。目标是不等用户指定风格，也能从 PRD、Journey、口述需求或零散材料中读出信号，做出能指回依据的设计选择，并在动手前把判断说清楚。

## 原则

1. **依据可追溯**：每个主要设计决定都写明来自哪条信号（用户原话、Journey 步骤、PRD 字段、仓库现状或用户措辞）。说不出依据的选择就是模型默认值，按方向指南的「模板默认项」处理。
2. **先说判断，再动手，不等批准**：动手前写出判读单，默认继续；用户改一个条件，只重算受影响的决定。
3. **品牌和设计系统优先**：推断只填用户指令和现有品牌/设计系统留下的空间。
4. **假设要标出来**：信号弱时照样做决定，但标为「假设」，交付时列出仍未确认的假设。

## 一、建立需求基线

| 输入情况 | 模式 | 需求基线 |
|---|---|---|
| PRD + User Journey | 正式 | `REQ-*`、Journey 步骤与步骤级 edge case matrix |
| 只有 PRD 或只有 Journey | 部分 | 已有文档 + 需求推断卡补齐缺失部分（如从 PRD 推出主要路径） |
| 口述需求、截图、竞品链接、零散文档 | 独立 | 需求推断卡 |

三种模式都能完整执行本 skill；不因缺少 PRD 或 Journey 而要求用户先走其他流程。

### 需求推断卡

把口述或零散材料整理成一张卡，写入设计记录（ui-designer 的设计说明或 prototype-designer 的 Manifest）。每条有稳定 ID（`IR-01`、`IR-02`…）和来源标记：`原话`（用户原话或材料原文）、`推断`（从原话合理推出）、`假设`（缺少依据、为继续工作暂定）。同时记录用户原始需求（原话或摘要及材料位置），供复核对照。

至少覆盖：

- **用户与场景**：谁用、在哪用、多频繁、用什么设备。
- **核心任务**：P0 任务（本轮必须走通）和 P1 任务（只做占位），每个任务拆成能映射到页面的步骤。
- **业务实体与关键字段**：供 mock 数据和下游输入使用。
- **关键状态**：空、加载、错误，以及与任务相关的边界情况（超量、冲突、权限不足等）和恢复方式。
- **不做什么**：本轮明确不覆盖的内容，防止自己加戏。

推断只补达成原话目标所必需的步骤和状态；原话没有提到的新功能不进入 P0，确有价值的写进「不做什么」或作为建议。

### 什么时候必须先问

只有连**产品是什么、给谁用、核心任务是什么**都无法判断时才提问。一次最多 3 个问题，每个问题附上建议答案，用户确认或改一处即可。其余缺口按假设继续，不因信息不全停工。

## 二、读信号

从需求基线、仓库现状和用户措辞里找下列信号。一条信号可以影响多个决定；信号冲突时，以核心任务和高频场景为准。

| 信号 | 常见来源 | 影响的决定 |
|---|---|---|
| 使用频率与单次时长 | Journey 步骤；口述中的“每天”“偶尔”“一次性” | `visual_density`、快捷操作与键盘、`motion_intensity` |
| 设备与使用情境 | “在手机上”“平板”“大屏”“边打电话边操作” | 主轨、构图、拇指区、点击尺寸、是否单手 |
| 领域惯例与心智模型 | 日程、表格、邮件、地图、购物车等用户早已熟悉的形态 | 核心布局沿用惯例；辨识度改由细节和招牌交互承担 |
| 商业目标 | “想让人下单”“留下联系方式”“报名” | 说服结构：向往的结果画面、具体的证明、低门槛的下一步 |
| 观看距离与环境光 | “挂在墙上”“投屏”“夜里”“户外” | 字号下限与关键读数大小、对比度、背景明暗、动效是否会分散注意 |
| 任务动词 | 比较、监控、录入、审批、浏览、阅读、购买 | 主轨、主构图、主要组件（表格/卡片/看板/表单/抽屉） |
| 数据规模与形态 | 实体条数、时间序列、图片为主、长文本 | 内容主角，列表/表格/画廊，分页与筛选 |
| 操作后果与可逆性 | 删除、支付、发送、审批 | 确认/撤销/长按、反馈强度、危险动作的视觉降级 |
| 用户专业程度 | 新手、专业人员、内部员工 | 信息披露深度、术语、引导与空态写法 |
| 时间压力与注意力 | “很忙”“紧急”“值班” | 首屏取舍、状态色、通知方式 |
| 信息复杂度与所处阶段 | “规则很多”“第一次办”“新人”“流程” | 按用户所处步骤渐进展示，而不是一次铺满 |
| 行业与情绪语境 | 医疗、金融、儿童、宠物、创意、政务 | 视觉性格、字体语气、色彩性格、动效气质 |
| 产品定位与受众 | 门面展示、内部工具、高端消费、大众服务 | `design_variance`、签名强度、品牌表达比重 |
| 法规与无障碍 | 公共服务、医疗、老年用户 | 三轴上限、字号与对比度、动效克制 |
| 品牌与现有系统 | 仓库 token、组件库、用户给的 logo 或截图 | 继承、补齐或新建基线 |
| 用户措辞 | “专业”“温暖”“像某某产品”“别像模板” | 视觉性格的修正 |

## 三、从信号到视觉性格

风格是需求里最少直接写明的部分。先用 2–3 个性格词概括（如“冷静、精确、克制”），再落到六层视觉语言。性格词至少要有一条**产品特有**的依据，不能只来自行业：同一行业的两个产品，受众、场景和定位不同，性格就该不同。

下表说明同一种性格可以有截然不同的落法，每行给两种，**都不是默认答案**。实际落法从产品特有的信号推出，可以是表外的第三种。

| 性格倾向 | 常见信号 | 落法一 | 落法二 |
|---|---|---|---|
| 冷静精确 | 高频专业使用、出错代价高 | 中性底，强调色只给状态；无衬线 + 等宽数字；细线分隔 | 深色底，亮度分层代替边框；数字主导，标签退后 |
| 高效密集 | 批量处理、大量同构记录 | 表格优先、紧凑行高、键盘操作 | 分栏工作区，左列表右详情，状态用图形编码而不是色块 |
| 可信稳重 | 公共服务、医疗、老年用户 | 高对比、大字号、明确的步骤条 | 文档式单栏、宽松行距、每步只问一件事 |
| 温暖可亲 | 日常记录、家庭与个人生活 | 柔和标题字形、较大圆角、轻量弹性反馈 | 手写或插画感的局部点缀，界面本身克制，温度来自内容和措辞 |
| 安静高级 | 门面展示、精品品牌、作品呈现 | 大留白、宋体或明朝体标题、作品大图主导、过渡少而慢 | 图纸式标注、等宽编号、网格严谨，克制来自秩序而不是空白 |
| 活力表达 | 活动、娱乐、年轻用户 | 高对比撞色、窄体粗标题 | 动态排版和滚动叙事，颜色反而收敛 |

选落法时先问：目标用户看到会不会觉得好看、想用？在这个前提下再追求与众不同。选出后仍按 [视觉方向指南](design-direction-guide.md) 逐层独立决定，并检查模板默认项和视觉手法的代价。

## 四、场景操作构思

读完信号后，为每个 P0 任务回答一句：**在这个场景下，最省力的完成方式是什么？** 先写下场景的约束（一只手拿着电话、戴着手套、站着走动、隔着几米看、来电时只听得到尾号），再选与之匹配的输入方式，而不是默认用表单和下拉框。

| 场景约束 | 可能更省力的方式 |
|---|---|
| 边接电话边操作 | 屏幕数字键盘按尾号查人、可直接照读的确认话术、少打字 |
| 戴手套、推车、走动中 | 大目标、扫码、整行可点、确认靠手势或大按钮、震动或声音反馈 |
| 远距离观看、无人操作 | 不需要交互即可读懂，状态变化自己出现、自己说明 |
| 高频重复录入 | 快捷键、默认值、上一次的选择、批量操作 |
| 犹豫要不要买或联系 | 先看到结果和价格区间，再一步留下联系方式 |
| 第一次办理复杂流程 | 分步带着走：当前在哪一步、这一步要准备什么、怎么做、结果和时间预期；其余规则按需展开，不在开始前铺满 |

每个 P0 任务至少落实一个这类为场景而设计的操作方式，写进判读单和交互编排；它往往比视觉风格更决定“好不好用”。

## 五、判读单

动手前写出判读单，写入设计记录，并在确认范围或方向时连同页面清单一起展示。它是假设清单，不是逐项审批：用户不回应时按判读单继续。

先用一段话概括：这是什么产品、给谁、在什么情境下完成什么，因此视觉性格、密度和动效取向如何。再列出主要决定。以下示例题材刻意冷门，只演示写法，遇到相近需求也不能沿用其中的决定：

| 决定 | 选择 | 依据（来源位置） | 置信度 |
|---|---|---|---|
| 视觉性格 | 利落、可靠、略带手作感 | IR-02 “借工具的人排着队，管理员一个人”；IR-05 社区共享工具间 | 推断 |
| 主轨（借还页） | 操作/配置 | IR-03 “扫码借、扫码还” | 明确 |
| 主构图（借还页） | 主区 + 常驻窄栏：扫码结果为主区，逾期提醒常驻右侧 | IR-04 管理员要同时盯着逾期 | 推断 |
| 密度（借还页） | `visual_density` 4 | 每次只处理一件工具 | 推断 |
| 主色 | 中性底 + 单一强调色 | 没有品牌材料 | 假设 |

置信度分三档：`明确`（PRD/Journey 或用户原话直接给出）、`推断`（由信号合理推出）、`假设`（缺少依据的暂定）。注意与需求推断卡的来源标记区分：推断卡用 `原话/推断/假设`，判读单用 `明确/推断/假设`。交付时列出仍为「假设」且未经用户确认的条目。

用户改了某个条件（如“其实是给前台在手机上用的”），只重算受这个条件影响的决定并更新判读单，不推倒重来。
