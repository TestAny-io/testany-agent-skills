# 视觉设计指南

制定视觉方向时读「定位与基线」，并按 [视觉方向与构图决策指南](design-direction-guide.md) 逐页选主轨、构图和三轴；组件匹配按需读 [组件选择与组合指南](component-composition-guide.md)，交互编排读 [交互编排与动效设计指南](interaction-design-guide.md)；代表页及自检时读「运行、观察与有限迭代」。ui-designer 与 prototype-designer 共用；「设计记录」「交付记录」的含义见质量清单开头。验收项统一放在 [质量清单](quality-checklist.md)，不另建重复报告。

## 定位与基线

### 先理解页面的工作

从需求基线、用户上下文和 [设计判读](design-inference-guide.md) 的判读单中提取受众、主要任务、使用频率、设备、语言和信息量，先数一下每页首屏需要承载多少信息，再按 [六种页面主轨](design-direction-guide.md#按页面任务分轨) 判断每页的第一目标、密度和动效倾向，用一句具体描述说明设计目标。

主轨是页面任务，不是互斥产品分类；同一产品的不同页面可以有不同主轨和密度，但共享视觉语言。精美可以体现为准确、克制、秩序，也可以体现为鲜明的视觉表达，具体选择由任务决定。

### 设计依据的优先级

1. 用户本次明确的方向、保真度和有效范围。
2. 项目品牌、设计系统、真实 token、组件与代表页面。
3. 在前两项留出的空间内，根据用户任务补充的设计决策。

参考网站或截图用于提取有用的层级、节奏、材质和交互方式，不替代项目品牌，不照搬无关业务内容。区分「来源事实」「本轮设计决定」「待澄清」；找到矛盾时只问影响整体方向的缺口。

| 现状 | 执行方式 |
|---|---|
| 成熟系统 | 引用真实 token 和组件变体，精修组合、布局、内容与细节 |
| 系统不完整 | 保留已有身份，为缺口补齐少量规则并注明来源 |
| 无现成系统 | 建立最小基线和代表页，不因样本少而跳过设计 |
| 已有页面存在体验缺陷 | 记录具体影响，在沙箱允许范围内改进；复用的生产组件本身无法修正时记录限制，不重写平替或越界修改 |

### 视觉方向记录与 token

视觉方向写在设计记录中（ui-designer 的设计说明与设计语言，prototype-designer 的 Manifest Visual Brief），避免另造一套必交文档。至少写明任务、页面主轨、方向句、三个校准轴、六层视觉语言、构图、内容主角、设计签名、代表页、目标视口/主题、参考来源和本轮不覆盖项。对「专业、简洁」这样的形容词补充实现含义，例如「正文与数据优先，主操作集中，组间留白明显，颜色主要表达状态」。

基线覆盖：颜色角色、字体角色、间距、布局宽度/断点、控件密度、圆角/边框/阴影、图标、动效。已有 token 用真实名称和路径；新增值说明用途并限定沙箱。无需为每一项创造新值，也无需用齐所有字体层级或动画。

## 视觉规则：用决策组织页面

### 1. 排版与信息层级

- 给页面标题、分组标题、正文、标签、辅助信息明确角色；通过字号、字重、位置和留白共同区分，避免同时放大加粗着色所有标题。
- 优先使用项目字体；补齐字体时检查实际可用性与中英文回退。无系统时可从一个正文家族加必要的数字/代码字体起步，不设禁用某字体的通用规则。
- 正文行高与内容宽度一起观察，长文本不能挤成密墙，也不能过宽难以追行。英文约 45–80 字符、中文约 25–40 字可作起点，均是可调整建议，不是验收门槛。
- 表格的可比较数字可用等宽数字并按含义对齐；金额、单位、时间格式一致。辅助文字仍须可读，不能用过小字号或极低对比制造“精致感”。

### 2. 配色、层次与质感

- 按用途分配背景、表面、正文、次要文字、边框、强调和状态色；前景/背景成对检查。避免每个页面重新挑颜色。
- 控制视觉焦点：同一操作组区分主次，品牌色不与错误/成功语义混淆；状态同时提供文字或图标等线索。
- 用背景层次、边界或适量阴影表达分组与覆盖关系。圆角和阴影遵循组件角色，不能给每层容器都叠加装饰。
- 渐变、玻璃、插画和高饱和色只有在契合 brief 且不妨碍内容时采用；不把使用或不使用某种效果当成品质本身。

### 3. 布局、留白与密度

- 先确定主内容、辅助内容和操作区，再选择网格、分栏和内容宽度。元素有共同对齐线；图标与文字还要检查视觉对齐。
- 避免把网格理解为等宽等高：按内容权重选择主导比例、结构化非对称、横带、主从或层叠；需要大量同构比较时才使用规则网格。构图选型与风险见视觉方向指南。
- 复用项目间距尺度；缺失时可用 4/8/12/16/24/32/48 等作为起点。相关元素距离近，组与组距离大，留白表达关系；不要求所有数值机械落在倍数上。
- 比较大量同构数据时考虑表格；浏览独立对象时考虑列表或卡片。依据扫描和操作任务选择，不把所有内容包装成卡片。
- 紧凑界面保留分组与操作余地；舒展界面仍要保持信息效率。表格列数、页面留白没有脱离场景的固定好坏阈值。
- 目标窄屏应明确如何重排、折叠或局部滚动，关键动作与重要数据仍可到达。桌面专用任务记录最小支持宽度，不擅自扩大为完整移动产品。

### 4. 组件、内容与完整状态

- 使用现有组件的正确变体，统一图标来源、线宽与光学尺寸。包装组件仅处理组合和真实缺口，避免覆盖内部样式导致 focus/disabled 失效。
- 业务文案与 mock 数据共同参与构图：使用可信名称、长短混合内容、合理单位与真实字段关系。转化页需要的案例成果、评价、数字可以用示例内容做出完整效果，在设计记录中标明待替换，不留空也不删掉这些结构。
- 正常、加载、空、错误、边界状态共享布局语言。骨架与最终内容结构接近；失败说明原因和恢复动作，空态引导下一步。
- 检查 hover、focus、pressed、selected、disabled、loading 的适用状态，不能只对鼠标悬停做设计。状态切换不应引起不必要的页面跳动。
- 状态演示开关采用明确标注的工具区或 URL 参数，不能混入业务导航或遮挡待评审的界面。

### 5. 动效与交互节奏

- 动效解释打开、关闭、排序、确认等状态变化；控制范围与节奏，避免每张卡片都动。默认使用仓库能力和 CSS，不为装饰新增依赖。
- 先在设计记录写清关键交互编排，再实现动画；过渡需回答从哪来、变成什么、到哪去，直接操控还要覆盖跟随、阈值、速度、吸附与取消。
- 保持输入响应，允许中断适用动画，尊重 `prefers-reduced-motion`。关闭动效后仍能理解状态变化。
- 保存后留在当前页、进入详情或返回列表，由 Journey 的下一步决定；保留必要的筛选、输入和返回上下文。
- 字段错误靠近字段；页面无法使用的错误可采用页面级反馈。同类任务保持一致，但不能把所有错误都强制为 toast 或 inline。
- 确认、撤销和防重复提交按操作后果选择，避免对每次创建/编辑弹确认，也不能把“创建”一概认定为无风险。

### 6. 美观与质感：让普通用户觉得好看

层级集中和样式克制是为了让重点清楚，不是把页面做“素”。目标用户（不是设计师）第一眼要觉得好看、想继续看。

- **主视觉要有质量**：优先用真实照片；没有照片时，画有细节、有光影和氛围的插画或场景图，与产品气质一致。统一的几何示意图、灰色占位块会让整页显得像线框。
- **字体有气质**：展示类页面的大标题选一款有性格的展示字体（中文常见做法是宋体或明朝体标题配黑体正文），调好字重、字距和行高；工具类页面把数字和标签的层级做清楚。
- **配色和谐**：一个主色、一组中性色、少量点缀；可以从主视觉图片里取色。广受欢迎的好看组合（暖色纸张底配衬线标题等）契合产品就可以用。
- **细节做足**：图标风格统一，圆角、阴影、分隔线和纹理有精致度，空态和加载态也有设计。
- **自检**：把截图当作目标用户来看，问“一般人看到会觉得好看、想点进去吗？”，再和同类产品里做得好的网站或应用比一比。答案是否定的，先补质感，再谈与众不同。

## 运行、观察与有限迭代

### 代表页到全范围

先做一个能代表核心任务、布局和状态的页面并观察实际效果；有明显层级、密度、模板默认项、溢出、组件或交互问题时先修正，再扩展。扩展门槛见视觉方向指南的「代表页完成门槛」。后续仍需检查全部本轮非占位页面，代表页通过不能代替全范围检查。P1 占位页只验标识、导航及基础视觉一致性。

### 四遍批判式观察

对同一份实际截图和可运行页面依次观察，避免一边改颜色一边漏掉结构问题：

1. **三秒扫视 + 测量**：第一眼落在哪里，是否就是任务主角；主要操作是否可发现；再用测量证据核对最大区块占比和首屏信息单元数，确认主角不是错觉。
2. **构图、语言与美观**：以目标用户的眼光判断是否好看、想继续看；再检查比例、对齐轴、留白、字阶、强调色落点与面积、材质和真实内容；回答「第一屏给了谁、删掉了什么」，并核对三轴声明与实测一致。
3. **交互与状态**：实际触发 hover/focus/pressed/loading、P0 编排和关键业务状态，检查空间连续、反馈、恢复、焦点与减少动效。
4. **辨识与韧性**：核对模板默认项是否都有事前声明、所用视觉手法的代价是否已规避；再放入长文本、空/错误/边界数据和最窄视口，确认设计签名仍成立且页面没有因真实内容崩塌。

每遍只记录能定位的观察与影响，不用「不高级」「再好看点」作为问题。先修构图和任务焦点，再修 token 与组件细节，最后调整动效参数。

### 测量证据

测量用来定位问题、核对设计记录，不是验收阈值：不因某个数值本身判缺陷，只在它与设计记录矛盾或解释了可见的任务问题时使用。代表页必测，其余页面在构图变化或出现相应症状时测；数值、方法、实际 URL 和视口写入交付记录。

| 测什么 | 怎么测 | 用来判断 |
|---|---|---|
| 首屏各主要区块的可见面积占比，最大与第二大之比 | 读取区块的 bounding box（下方片段一），或在截图上量 | 主角是否成立：四块各占四分之一、最大块只占一成多，说明没有主次。主视觉铺满整屏背景，或主角靠颜色和字号而不是面积取得时，面积比没有意义，改为说明主角靠什么突出 |
| 同级模块的尺寸种类 | 同一层级区块的宽高去重计数 | 全部等大往往等于没有主次；种类过多又显得零碎 |
| 强调色落点与面积 | 列出使用强调色的元素，在截图上估算面积 | 是否只落在当前状态、主操作或异常上；面积越大越难成为“重点” |
| 首屏可见信息单元数 | 在目标视口首屏数能单独读出含义的最小单元：一个指标、一条记录或一张卡、一个图表、一个主要操作区；同构的重复项逐个计数，装饰和纯标签不计；进度点、路线站点这类导航性的重复标记合计算一个 | 与 `visual_density` 一致：约 8 个以内对应 1–3 档，约 9–30 个对应 4–7 档，30 个以上对应 8–10 档；同样内容量下判断“太空/太挤” |
| 偏离惯例项 | 对照页面决策中的清单逐条确认 | 与 `design_variance` 一致 |
| 字号、圆角、阴影的种类 | 读取首屏元素计算样式去重计数（下方片段二） | token 是否泛滥；“太花”通常表现为种类过多 |

无法自动测量时可在截图上估算并标注「估算」；没有浏览器能力时记 `evidence_gap`。不要为测量新增依赖。自己写的测量和检查脚本放在 `evidence/` 下，可以重跑。文字压在插画或照片上时，在文字背后的区域取样像素算对比度，取最不利的位置。

在任意可执行页面脚本的浏览器能力中，可用以下片段读取数据。片段一按本页主要区块填写选择器：

```js
((selectors) => {
  const vw = innerWidth, vh = innerHeight;
  return selectors.map((s) => {
    const el = document.querySelector(s);
    if (!el) return [s, null];
    const r = el.getBoundingClientRect();
    const w = Math.max(0, Math.min(r.right, vw) - Math.max(r.left, 0));
    const h = Math.max(0, Math.min(r.bottom, vh) - Math.max(r.top, 0));
    return [s, Math.round((w * h) / (vw * vh) * 1000) / 10]; // 首屏面积百分比
  });
})(['main', 'aside', '#hero']);
```

片段二统计首屏可见元素的字号、圆角和阴影种类；结果包含组件内部元素和被遮挡的元素，按角色解读，不直接当作缺陷：

```js
(() => {
  const seen = { fontSize: new Set(), borderRadius: new Set(), boxShadow: new Set() };
  for (const el of document.querySelectorAll('body *')) {
    const r = el.getBoundingClientRect();
    if (!r.width || !r.height || r.top >= innerHeight || r.bottom <= 0) continue;
    const cs = getComputedStyle(el);
    if (cs.visibility === 'hidden' || Number(cs.opacity) === 0) continue; // 跳过不可见元素
    if (el.childNodes.length && [...el.childNodes].some((n) => n.nodeType === 3 && n.textContent.trim())) seen.fontSize.add(cs.fontSize);
    if (cs.borderRadius !== '0px') seen.borderRadius.add(cs.borderRadius);
    if (cs.boxShadow !== 'none') seen.boxShadow.add(cs.boxShadow);
  }
  return Object.fromEntries(Object.entries(seen).map(([k, v]) => [k, [...v]]));
})();
```

### 证据与执行

1. 用可用浏览器能力访问真实入口，记录当前实现版本/变更基线与运行命令。不得假定某个宿主、Playwright、截图工具或图像生成工具必然可用。
   - 浏览器工具打不开本地文件时，在输出目录用只读静态服务打开（如 `python3 -m http.server`，只绑定 127.0.0.1），结束时关闭。
   - 浏览器可能被其他会话共用：在独立的浏览器上下文或新标签页中取证，并核对截图和测量时的实际 URL 与视口。
   - 浏览器工具可能在当前工作目录写日志或快照；结束前检查允许范围之外有没有新增文件，有就清理并记录。
   - 修改后复验前关闭缓存或给资源加版本参数，避免读到旧的样式和脚本，误以为修改没生效。
2. 逐页在设计记录约定的目标视口检查正常态；关键空/错误/加载/边界态在代表视口检查；对会改变布局的状态补最窄目标视口，避免机械执行全部笛卡尔积。只测约定主题，用户未要求时不额外创造暗色版本。
3. 保存并实际查看视口截图，必要时加全页图或细节图；按四遍批判式观察和测量证据检查焦点、构图、六层视觉语言、模板默认项、内容韧性及细节。截图存于沙箱内的证据目录或用户已允许的位置。
4. 对照交互编排实际触发 P0 Journey、状态切换及适用的表单/返回/弹窗/拖拽/键盘操作，分别记录触发、反馈、完成、恢复与焦点的预期和实际。截图无法证明保存、导航、吸附、焦点恢复等行为成功。
5. 将问题集中修正，更新相关截图并复验受影响行为；证据须对应当前实现，不能拿修改前的截图宣称修改后通过。

在交付记录中写明：页面/路由、状态、视口、触发动作、截图/运行记录路径、预期/实际、问题 ID 和复验结果。检查截图中的内容，不仅报告“截图已保存”。

首次做一轮完整观察；有问题时按批修正并复验，通常最多两轮集中整改；复验中顺带发现的新问题可以继续修，但要记入问题清单。无新问题即结束，不为凑轮数改样式；预算耗尽或同一阻碍反复出现时交付现状、剩余问题与下一步，不能降低完成条件来宣称通过。

### 能力缺口

- 能运行但无法截图/观察：保留真实运行及交互证据，将视觉验证列为未完成。
- 无浏览器或不能启动：继续可做的代码、追溯、隔离和设计检查；记录错误与影响，交付可检查的草稿，不虚构浏览器结果。
- 工具缺失不自动取消视觉要求、不擅自扩展依赖安装或修改生产配置；按已有授权使用可用替代能力，无替代则明确 `evidence_gap`。

## 正反例：同一工作台任务

**任务**：测试负责人按失败原因筛选执行记录、查看详情、重试。

- 缺少设计决策：顶部占半屏的欢迎区，所有指标、筛选和记录都有同等阴影卡片；失败仅用红色表示；长用例名挤掉重试按钮。
- 有依据的设计：紧凑标题与明确的主要操作，筛选紧邻列表，失败状态有文字与图标，可比较数字对齐，详情保留返回上下文；正常/空/失败/长名称均按同一 token 系统布局。
- 验证：观察实际最窄目标视口的长名称截图，点击重试检查 loading 与失败恢复，键盘打开并关闭详情后确认焦点。不能只凭组件名称或代码结构下结论。
