# 设计与原型质量标准

ui-designer 和 prototype-designer 实现时遵循、交付前逐项自检；prototype-reviewer 的门二使用同一标准。设计方法见 [视觉设计指南](visual-design-guide.md)，本文件定义检查与完成条件。

本文中的「设计记录」指 ui-designer 的设计包（`design-brief.md`、`design-language.md`）或 prototype-designer 的 Manifest；「交付记录」指设计包的证据部分或 prototype-designer 的交付摘要。

| 维度 | ui-designer | prototype-designer |
|---|---|---|
| 1 可访问性 | 适用 | 适用 |
| 2 Mock 数据与内容 | 只查内容是否可信、是否覆盖长短与边界内容 | 适用 |
| 3 组件使用纪律 | 仓库模式适用，按 `[DESIGN]` 规则 | 适用 |
| 4 视觉方向与构图 | 适用 | 适用；有设计包时核对是否符合设计包 |
| 5 交互编排与动效 | 适用 | 适用 |
| 6 UX 走查 | 只查已设计页面和关键状态 | 适用 |

## 1. 可访问性基线

检查本轮页面适用的基础项目，记录实际覆盖；这不构成完整 WCAG AA 合规声明。用户明确线框稿时同样保留可读性、语义与键盘要求。

| 检查项 | 实现与验证 |
|---|---|
| 语义与键盘 | 操作用原生 button，导航用链接，输入关联 label；交互可聚焦、可用适当键操作，不能仅给 div 加 tabIndex 就声称支持键盘 |
| 焦点 | 焦点可见、不被遮挡；弹窗打开时合理移入、模态内部循环、Escape 关闭，关闭后回到触发点或 Journey 合理位置 |
| 名称与反馈 | 图标按钮有可访问名称；动态反馈按语义使用 status/aria-live，避免每次重绘重复播报；状态不只靠颜色 |
| 文字对比 | 普通文字至少 4.5:1，大号至少 3:1；大号按 WCAG 的 18pt 或 14pt 粗体定义，不按“标题”标签判断；非活跃控件、标志等按标准例外处理 |
| 非文字对比 | 识别控件/状态所必需的视觉信息与相邻颜色至少 3:1；不要求所有装饰边框达到该数值 |
| 点击目标 | Web 通常至少 24×24 CSS px，或满足间距、行内等标准例外；触屏可选更大舒适目标，不能把 44px 冒充 WCAG 通用下限 |
| 缩放与动效 | 不禁用浏览器缩放；目标视口文字和操作不被截断；尊重减少动效偏好，静态情况下仍能理解状态。按视口等比缩放的固定画布（挂墙大屏、展示屏）会让浏览器缩放失效，要在设计记录中声明，并说明在普通屏幕上查看时如何保证可读 |

自检：实际完成关键键盘路径和弹窗焦点检查；按真实前景/背景检查对比度，说明测量工具或方法。不能仅凭肉眼把对比度写为已通过；无法测量的项目记未验证。

标准来源：[文字对比](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[非文字对比](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)、[点击目标](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)、[APG 对话框](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)。具体适用例外以对应标准为准，不外推为整站合规。

## 2. Mock 数据与内容质量

仓库模式下 Mock 集中放在沙箱 `mock/` 下，服务交互验证、视觉构图和下游数据发现；独立模式的设计页面同样使用可信内容。

- [ ] 核心字段与需求基线（PRD 或需求推断卡）中的业务实体一致；额外 UI 数据需求在设计记录中标注为「需求未定义」，不擅增业务功能。
- [ ] 数据依赖页有正常、空和至少一组相关边界数据；单个对象用 null/缺失字段等表达空态，不强制所有实体都是数组。
- [ ] 名称、时间、单位、状态和字段关系可信；包含长短文本、中英文混排等本轮真实内容特征。
- [ ] 高密度列表、长标题或特殊字符等按页面风险选择，不能用固定条数代替边界覆盖。
- [ ] 类型遵循仓库技术栈；TypeScript 项目提供可复用类型，其他项目不因此引入 TypeScript。

## 3. 组件使用纪律

### 三级规则

| 优先级 | 场景 | 处理 |
|---|---|---|
| 1 | 已有完全匹配组件 | import 使用，禁止重写平替 |
| 2 | 已有近似组件 | 使用公开 Props、组合或沙箱包装；标注包装为 `[PROTOTYPE]` |
| 3 | 无对应组件 | 沙箱内新增最小组件，标注 `[PROTOTYPE]` 并在 Manifest 记录缺口 |

ui-designer 在现有组件无法表达设计决定时，可在沙箱新增 `[DESIGN]` 组件，并在设计语言中记录对应的生产组件、替代理由和对组件库的改进建议；prototype-designer 使用这些已记录的 `[DESIGN]` 组件不算平替。规则见 [前端仓库与原型沙箱](../frontend-sandbox.md#4-沙箱目录与隔离规则)。

- [ ] 保持现有样式方案；未新增依赖、修改生产组件或全局主题。
- [ ] 组件类型与该页构图和任务匹配：比较优先表格/列表，独立对象才用卡片；popover/dialog/drawer/inline/page 按任务长度、阻塞性、上下文和 URL 需求选择，不用同一种容器解决全部问题。
- [ ] 关键组件在设计记录的组件清单中记录任务角色、公开变体/密度与适用状态；组件一致性按相同语义判断，不要求所有组件同圆角、同阴影、同尺寸。
- [ ] 沙箱 token/样式有作用域，不能通过全局选择器影响生产页面。
- [ ] 包装和视觉调整没有破坏焦点、disabled、语义或布局能力。
- [ ] 组件、图标、字体、素材的实际来源已核实，未假设不可用的包或资源。

## 4. 视觉方向与构图

对照设计记录中的视觉方向、页面设计决策、实际 token、代表页和交付记录中的测量证据检查。无旧页面时对照本轮新建基线，不跳过本维度；线框稿按用户指定保真度评价，不强求颜色或装饰。

| 维度 | 观察与判断 |
|---|---|
| 设计判读 | 主要设计决定（视觉性格、主轨、密度、动效、主要组件）都能指回需求信号；视觉性格至少有一条产品特有的依据，不只来自行业；假设已标出；页面实际表现与判读单一致，或已更新判读单 |
| 惯例与目标 | 核心布局遵循领域惯例（日程、表格、邮件、地图、购物等），偏离有任务依据且第一次使用不别扭；每个 P0 任务至少有一个为场景设计的省力操作；转化页有向往的结果画面、具体的证明和低门槛的下一步 |
| 美观（目标用户视角） | 目标用户第一眼会觉得好看、想继续看；主视觉有质量，不是统一几何占位或灰块；字体、配色、细节有完成度；与同类做得好的产品相比不显简陋 |
| 分轨与方向 | 每页主轨与任务一致；方向句已经变成实际构图和组件选择，不是只写了风格词；页面共享视觉语言，相邻页面没有无理由复制同一主构图 |
| 任务与焦点 | 3 秒扫视首先看到的内容与主要任务匹配；同一操作组有明确主次；装饰没有抢占工作区域 |
| 构图与视觉重量 | 第一屏分配、主导比例、对齐轴、层叠/留白和滚动节奏有意图；能回答重量落在哪里、第一屏给了谁、删掉了什么；测量证据（最大区块占比、首屏信息单元数、偏离惯例项）与该页三轴和方向句一致 |
| 排版 | 字体角色、字号、字重、行高有层级；文字清晰；中英文、数字和单位协调，换行与截断有合理策略 |
| 配色 | 语义颜色一致；强调色只落在声明的元素上，面积与用途相符；前景背景搭配可读；状态同时有非颜色线索 |
| 布局与密度 | 对齐稳定，组内/组间间距表达关系；内容宽度与密度符合任务，避免不必要的嵌套容器 |
| 细节 | 图标、圆角、边界、阴影符合角色；不同控件及其状态具有一致完成度 |
| 设计签名 | 1-3 个识别点与业务内容或交互关系相连；移除品牌名后仍不至于无损套到任意产品；没有让每个组件同时抢戏 |
| 模板默认项 | 页面中出现的生成默认项（通用 hero、等权卡片墙、装饰渐变/玻璃/发光、随机图标底板、虚构指标等）都在设计记录中事前声明且依据成立；所用视觉手法的代价已规避 |
| 跨页与多状态 | 正常、加载、空、错误、边界态共享视觉语言；页面例外有依据，没有任意换字体/颜色/密度 |
| 适配 | 约定视口下无意外遮挡、错位、内容丢失；局部滚动或折叠可发现，主要操作仍可到达 |

每个结论给出观察依据，例如「窄屏长用例名把重试按钮挤出可视区」「所有标题和指标同等加粗，难以区分当前筛选结果」「页面决策写 V=8，但实测四块各占约四分之一、无偏离惯例项，仍是居中标题加三张等权卡」。测量值本身不构成缺陷，与设计记录矛盾或造成任务影响才构成问题。风格问题应说明与目标用户、任务或设计记录的关系及可行改进；“不高级”“我不喜欢绿色”不能单独构成缺陷。

## 5. 交互编排与动效

对照设计记录中的交互编排和组件清单的适用状态实际操作。存在 CSS 动画或事件处理代码不等于交互已经成立。

| 维度 | 观察与判断 |
|---|---|
| 因果与反馈 | 每次输入有及时、适量的接收反馈；用户知道哪个对象触发了变化，不出现无来源弹层或无结果点击 |
| 空间与对象连续 | 打开/关闭、展开/收起、列表/详情与图标状态保持来源和身份；返回后找得到原对象及上下文 |
| 直接操控 | 拖拽/滑动跟手，距离/速度阈值、边界阻尼、合法吸附点和取消路径成立；有键盘/按钮等价方式 |
| 状态转换 | loading/success/error、筛选联动、数字/图表变化和通知计数彼此一致；骨架与最终内容几何接近，不无故跳动 |
| 节奏与预算 | 每页 1-3 个招牌时刻有任务含义；其余动效服务反馈和空间；开始、减速、吸附、完成和回收完整且可中断 |
| 输入适配 | hover 不承载唯一信息；touch、键盘、系统事件和窄屏有可用路径；焦点、动态播报与命中区域合理 |
| 减少动效 | `prefers-reduced-motion` 下取消大位移、视差、循环和弹性后，状态含义、焦点和操作路径仍成立 |
| 实现克制 | 使用项目已有能力或交互指南的实现手法（FLIP、共享滚动进度、两层弧线等），未为装饰新增依赖；未用 `transition: all` 掩盖状态设计，动画结束不是唯一业务状态来源 |

完整编排至少实测触发、反馈、完成和一个适用的恢复路径；一行编排至少实测触发、结果与返回。截图只能作为关键帧证据，不能证明拖拽吸附、焦点返回、撤销或数据同步。

## 6. UX 走查

按 P0 Journey（或推断卡 P0 任务）真实操作，针对本轮适用场景验证，不用查到一个条件渲染分支代替行为证据。

| 场景 | 应观察的结果 |
|---|---|
| 提交与保存 | 请求中有清晰反馈并防重复操作；成功后数据更新，去向符合 Journey；失败保留合理输入并提供恢复动作 |
| 校验与错误 | 字段错误可定位，提交失败能找到需修正处；局部或全页错误按影响范围选择，不误清空无关内容 |
| 空态与无结果 | 区分首次空数据、筛选无结果和加载失败；适用时有创建/清筛选/重试等可执行下一步 |
| 导航与返回 | 链接目标正确且在原型前缀内；Back/Forward、返回来源及筛选/滚动上下文符合 Journey |
| 弹窗与键盘 | 焦点进出合理，键盘能完成主要操作；覆盖层不会吞掉后续操作或让焦点迷失 |
| 破坏性动作 | 按后果、风险和可恢复性选择确认或撤销；Mock 中也展示约定行为，不一律对创建或归档套同一规则 |
| 信息组织 | 表单按业务关系分组，重要字段与操作易发现；表格列数和信息披露按任务判断，不按固定列数认定过载；流程和制度类内容按用户所处步骤渐进展示，第一屏能回答“我现在该做什么”，不在开始前铺满全部规则 |
| 边界与适配 | 长文本、大数据、禁用、加载等仍可理解与操作；目标最窄视口下操作路径成立 |

## 问题分层与完成标准

采用 [共同评审规则](../review-assurance.md) 的 kind 与严重度；作者自检和 reviewer 使用同一口径。

| 情况 | 记录与处理 |
|---|---|
| 主要操作不可到达/不可用、严重遮挡或不可读、关键状态丢失等有证据的缺陷 | `defect`，按影响判 P0/P1/P2；重大体验缺陷必须修复，不一律降为建议 |
| 有证据显著偏离本轮有效设计约定，影响核心演示或用户任务 | `defect`，绑定具体要求、截图与影响判级；不得凭个人偏好定 P1 |
| 少量视觉润色或另一种同样合理的风格 | `optional` / P2，记录、不按数量阻断 |
| 浏览器、截图、对比测量或必要基线不可得 | `evidence_gap`，列受影响结论；必要证据不足则未完成验收，不能冒充已证实代码缺陷 |
| 品牌/范围要求冲突且无有效取代决定 | `scope_decision`，只问冲突点，继续不依赖该决策的检查 |

- **完成**：本轮适用范围无未关闭 P0/P1，必要视觉与交互证据充分；设计符合设计记录，轻微建议可以保留。
- **未完成验收**：可交付可运行草稿、自检记录和剩余项，明确原因，不将“代码已写”“启动成功”说成视觉或交互验收通过。
- **独立准出**：原型由 prototype-reviewer 按其范围与证据判断；作者自检不签独立批准。

问题记录在交付记录中：稳定 ID、kind、严重度、页面/状态/视口、证据、影响、修正建议、状态及复验。已有页面缺陷应在沙箱内可行地改进；无法在允许范围修复的，保留限制及影响，不擅改生产代码、不虚报通过。
