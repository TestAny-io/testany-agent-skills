| c3 执行进程存活，锁被其他 pid 持有 | `ready` | 锁被占用 | 一致 |
| c4 执行进程已退出，`source` 等于本实例 | `ready` | 锁可回收 | 一致 |
| c5 执行进程已退出，`source` 不同 | `failed`（“重启任务未完成。”） | — | 一致 |
| c6 锁文件残留，其 pid 已被另一用户的进程占用（以 pid 1 模拟，`EPERM`） | `restarting` | 锁也被判为占用（`BUSY`） | 两者判断一致；但“避免 pid 被复用时误判”不完全成立（APIR8-P2-03 a） |
| c7 未被接受（无 `executor`），`preparing` | `preparing` | — | 一致：未被接受的任务不被误判 |

判断：

- 定义自洽、可实现，与实现一致。
- 改用“持锁”判断后，健康检查与启动锁对“执行进程是否还在”的判断完全一致，比比较时间更稳妥。
- 只是“避免 pid 被复用时误判”说过了：锁文件残留、其 pid 又被复用时，两者都会判为“仍在运行”。这是启动锁自 0.10.2 起就有的限制，不是本轮引入的。

### 5.4 G-16、G-17 与 0.10.2、0.10.3 冻结代码及实现

**APIR8-P2-03 执行进程判断、G-16 分界与窗口期任务**

- (a) **“避免 pid 被复用时误判”说过了。**

  - 两者判断一致，限制来自 0.10.2 起就有的启动锁设计。
  - 建议改为“与启动锁的占用判断一致”，并注明这一残余：直到该 pid 退出或锁文件被移除。
- (b) **G-16 两种情形的分界。**
  - 实验 E1：0.10.x 协调器在服务开始关闭后就不再改写（`if (closed) return;`）。所以“旧实例已收到停止信号、尚未退出”时被终止，结果与 (a) 相同（保持 `restarting`、带 `executor`）。
  - 建议把 (a)(b) 写为“旧实例收到停止信号之后 / 之前”。
  - 并补一句：(a) 之后没有实例运行时，记录停在 `restarting`，直到下一次非任务启动按 G-17 关闭；此前没有健康检查可报告。
- (c) **窗口期任务的接受。**
  - 7.4 承认“协调器写入、启动器尚未取锁”的窗口，并让第二条规则避开它；第一条规则（G-17）却会在这个窗口里关闭尚未被接受的任务。
  - 实验 E3：任务被关闭后，它自己的启动器取锁时仍会接受并执行，因为接受时不看 `status`（`launch.mjs` 第 185 行）。
