## 阶段 1 代码复核 R2-P2-02：迁移取锁顺序

### 文字与实现是否一致

v1.11 第 704～705 行与第 1013 行写的是：先取启动锁；构建好新运行目录后取实例锁与 Codex 锁（Codex 配置根存在时），锁被占用时在停止任何实例之前失败、旧实例照常运行、不算迁移失败；持锁后再停止存活的旧实例，两把锁一直持有到新实例写好启动记录，或迁移失败后旧实例恢复；接管后台注册在上述锁内进行。

| 条文 | 实现（`2b7a4f3` 中的代码，与 `74cce24` 相同） | 判断 |
|------|-------------------------------------------|------|
| 先取启动锁 | `launch.mjs` 第 231～233 行取 `launcher.lock`（不等待，忙即“另一个启动操作正在运行”），持有到第 360 行 `finally` | 一致 |
| 构建后取实例锁与 Codex 锁 | 第 318 行 `prepareRuntime`，之后第 336 行 `withStateLocks`；`state-locks.mjs` 第 15～29 行先实例锁、再 Codex 锁，Codex 根不存在时不取 | 一致 |
| 锁忙时在停止之前失败，不算迁移失败 | `withStateLocks` 在进入回调之前抛 `BUSY`；第 354～357 行在“`BUSY` 且未停止旧实例”时给出“……未停止现有服务；请稍后重试。”，任务记为 `failed`；`writeMigrationFailure` 只在第 325～333 行的 `recover` 中调用 | 一致。实验 P1：旧实例 pid 不变，0.10.x 读取的文件逐字节不变，没有 `migration-failure.json` |
| 持锁后停止存活的旧实例 | 第 337～338 行：锁内先核对记录未变，再 `stop(current, …, { locked: true })` | 一致 |
| 锁持有到新实例写好记录或旧实例恢复 | 第 339～347 行：迁移、`startRuntime`（写记录）与 `recover`（恢复旧实例）都在回调内 | 一致；另有第 6 步的情形（迁移已完成、新版启动失败）同样在锁内结束，条文未提，见 R19-P2-02 (a) |
| 接管后台注册在锁内，有限次数重试 | 第 140～164 行 `migrate`：`TAKEOVER_ATTEMPTS = 3`，失败则撤销触及的文件 | 一致 |
| “锁被占用时”即失败 | 实现先等待 `lockWait`（默认 60 秒）再失败 | 属“锁的细节在实现中定”（DG-NO-LLD）；措辞见 R19-P2-02 (b) |

另：非存活的旧记录（健康检查不匹配）仍在取实例锁之前经 `stop` 处理（第 296～297 行，0.10.x 记录在进程已不在时删除，与 0.10.2 相同）。条文第 1 步只约束“存活的旧实例”，两者不冲突。

仓库测试（`launcher.test.mjs` 中实例锁、Codex 锁忙时重启，锁忙时 `stop`；`migration.test.mjs` 中代号 1 迁移时实例锁忙）在导出副本中运行，4 项全部通过。本轮补做的探针 P1 覆盖了代号 1 迁移时 **Codex 操作锁**忙的情形（这正是 0.10.x 后台任务与服务使用的锁），带与不带 0.10.x 重启任务各一次，结果见契约第 11 轮报告第 5.4 节。

### 对 0.10.3 与 0.10.2 冻结代码可观察行为的影响

新顺序是 0.11 自身的行为。逐项核对冻结代码与这把锁、这个时序有交集的地方：

| 交集 | 冻结代码事实 | 新顺序下的表现 | 判断 |
|------|-------------|---------------|------|
| 启动锁 `launcher.lock` | 0.10.2、0.10.3 的 `launch.mjs` 取锁不等待（`337547a` 第 144 行）；36b 第 61 行、S-17a、S-17b | 0.11 仍最先取得、持有到结束，与 v1.10 相同 | 不变 |
| 实例锁 `instance.lock` | `git grep` 证实 0.10.2、0.10.3 都不使用 | — | 无交集 |
| Codex 操作锁 `<CODEX_HOME>/.skilldock-operation.lock` | 0.10.2 `service.mjs` 第 121 行、`background-worker.mjs` 第 62、85 行；0.10.3 同（第 121 行；第 66、89 行）：都不等待，忙即返回 `BUSY` 或跳过 | 0.10.x 持锁时：0.11 等待有限时间后失败，旧实例不被停止（实验 P1）。0.11 持锁、旧实例尚未停止的数秒内：0.10.x 的写操作得到它原有的 `BUSY`。v1.10 的顺序下，0.11 在接管期间同样持有这把锁 | 冻结代码的处理分支不变 |
| 旧实例收到 SIGTERM 后的关闭路径 | 0.10.2 `index.mjs` 第 81 行 → `app.close`（第 73 行：`updater.close`、`service.close`、`scheduler.close`），都不取锁；只等待进行中的操作，而进行中的写操作必然持有 Codex 锁，0.11 此时取不到锁、不会发 SIGTERM | 不会出现“旧实例等锁、启动器等旧实例退出”的互等；0.11 自身服务的记录刷新与补写也只试取锁（`wait: 0`，`launch-plan.mjs` 第 79～86 行、`launcher-record.mjs` 第 118～127 行） | 不变 |
| 重启任务的终态 | 0.10.x 协调器只区分启动器退出码 0 与非 0（`self-update.mjs` 第 25 行）；36b 7.4 允许 `restored` 省略 | 锁忙：退出 1，`restart.json` 记为 `failed`、带 `executor`、不带 `restored`（实验 P1；G-12） | 在契约既有语义内 |
| 0.10.x 读取的文件 | 门槛失败与锁忙时都不得改动（3.7 第 698 行；36b 7.4 只允许接受任务后写 `restart.json` 终态） | `launcher.json`、`local/updates.json`、后台上下文与入口逐字节不变；没有 `generation.json` | 不变 |

结论：**新取锁顺序不改变 0.10.3、0.10.2 冻结代码的任何可观察行为**。与 v1.10 的写法相比，锁忙时旧实例不再被停止、恢复，也不会因此被记为迁移失败，对 0.10.x 用户的打断更少。锁忙不触发快速拒绝，0.10.x 协调器会再次发起，但每次最多等待 60 秒、不停止旧实例，不是快速拒绝要防的“反复停止和恢复”。

**R19-P2-01 3.3A：连续两次读回不一致时保留哪几份副本（建议在实现阶段 5 的 Claude 插件更新之前处理）**

- 有效依据：
  - 第 634 行：每个插件只保留最近一次更新前的副本；上一次读回不一致时保留那一份，下一次更新另存本次的更新前副本，“同一插件此时最多两份”；之后一次读回一致的更新完成时删除更早的那份；
  - 第 629 行：读回不一致后暂停该目标的自动应用，直到用户重新预览；
  - 第 636 行：更新确认中说明保留更新前副本供手动恢复。
- 当前问题：设插件原为内容 v0（最后一次读回一致）。第一次更新前另存副本 A（= v0），读回不一致；重新预览后的第二次更新另存副本 B（= 第一次装入的、与预览不同的内容），又读回不一致。此时：
  - 按“上一次读回不一致时保留那一份”，要保留的是 B；A 只有在“之后一次读回一致的更新完成时”才删除，所以也还在；
  - 第三次更新再另存 C，就有三份，与“最多两份”不符；若为守住“最多两份”删掉 A，丢掉的恰是最有价值的“最后一次读回一致的内容”。
- 影响：阶段 5 实现与 V11 核实时，对副本数量与该留哪一份会有不同理解。不改变已批准边界。
- 建议（推荐）：写明两个位置：
  - “基准副本”：最后一次读回一致之后、第一次读回不一致的更新之前的副本，一直保留到某次读回一致的更新完成；
  - “最近副本”：本次更新前的副本，每次更新替换；
  - 两者最多两份；读回一致的更新完成时删除基准副本，恢复只保留一份；`message` 写明各份位置与含义。
