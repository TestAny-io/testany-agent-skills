**作者的结论**（`37`:249）：通用指纹的结果保存在十多处记录里，全局忽略 `.DS_Store` 会让旧记录被误判；逐处兼容超出补丁版本；只放宽手动更新的两处会与计划绑定不一致；触发条件少。所以不在 0.11.1 改。

**对照代码**（已核对；没有做实验）：

- 指纹是 `hash(JSON.stringify(entries))`，`.DS_Store` 是其中的普通条目（`server/files.mjs:68-91`）。它被保存在七类记录里，写入点约二十处：
  1. 技能来源记录 `sources[key]`（`service.mjs:600`、`:641`、`:647`、`:1295`、`:1322`），其中还带逐文件摘要 `files`；
  2. 恢复记录的 `expectedFingerprint`、`priorFingerprint`（`:649`、`:660`、`:1074`、`:1659`、`:1664`）；
  3. Codex 插件基线 `pluginBaselines`（`:1411`、`:1600`）；
  4. 单插件记录 `registry.plugins[id].fingerprint`（`:1584`、`:1730`）；
  5. Claude 生成 marketplace 的来源记录（`:1014`、`:1521`、`:922`）；
  6. 计划绑定（`:1865`，对 `plugin-reinstall`、`skill-source`、`plugin-files` 三条路线带指纹）；
  7. Claude 插件基线（`:839`、`:847`、`:915`、`:921`，0.11.0 已处理）。
- 这些记录之后都按相等比较：技能检查 `:623`，Codex 插件 `:1370`、`:1379`，恢复 `:671`、`:679`，计划绑定按整段 JSON 比较（`:1392`、`scheduler.mjs:287`）。

**判断**：

- **主要理由成立。** 若在 `inspectTree` 里全局忽略 `.DS_Store`，凡是“记录时目录里已有 `.DS_Store`、现在还在”的对象，新算出的指纹都不等于记录：技能报本地修改，Codex 插件报基线变化，计划跳过并要求重新选择，更新前留下的备份因 `BACKUP_CHANGED` 无法恢复。最后一条作者没有提到，是最不该出的一种。所以“不做全局忽略”是对的。
- **“十多处”** 按写入点算属实，按记录的种类算是七类。
- **“只放宽手动更新的两处会与计划绑定不一致”** 说得对，但这不是回退：今天访达写入之后，手动与计划两条路都会停；放宽手动之后，是手动能过、计划仍跳过并给出已有的提示。
- **有一种更小的做法没有被单独权衡**：照 0.11.0 对 Claude 插件的办法，在判定“本地修改”的地方做有记录依据的放宽，而不动指纹本身。对独立技能尤其简单：来源记录里本来就存了逐文件摘要（`sources[key].files`），在 `skill.checkUpdate`（`:621-626`）把“记录中没有的 `.DS_Store`”从当前内容里去掉再比较、再出差异即可。它不需要新的存储格式，不需要兼容两种指纹，只会减少误报，不会让旧记录变成“已修改”；一处改动同时覆盖两侧的独立技能与 Claude 的技能目录插件。Codex 插件的基线只存了指纹，只能照 Claude 那样接受两三种口径，稍逊一筹。计划绑定仍需要另行设计，作者说与“计划绑定按版本目录计算”一起做是合理的。
- **还有一种不改判定的做法**：`skill.checkUpdate` 报本地修改时，用 `sources[key].files` 算出改了哪些文件；差别只有 `.DS_Store` 时，在提示里直接说出来（“差别只有访达写入的 `.DS_Store`，删除后可继续”）。这不改变任何放行或拒绝，只是让用户知道怎么办。

**给 Owner 的建议**：推迟是合理的，理由是触发条件少（SkillDock 没有“在访达中显示”，已核对界面与服务端都没有这类入口）、最终 UAT 只在 Claude 一侧碰到、而且更新与计划流程刚经过多轮评审。如果想在 0.11.1 里先减轻一点，按风险从低到高是：只改提示；只对独立技能做有记录依据的放宽。两者都不涉及 HLD 的冻结面，但后者会改 3.3A 之外的更新流程，需要写进 HLD 并复审。无论哪种，建议把上面第 4 点记进 37，后续版本从它开始设计；CHANGELOG 已如实写了“没有改的”。
