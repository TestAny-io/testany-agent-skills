### 对协调者几个问题的回答

- **强制读取“跟随”的实现有没有新的问题：没有发现（实测，探针）。**

  | 情形 | 结果 |
  |---|---|
  | 非强制读取在途，来了三个强制调用方 | 等它结束，然后只发一次强制读取，三个拿到同一个结果 |
  | 强制读取在途，又来强制读取 | 共用 |
  | 强制读取在途，又来非强制读取 | 普通的那种立即拿到现有结果；“过期的不行”的那种在结果未过期时也立即返回（实测），过期时等这次强制读取（推断，代码） |
  | 在途的非强制读取失败 | 不妨碍随后的强制读取；强制读取自己也失败时，调用方拿到的是它的错误，之后一分钟内的非强制调用直接报这个错，一分钟后的那一次要等 |
  | 进程的第一次读取（非强制）在途，来了强制读取 | 跟在后面再读一次（0.11.1 这时是共用） |
  | 未处理的 rejection | 0 个 |

  **清理与 `this.forced` 的时序（推断，代码）：** 跟随的那一步挂在 `this.loading` 上，它就是带清理的那个 promise，所以轮到跟随时 `this.loading` 已经清空；`this.forced` 只在有读取在途时才被读，每次发起读取时重写，读取结束后留着旧值不影响判断。
- **会不会让“核对连接”多等很久：不会比 0.11.1 多（实测，替身）。** 目录过期时是两次读取的时长，与 0.11.1 相同（0.11.1 是前一步等一次、强制再读一次；现在是强制读取等后面那一次、再读一次）。目录没有过期时是一次。一种更慢的情形是推断：Codex 完全不响应时，现在要等两个 45 秒超时才报错，0.11.1 在第一个超时后就失败了。
- **`stale: false` 的路径是否就是改动前的行为：是。** 逐行对照 0.11.1 的 `list()`：结果未过期直接返回、失败后一分钟内直接抛错、有读取在途则共用、否则发起一次并等它，四步相同（推断，代码）；探针里它与 0.11.1 的模块发出同样的读取、得到同样的结果、用时相同（实测）。
- **那一处读回之外有没有同样应该要新鲜结果的地方：没有发现。** 向用户说“是否已连接”的只有两处：安装官方目录插件之后的读回（这次改了），和“核对连接状态”（先强制刷新，之后那次读取拿到的就是刚读回来的）。其余几处读回（更新、卸载、启停、市场来源的增删与刷新）核对的是命令行清单里的安装与启用状态，不涉及官方目录的连接状态（推断，代码）。快照与安装预览按设计可以用过期的结果；预览另读应用详情。
- **放宽那条旧用例的时限是否掩盖了什么：没有。** 改的 15 秒是传给读取函数的超时上限，不是对耗时的断言；这一步验证的是“能初始化、能读到清单”，实现若卡住，仍会在 15 秒后失败。它要测的“不响应的宿主有界”在下一行（200 毫秒），没有动；那一行在替身进程启动慢时同样以同一个错误码结束，不受机器忙闲影响（推断，代码）。本机连跑 3 次，这条用例所在的运行各约 0.37 秒（实测）。
