## 4. 发现

### PH5C-P1-01 关闭状态下保存新增的跨侧技能被记为“1 版来源”：从不要求确认，启用后后台自动应用改写另一侧插件

- **位置**：
  - `server/service.mjs:2087`：关闭计划（`enabled: false`）的请求先把带 `targets` 的 `disabled.json` 写入；
  - `server/service.mjs:190`：随后 `withOperation` 在执行请求前 `scheduler.reload({ recover: true })`，`reload` 把 `disabled.json` 并入 `state.schedule`（`scheduler.mjs:55`）；
  - `server/scheduler.mjs:114`：`configureTransaction` 此时取到的 `prior` 已含本次请求的目标；
  - `server/scheduler.mjs:132-134`：新增的目标因此被判为“原样重新提交”，没有记录时默认 `{ origin: 'v1' }`；
  - `server/scheduler.mjs:138`：`counted` 只算 `origin === 'v2'`，于是不要求确认，也不记为待确认；
  - `server/service.mjs:2089`：有操作在进行时，关闭请求在 `configure` 之前就返回，目标同样经 `disabled.json` 进入计划且没有记录（同一根因，未单独实验）。
- **问题**：36c 第 6 节第 1 条要求“另一侧已启用管理时，2 版 `schedule.configure` 新增这类目标……须带 `confirm: true`”，与计划是否启用无关；这一侧没有被问到，之后它被当作 1 版目标，按 0.10.2 行为照常自动应用，确认机制对它完全失效。
- **失败场景**（E1）：Claude 已启用管理；Codex 独立技能 `inner` 的内容位于 Claude 技能目录插件 `sd` 中，已关联来源。
  1. 2 版保存关闭的计划（`enabled: false`、`autoApply: true`、目标 `[inner]`）、不带 `confirm`：**成功**，没有 `CONFIRMATION_REQUIRED`；
  2. 多 Agent 快照中该目标**没有** `confirmation` 字段，更新页不显示待确认提示；
  3. 2 版启用计划（同样目标、自动应用）、不带 `confirm`：**成功**（“启用自动应用的已停用计划”本应要求确认）；
  4. 来源出新版后到期运行：该项 `updated`，`sd/skills/inner/SKILL.md` 被改写。
  调试插桩确认第 1 步时 `priorKeys` 已含该目标，`meta` 为 `{ origin: 'v1' }`。现有用例只在启用状态下新增目标，所以没有发现。
- **影响**：界面的计划对话框在计划关闭时保存就是这条路径；“先选目标、稍后启用”是自然的操作顺序。结果是 MR-SDX-001/AC-003 要守住的“未经确认的后台改写另一侧插件”在常见流程中发生。内容可从操作记录恢复，但用户不会被告知。
- **建议修法**（取舍按复杂度排序）：
  1. **最小修法（建议必做）**：关闭请求写 `disabled.json` 时记下请求版本（如 `origin: 'v2'`），调度器在三处并入 `disabled.json`（`persist`、`reload`、`run` 中各一处：`scheduler.mjs:42`、`:55`、`:238-239`）时，为还没有记录的目标补上该来源。这样经关闭记录进入计划的 2 版目标是“待确认”，启用自动应用时按 `starts` 要求确认，后台在确认前只检查。约 6 行，不改变“关闭立即生效”的顺序。已在副本中试过：E1 变为第 2 步显示 `pending`、第 3 步 `CONFIRMATION_REQUIRED`、运行不改写插件（第 6.4 节）。
  2. **贴合条文（可选）**：`dispatchRequest` 在写 `disabled.json` 之前取当前计划的目标与记录，传给 `configure` 作为 `prior`，使关闭状态下新增的这类目标当场返回 `CONFIRMATION_REQUIRED`。代价是多一个参数穿过 `executeRequest`；即使被拒，关闭仍已生效（记录已写），配合第 1 条不会留下未标记的目标。
  3. 不建议把“先检查确认、再写 `disabled.json`”作为修法：那会让“关闭计划”可能被确认拦住，削弱关闭的可靠性。
  4. 补用例：关闭状态下新增跨侧技能 → 显示待确认（或要求确认）；启用自动应用 → 要求确认；确认前到期运行只检查。

### PH5C-P2-01 “原样重新提交”按绑定身份判定，比 36c 宽：1 版原样保存把待确认目标变成自动应用，2 版原样保存丢掉已有确认

- **位置**：`server/scheduler.mjs:29`（`sameIdentity`：绑定去掉内容指纹后整体比较）、`:132`（`resubmitted`）、`:134`；绑定字段见 `server/service.mjs:1752-1770`（`real`、`dev`、`ino`、`generation`、`sourceIdentity` 含 `commit`）。
- **问题**：36c `UpdateTarget.confirmation` 一行写明“‘原样提交’的比较只看目标身份（`kind`、`id`、`agent` 与安装身份）”；第 6 节还写明“原本经 2 版保存、未确认的目标被 1 版原样保存后仍是未确认，不会因此变成自动应用”。实现把绑定中的目录 inode、来源记录代号、来源提交也算进去：这些在重新关联来源、目录被替换（例如所在插件被更新）后都会变，而目标身份不变。
- **失败场景**：
  - E2：Claude 只读时 2 版保存自动应用计划（目标 `inner`），随后启用 Claude 管理 → `pending`。用户在同一侧重新关联同一来源（代号改变）。0.10.x 界面（1 版）原样保存计划 → 该目标的记录变为 `origin: 'v1'`、不再显示待确认；到期运行 `updated`，`sd` 插件被改写。
  - E2b：已确认的目标，在重新关联来源后用 2 版原样保存（只改间隔）→ `CONFIRMATION_REQUIRED`，已有确认丢失；不重新关联时同样的保存不问。
- **取舍分析**：绑定变化时，运行本来就以 `TARGET_BINDING_CHANGED` 拒绝该目标，直到重新保存——这是 0.10.2 的“不接管新对象”。确认要回答的是“这个技能的内容在另一侧插件里”，每次由 `crossSide` 重新判断，与绑定无关。所以只按目标身份判定不会扩大自动应用的范围，反而去掉一个绕过和一次多余的确认。
- **建议修法**：`resubmitted = key => priorKeys.has(key)`（1 行；同时可删去 `sameIdentity`）。已在副本中试过：E2 变为保存后仍 `pending`、运行只检查；E2b 不再要求确认；相关 61 项用例通过。若坚持现行为，则须改 36c 的定义，并接受“1 版原样保存可让待确认目标变为自动应用”——不建议。补用例：重新关联来源后 1 版、2 版原样保存，确认状态不变。

### PH5C-P3-01 生成 marketplace 的副本替换：还原失败时被吞掉，备份随暂存区删除；替换用复制而非原子移动

- **位置**：`server/service.mjs:818`（`undoDirect`）、`:819-820`、`:825`（`.catch(() => {})`）、`:850`（`finally` 删除暂存区）。
- **问题与场景**（E8）：`plugin update` 失败后执行还原，若把 `staging/previous` 移回副本位置失败（注入 `EIO`）：错误被吞掉，结果只报“Claude 命令行 plugin update 失败”；副本目录已被删除，`marketplace.json` 停留在新版本条目；`finally` 随即删除暂存区，**备份一并消失**。此后 marketplace 的插件目录不存在，每次应用都会在 `move(destination, previous)` 处失败，只能卸载重装。复制阶段失败时（`:820`）还原失败会抛出还原的错误、掩盖原错误，同样删除备份。另外 `copySkill` 直接写到副本位置，复制过程中 Claude 若读取这个 marketplace 会看到不完整的目录；`refreshDirectSource`（Codex 一侧）用的是同一文件系统内的 `move`。
- **严重度说明**：同一文件系统内两次 rename 中第二次失败的概率很低，副本可以从来源重建，Claude 已安装的插件不受影响，列 P3。
- **建议**：还原失败时保留暂存区（`keep = true`），结果追加“自动恢复未完成，备份在……”（`claudePluginSourceAction` 已有类似措辞“自动恢复未完成……请保留备份区”，需补英、日译文）；把 `copySkill(preview.candidate, destination)` 改为 `move`（候选在应用后不再需要），缩短不完整窗口。约 5 行。

### PH5C-P3-02 Git 来源的应用前核对取 `ls-remote` 的第一行：附注标签与同名后缀分支下提交永远对不上

- **位置**：`server/service.mjs:797`（生成 marketplace 的 Git 来源用 `claudeFetchers.resolve`）；`server/claude-plugin-updates.mjs:77-82`（`resolve` 取 `git ls-remote -- url <ref>` 输出的第一行）；检查时的提交来自 `checkoutGit`（`server/cli.mjs:65`，`rev-parse <ref>^{commit}`）。
- **问题与场景**（E11，本地仓库、不联网）：
  - ref 为附注标签 `v1.0`：检出提交 `c59ef4108f4c`，`ls-remote` 第一行是标签对象 `0244811302f2`，不同；
  - ref 为 `main` 而仓库另有分支 `feature/main`：`ls-remote` 按尾部匹配，第一行是 `refs/heads/feature/main` 的提交，不同；
  - 不写 ref：一致。
  不一致时每次应用都返回“来源在预览后发生变化，请重新检查”，重新检查后仍然如此，更新永远无法应用。GitHub 目录链接 `tree/main/...` 会把 ref 记为 `main`，仓库中有任何以 `/main` 结尾的分支即触发。
- **说明**：`resolve` 是阶段 5b 的辅助函数，5b 的 Git 来源同样使用（不在本轮范围）；5c1 新增了一处调用。
- **建议**：按完整引用名精确匹配：先找 `refs/heads/<ref>`，再找 `refs/tags/<ref>^{}`（取剥离后的提交）、`refs/tags/<ref>`，40 位十六进制直接返回；或把 `ls-remote` 的参数改为 `refs/heads/<ref> refs/tags/<ref> refs/tags/<ref>^{}` 后按名称挑选。改动集中在一个函数，5b 一并受益。补用例：附注标签与后缀分支。

### PH5C-P3-06 文案与文档小处

1. **`nativeRules` 条目的中文标点**：计划的确认条目为 `${技能}（${插件.join('、')}）`（`scheduler.mjs:143`），英文、日文界面中也显示全角括号与顿号。建议条目只放插件名（与单次操作一致），或在服务端按语言无关的形式拼接（如 `inner (sd)`），技能名放进 `message`；UI-12 已计划在重新设计时列出插件，可一并处理。

## 7. 未覆盖的范围与剩余风险

- **未用真实 Claude 命令行**：生成 marketplace 的更新只在替身中验证（替身按“版本变化才更新、无版本时原地覆盖”模拟）。真实 `plugin marketplace update` 对目录型 marketplace 是否重读条目、`plugin update` 对无版本插件是否覆盖，依赖 HLD 9.3 的实测结论；建议在 UAT 或冒烟中补一次生成 marketplace 的真实更新。
- **读回失败后的副本与登记**（E9）：副本与条目已是新内容，登记的指纹仍是旧的，自动应用暂停直到手动应用。若之后卸载时因其他项目仍有安装而保留 marketplace，再从同一来源安装会因“目录内容与登记不符”被 `TARGET_EXISTS` 挡住。HLD 未规定读回失败时副本的处理，影响小，未列为发现。
- **并发**：应用在 Claude 锁与实例锁下进行，生成 marketplace 的写入方（安装、卸载、清理、更新）都经同一把 Claude 锁（E7 断言调用时持锁）。Claude 自身的进程不受这把锁约束，复制窗口见 P3-01。后台工作进程在运行中持有自己的计划状态，与前台保存的竞争是 0.10.x 以来的既有设计，本轮未展开。
- **有操作进行时的关闭请求**（`service.mjs:2089`）：与 P1-01 同一根因，按代码推断，未单独构造实验。
- **1 版界面**：只按服务端行为核对（1 版快照、1 版保存与返回、1 版批量），没有运行 0.10.x 冻结界面。
- **原生界面**：`native/ui.html` 只核对了 `build.json` 的输入哈希（`native-protocol` 用例），没有在原生宿主中查看待确认提示。
