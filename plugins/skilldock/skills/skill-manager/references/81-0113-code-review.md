## 2 六项改动逐项判定

### 2.1 服务关闭设期限 —— 实现正确

`assets/app/server/index.mjs:17`、`:59-61`、`:119-125`。

- **真实入口（实测，隔离目录）**：有一个请求在途时让 0.11.3 的入口停止，不到 0.2 秒退出，退出码 0，新连接被拒绝。把同一个探针对着 0.11.2 的入口（仓库历史里的那一版，放在副本里）：7 秒后仍在运行，那条连接上的请求一直有答复——事故的机制重现了。
- **还会无限等待的路径**：只有写操作收尾之前的那几步（`updater.close()`、`service.close()`），这是有意的；这期间监听开着，健康检查照常应答。写操作收尾之后有上限：宽限 2 秒，到点切断所有连接（变异 X1、X2、X5 被杀）。
- **切断在途读取的副作用**：没有发现。被切断的是读取；处理函数继续跑完，往已断开的连接写不会抛错；随后进程退出，读取起的命令行子进程随之结束（推断，代码）。
- **`answering` 集合**：响应关闭时移除，大小不超过同时在途的请求数。
- **`process.exit(0)` 是否总能到达**：写操作收尾后总能到达；`close()` 抛错时进程以未处理的 rejection 退出（退出码 1），也结束了（推断）。
- **两点不计入意见的观察**：
  1. 入口用的是 `process.once`：第二个停止信号按系统默认处理，进程立刻结束，不等写操作（实测：0.11.2 的入口副本，第二个 SIGTERM 到达即以信号结束；0.11.3 这一行没有变）。所以“仍在应答就留给它收尾”只保得住第一次：没有持锁的 `stop` 再来一次，它就在写的中途结束了。这是 0.11.0 起就有的行为。
  2. `agent.`、`settings.` 开头的操作不看服务的关闭标记（`service.mjs:2302`）。关闭开始之后若有这样一个请求从还没断开的连接进来，它会开始执行，而进程在 2 秒内退出（推断）。原来进程会等这条连接。窗口很窄。

### 2.2 启动器的 `stop()` —— 认定“是哪个进程”可靠；认定“它已经不在写”不可靠

`scripts/launch.mjs:68-125`。

**（一）作者的依据是否成立：成立。** 三个已发布版本的 `close()` 都是 `await updater.close(); await service.close()` 之后才 `server.close()`（实测：逐版本读了 `838b619`、`820d718`、`797397e`）。`service.close()` 等的是计划批次和在途操作；所有写操作都经 `withOperation` 登记，关闭开始后新的写操作被拒绝（例外见 2.1 观察 2）。计划批次在服务进程里跑时也在其中；后台工作进程与执行重启任务的启动器是另外的进程，启动器只对记录里的那个 pid 动手，不会碰它们。

**（二）问题在于“不再应答”是怎么判断的** → C15-P2-01。

**（三）会不会结束别的进程：没有发现。**

| 担心的情形 | 判定 | 依据 |
|---|---|---|
| pid 被别的进程占用 | 需要那个进程的命令行也以同一个运行目录的 `server/index.mjs` 结尾。运行目录在数据目录之下、按来源摘要命名，所以只能是同一份数据、同一版本的另一个服务进程 | 推断（代码：`runtime.mjs:30`） |
| 记录里的 pid 是 0、负数、不存在的大数 | 读进程表返回空，不结束任何进程 | 实测 |
| 命令行被截断 | `ps -ww` 给出完整命令行，长路径完整 | 实测 |
| 路径含空格 | 能认出 | 实测（真实 `ps`，夹具路径含空格） |
| 路径含非 ASCII 字符 | UTF-8 区域设置下能认出；没有 `LANG` 时认不出，退回拒绝 | 实测 → C15-P3-02 |
| `record.runtime` 被改写或指向别处 | 要能写数据目录，也就是同一个用户；不构成越权。指向别处时，那个 pid 的命令行得正好以那个路径结尾 | 推断 |
| 符号链接 | 记录里存的与启动时用的是同一个规范路径，按文字比较成立 | 推断 |
| `endsWith` 够不够严 | 不核对可执行文件是不是 Node，也不要求只有这一个参数；配合“pid 正是记录的 pid”已经足够。去掉前面的空格（变异 L13）用例不失败，实际上分不出差别 | 实测（变异）、推断 |
| 读不到进程表（沙箱、Windows、`ps` 超时或不存在） | 拒绝，与 0.11.2 相同 | 实测（沙箱内探针 3） |

**（五）四个动作**

| 动作 | 会不会走到强制结束 | 持锁吗 |
|---|---|---|

## 4 新发现

### C15-P2-01 “不再应答”是用一次 1.5 秒的健康检查判断的：答得慢的服务会被强制结束，哪怕正在写（发布前应处理）

- **位置**：`scripts/launch.mjs:34-39`（`probe`）、`:104-108`、`:114-121`。
- **原因**：`probe` 对连接被拒绝、超过 1.5 秒没答完、答的不是 200 或不是 JSON，都返回空。两条新路都把空当作“监听已关，写操作已收尾”：
  - 无人应答那一条：发停止信号，3 秒后强制结束，中间不再问一次，也不看它是不是还在写。
  - 核实过那一条：等满 10 秒后只问一次，这一次没有及时答复就强制结束。
- **现象（实测，替身；沙箱内，进程表的读取用注入的函数）**：

  | 情形 | 0.11.3 的结果 |
  |---|---|
  | 服务正常，只是每次答复要 2.5 秒；让它停时它有一个 6 秒的写操作。执行 `stop` | 4.6 秒后报“此实例已停止”；进程被强制结束，写操作没有完成 |
  | 同上，从另一个会话执行 `start` | 旧服务被强制结束，写操作没有完成；新服务起来 |
  | 核实过、让它停、它有 5 秒的写操作，此后答复变慢（等待设为 1 秒） | 2.7 秒后报已停止；进程被强制结束，写操作没有完成 |
  | 对照：同上但答复及时 | 报“服务尚未停止”，不强制；写操作完成后自己退出 |
  | 对照：第一种情形，读不到进程表 | 拒绝，与 0.11.2 相同 |

- **0.11.2 在这些情形下**：前两种拒绝（“无法核实”），第三种报“服务尚未停止”，都不结束进程（推断，代码）。
- **什么时候服务会答得慢**：健康检查要读两三个小文件，走的是 Node 的线程池；线程池被占满、磁盘卡顿、机器过载时，答复会超过 1.5 秒（推断）。同样的时刻，写操作也正卡在途中。没有在真实服务上造出这种局面（未做）。
- **哪里不受影响**：替换一个在应答的服务时启动器已经拿到两把锁，服务不在写（2.2（五））；在执行不了 `ps` 的沙箱里，无人应答那一条不会动手。
- **影响**：被强制结束的写操作等同于中途崩溃——它的撤销步骤不会执行。例如更新一个技能时，旧目录已移入可恢复区而新目录还没有就位，操作记录也还没有写。
- **为什么归为发布前应处理**：这一版的要点就是启动器开始强制结束进程；作者定的界线是“仍在应答的留给它收尾”，而实现在服务答得慢时越过了这条界线。能把两者分开的信息是现成的：连接被拒绝与超时是两种结果；服务在写的时候持有带它自己 pid 的锁文件。
- **测试**：没有用例覆盖“答得慢而不是不答”。

### C15-P3-01 服务恰好在最后一次检查期间自己退出时，`stop` 以“kill ESRCH”失败（可留到下一版）

- **位置**：`scripts/launch.mjs:120`（`:105`、`:106` 的两处 `process.kill` 同理，窗口更小）。
- **现象（实测，替身）**：等待结束时进程还在，启动器再问一次健康检查，这期间进程退出了；随后的强制结束抛出 `ESRCH`，`stop` 以这个原始错误失败，记录仍是“运行中”。下一次 `stop` 发现进程已不在，正常收尾。
- **影响**：服务其实已经停了，这一次却报失败。发生在重启任务里时，任务记为失败、没有新服务起来，要等下一次打开。对真实服务窗口只有几毫秒（监听已关时检查立刻返回）。

### C15-P3-02 数据目录路径含非 ASCII 字符、启动器又没有 UTF-8 区域设置时，认不出记录的服务（可留到下一版）

- **现象（实测，真实 `ps`，沙箱外）**：同一个替身、同一条路径（含中文）：`LANG=en_US.UTF-8` 时认出并结束；没有 `LANG` 时 `ps` 把非 ASCII 字节转义输出，比对不上，拒绝。路径只含 ASCII（可以有空格）时有没有 `LANG` 都认得出。
- **影响**：退回 0.11.2 的拒绝，不会误结束。从图形界面启动的 Agent 环境里通常没有 `LANG`。默认数据目录在主目录下，主目录含非 ASCII 字符的用户才会遇到。

### C15-P3-03 新用例每跑一次留下一个替身服务进程（可留到下一版）

- **现象（实测）**：单独跑 `tests/launcher.test.mjs` 里“a start finds the record's service alive and answering nobody…”这一条，通过之后进程表里多出一个 `…/server/index.mjs` 的替身进程，一直监听、不会自己退出。全量单元测试每跑一次留一个。
- **原因（推断）**：这条用例最后用 `launch('stop')` 收尾，而夹具删除临时目录的钩子登记在它之前，轮到它时记录已经没有了。

### C15-P3-04 新代码上没有断言的几处（可留到下一版）

实现都是对的，只是改错了也不会有用例失败：

| 变异 | 没有被钉住的 |
|---|---|
| L3、L7 | **0.10.x 的记录不走两条新路**。整份启动器用例（32 条）与兼容矩阵（103 条）都通过 |
| L12 | 读进程表用的参数：没有任何用例在 `ps` 能执行的地方跑过这一段 |
| L10 | 无人应答那一条先发停止信号、再强制 |
| L3b、L14 | 强制结束之后确认进程确实不在了 |
| L9 | 目标不在运行的失败任务原样保留（改成一律重写，原来的失败原因被换掉，用例通过） |
