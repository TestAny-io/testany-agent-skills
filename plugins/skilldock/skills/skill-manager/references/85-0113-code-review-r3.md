## 2 新功能四项的逐项判定

### 2.1 `server/app-directory.mjs`

**判定：正确。**

**目录表改成只留用到的字段。** 用到这张表的只有一处：`server/cli.mjs` 的 `list()`（165～174 行），它读的 11 个字段——标识、名称、介绍、插件显示名、安装入口、是否已连接、两个浅色图标地址与标志地址、深色图标地址与标志地址——`kept()` 全部保留（代码阅读）。`refreshDirectory()` 唯一的调用处（`service.mjs:1493`）不用它的返回值；`remoteDetails()` 走的是 `app/read`，拿的是 Codex 的原样结果，不经过这张表。顺带的两处变化都是变宽容：Codex 返回的条目里若有 `null`，以前会让整次读取失败，现在跳过；图标地址、介绍不是字符串时以前原样放进去，现在按没有处理。

### 2.3 `server/service.mjs`

**判定：正确，不违反 36a 第 8 节。**

- **路径与“能不能写”**：服务把 `<数据目录>/cache/app-directory.json` 交给适配器（154～155 行）；“能不能写”与服务其他写入用的是同一条规则（`ensureGeneration()`：盘上的世代高于启动时读到的就不写）。标记文件读不懂时按更高处理，不写。不传、换路径、不传配置根、恒可写、只看启动时的世代、把 `<=` 写成 `<`，六个变异都被杀（F41～F46，实测）。
- **创建适配器的地方**：全仓只有两处——服务（传）与后台任务 `server/background-worker.mjs:157`（不传）。后台任务每次自己读，与设计一致。用例里的适配器都是注入的目录，不涉及。
- **世代 1 的数据目录上也会写这个文件**（探针 S-d，实测；作者那条用例的数据目录也是世代 1）。36a 第 8 节末句允许门槛通过前写“0.10.x 不读取的位置”。在 0.10.2 与 0.10.3 的冻结提交里查过：服务端与启动器都没有读、列举或清理 `<数据目录>/cache/` 的代码，出现的 `cache` 都是 Codex 与 Claude 的插件缓存路径（只读的 git 查询，实测）。运行途中数据被迁到世代 2 时，这个世代 1 的服务不再写（S-d，实测）。
- **世代 2 的数据目录**——迁移过的机器实际的样子，作者的用例没有覆盖到——也照常写，`cache/` 是 `700`、文件是 `600`（S-a，实测）。标记文件在读取途中变得读不懂：不写（S-c，实测）。
- 这次写入不经过服务的操作锁，也不核对数据目录的边界，与数据目录下其他直接写的文件（世代标记、启动记录、Claude 根记录）是同一做法（代码阅读）。

### 2.5 观察（不要求改）

1. **存档按 Codex 配置根区分，不按账号。** 换了账号或工作区之后重启，第一次清单里的“已连接”标记可能是上一个账号的，直到后面那次读取完成；存档不满 10 分钟时则到期才重读。与本次运行内换账号的情形同类，只是现在能跨过重启（推断）。
2. **写到一半进程被结束会留下临时文件，没有人清。** 探针里用约 7 MiB 的内容连续写、随机结束，8 次留下 3 个，共约 10.5 MiB（B2，实测）——这是有意造出来的极端情形；真实的写入是每 10 分钟至多一次的小文件。全仓其他用 `writeAtomic` 的地方也都不清，属于同一做法。
3. **服务的 `close()` 不等后面那次读取。** 在同一个进程里（用例的用法），关闭之后那次读取完成时仍会写文件（S-b，实测）。正式入口在关闭之后立刻 `process.exit(0)`（`server/index.mjs:132`），不会有这次写入。作者的用例在结束前都等到了读取完成；基线跑完后临时目录里没有留下东西（实测）。
4. **`cache` 若是指向别处的链接，会跟过去写**（A12，实测）；读取只对文件本身用 `lstat`。只有本用户自己能做到。
5. **“只取一次”与“强制读取不取存档”没有被用例区分**（变异 F10、F11 存活）。差别只是多读几次文件，结果相同，不必补。

## 4 新发现

### C17-P3-01 新功能里三处判断没有用例钉住（可留到下一版）

三处的代码都是对的（探针实测），只是去掉之后整份 `tests/remote-directory.test.mjs` 仍然 14/14 通过。

| 变异 | 去掉的是什么 | 去掉之后会怎样 |
|---|---|---|
| F03 | `restore()` 读完文件之后，再看一次这次运行是不是已经读到了结果 | 探针实测：一次强制读取完成之后才读完的存档，会把刚读到的结果换掉，并在它自己的 10 分钟内一直用（刚按“刷新连接状态”读到的，被 5 分钟前的存档盖住）。顺序发生时有前一道判断挡着，只有读文件与一次读取的完成交叠时才会走到，所以是 P3 |
| F24 | 存档里的读取时刻必须是有限数 | 探针实测：时刻写成字符串的存档会被采用，过期时刻变成字符串拼接，这次运行里永不过期（把时钟拨到一个月后仍不向 Codex 读） |
| F31 | 写入之前的 8 MiB 上限 | 超过上限的文件会写下去，下一次因读取端的上限而不采用。后果只是白写 |

建议各补一条断言：前两条在单元那条用例里就能加（一个读得慢的存取替身加一次强制读取；`notTaken` 里加一个时刻是字符串的文件），第三条写一个超过上限的目录后确认文件没有变。

### C17-P3-02 启动器用例里“应当被拒绝的启动”一旦没有被拒绝，会留下一个服务进程（可留到下一版）

`tests/launcher.test.mjs` 里“记录里的服务活着而不应答”那条用例，用 `assert.rejects(launch('start', …))` 断言启动被拒绝。启动器要是错误地继续了，会真的起一个新服务；这个服务没有登记清理，夹具的收尾也只删目录。变异 N2、N3 各留下 1 个不会自己退出的替身服务（实测，已由我按路径结束）。这一轮新加的那条断言是同一写法，前面循环里的几条也是。

只在启动器出了回归时才会发生，但发生的地方正是 CI。建议在这条用例的收尾里读一次启动记录、结束记录里的进程，或者让夹具统一做。
