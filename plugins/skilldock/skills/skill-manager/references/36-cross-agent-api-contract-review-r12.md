## 2. 结论

- **结论：APPROVED（通过）**。P0 0 项，P1 0 项；P2 2 项，均为本轮新发现，不阻断。
- **第 11 轮问题全部关闭**：APIR11-P2-01～03 都按推荐做法落实（第 4.1 节）。其中 P2-01 新增的 `confirmation` 字段带出一处新的精度问题（APIR12-P2-01）。
- **第 11 轮范围外观察 1（归属判定的死路）**：**已在更新路径上关闭**。实现 `66767a9`、HLD v1.12 3.7 与 36b 6.3 的新括号一致；对照实验中，修正前 `start` 退出 4、`stop` 与 `status` 退出 1，修正后：
  - Claude 侧旧目录带废弃标记、旧实例存活：`status` 报运行中，`start` 先在锁内停止旧实例再迁移（实验 E1）；锁被占用时在停止之前失败、文件不变（E1b）；
  - 旧目录已移走、记录中的进程已不在：`start` 清理记录后迁移（E2）；
  - `stop` 停止存活的旧实例并清理 0.10.x 记录，之后 `start` 迁移（E3）；
  - 仍在使用、低于 0.10.3：`start`、`restart` 退出 4，`status`、`stop` 退出 1，0.10.x 读取的文件逐字节不变（E4）。

  残余：Claude 中已移除该 marketplace、Claude 配置整体删除，或从 Codex 侧看不到自定义 Claude 配置目录时，来源标识无法核实，记录按归属规则拒绝（退出 1），提示不可执行（实验 E6、U10、U13b）。这属设计层的提示问题，不涉及契约，记在 HLD 第 20 轮 R20-P2-02，本报告不另计。
- **36b 6.3 新括号（按 1a 复核）**：退出码 4 的归属来源收窄为“仍在用、未带废弃标记、低于 0.10.3”，只在 `start`、`restart`；冻结调用方只区分 0 与非 0。**不要求改变 0.10.3 或 0.10.2 的行为**（第 5.1 节）。
- **1a**：v0.12 没有改动任何 1a 条文（第 5.5 节）。**条件 1a：满足（维持）。条件 1b：满足**（以本报告绑定的 v0.12 为准）。
- **证书**：重新绑定到 v0.12 的四个 sha256（第 8 节）。
- **需要 Owner 决定的事项：没有。** 两项 P2 的推荐处理都在已批准边界内。

**APIR12-P2-01 `confirmation` 的请求方向与取值范围（建议在实现阶段 5 的后台计划之前处理）**

- 有效依据：

  - 第 202～203 行：经 1 版保存、从 0.10.x 继承的目标与另一侧未启用管理时的全部目标照常检查与应用，不需要确认。
- 当前问题：
  - (a) **请求方向**。`UpdateTarget` 也是 `schedule.configure` 请求中 `targets` 的类型。2 版界面把快照中的目标原样回传时会带上 `confirmation`；条文没有写服务端忽略请求中的这个字段，也没有写“原样”的比较不含它。若实现采信请求中的 `"confirmed"`，就绕过了确认框（AC-016、MR-SDX-001 所守的边界）。
  - (b) **照常应用的这类目标**。它们不需要确认，给 `"pending"` 会让界面列为待确认，给 `"confirmed"` 又不是事实；条文的“只对这类技能给出：待确认或已确认”没有区分。
  - (c) `UpdateRun.items[].target`、进度 `current.target` 也是 `UpdateTarget`，是否出现该字段未写（影响小）。
- 影响：阶段 5 实现与界面对“哪些目标待确认”的理解可能不同；(a) 若实现不当，会让确认可被请求自行声明。
- 建议：
  - 写明 `confirmation` 只出现在快照的计划目标中，服务端忽略请求中的该字段，“原样提交”的比较只看目标身份（`kind`、`id`、`agent` 与安装身份）；
  - 写明只对“另一侧已启用管理时须确认”的目标给出该字段，照常应用的目标省略；
  - G-15 补断言：请求中带 `confirmation: "confirmed"` 而不带 `confirm` 时，目标仍为待确认。
- 是否需要 Owner 决定：不需要。只是给 v0.12 新字段补上方向与取值范围。
