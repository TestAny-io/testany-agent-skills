## 3 新发现

### IF4-P3-01 根目录自带 manifest 的插件，条目列的是 `./` 或 `./skills` 时多列（可留到下一版）

- **位置**：`server/claude-catalog.mjs:155-164`。
- **现象（实测）**：来源为 marketplace 根目录、根目录的 `.claude-plugin/plugin.json` 声明了 `skills: "./more"`，条目的 `skills` 如下时：

  | 条目所列 | Claude（`plugin details`） | SkillDock | |
  |---|---|---|---|
  | `["./skills/"]` | `x y z` | `m1 m2 x y z` | 多列 |
  | `["./skills"]` | `x y z` | `m1 m2 x y z` | 多列 |
  | `["./"]` | `root-skill x y z` | `m1 m2 root-skill x y z` | 多列 |
  | `["./skills/", "./extra"]` | `e1 x y z` | `e1 m1 m2 x y z` | 多列 |
  | `["./extra"]` | `e1` | `e1` | 一致 |
  | `["./skills/absent"]`（不存在） | `m1 m2 x y z` | `m1 m2 x y z` | 一致 |
  | `["./skills/x/SKILL.md"]`（文件） | `m1 m2 x y z` | `m1 m2 x y z` | 一致 |
  | 不列 | `m1 m2 x y z` | `m1 m2 x y z` | 一致 |

- **归纳（推断）**：根目录来源的条目只要列出了至少一个实际存在的目录——`./` 和 `./skills` 也算——Claude 就不再看根目录 manifest 的 `skills`。实现只在“只算所列的”那一支里丢掉 manifest 的路径；列的是 `./` 或 `./skills` 时走的是另一支，manifest 的路径还在。
- **影响**：多列出几个 Claude 并不加载的技能，显示为可用的只读条目。要三个条件同时成立（根目录来源、根目录自带声明了技能路径的 manifest、条目列的是根目录或默认目录），少见。
- **来历**：不是这次提交带来的，`3825165` 已是如此；上一轮没有对照到这种组合。把 `./skills` 从“等同默认”的名单里去掉，单元用例照样全过（变异 M3b 存活），说明这条名单的取舍目前没有被钉住。

### IF4-P3-02 直接声明的技能，说明头不规范时名称与 Claude 不同（可留到下一版）

- **位置**：`server/claude-catalog.mjs:210`；`server/files.mjs:53-61`（YAML 解析不了时没有 `name` 可用，退回目录名）。
- **现象（实测）**，都只发生在“声明的路径本身就是技能”的情形：

  | 说明头 | Claude | SkillDock |
  |---|---|---|
  | `name: [unclosed`（YAML 解析不了） | `[unclosed` | 目录名 |
  | 两个 `name` 键 | 后一个的值 | 目录名 |
  | `name` 长 230 个字符 | 全长 | 截到 200 |

- **一致的（实测）**：`name` 是数字、布尔值或只有空白时两边都用目录名；中文、带空格、含 `/`、含 `:`、CRLF 换行、`---` 前有空行、用制表符缩进的，两边一致。技能目录下的子目录不受影响，说明头再怪也是目录名（两边一致）。
- **影响**：只是名称不同，条目照样列出、能读详情。这是本次新增规则的边角；改之前这几种同样对不上。
- **附**：`name` 里的换行和控制字符会原样进入快照。实测（探针，服务层）：这样的条目都能列出、读详情、拒绝开关，标识不受名称影响（4.4）。界面上的显示未做。

### IF4-P3-03 Claude 报告加载失败的插件，仍按“已启用”列出它和它的技能（可留到下一版）

- **现象（实测）**：条目写了 `strict: false`、根目录 manifest 又声明了组件时，`claude plugin list --json` 给出 `enabled: true` 和一条 `errors`（manifest 冲突），`claude plugin details` 说找不到这个插件，会话不提供它的任何技能。SkillDock 的目录读取（`claudeCatalog`）给出的是：已安装、已启用、3 个技能，没有原因说明，也没有诊断。
- **原因（实测：检索）**：`server/` 下没有任何地方读取 `plugin list --json` 的 `errors`。
- **来历与影响**：插件条目本身一直如此，不是这次提交带来的；从 0.11.1 起，它的技能也会跟着显示为可用。触发条件是插件作者的配置出错，少见。

### IF4-P3-04 新代码上还有几处没有断言（可留到下一版）

实现都是对的（见各自的实测），只是改错了也不会有用例失败：

- **N8**：没有文件清单的旧记录按原样比对。去掉 `source.files ?` 这个判断后，`tests/backend-lifecycle.test.mjs` 全部通过。
- **N10**：同一个目录既是某个技能目录的子目录、又被直接声明时，先到达的那一次决定名称。这与 Claude 一致（4.3 的 11 种重叠写法），但改成“直接声明的优先”后 `tests/claude-catalog.test.mjs` 全部通过。
- **M3b、M9b、F9b、N12、N13**：上一轮几个变异的近邻，以及两处边界——`./skills` 是否算默认目录；非根目录来源时是否仍采用安装目录里那份条目；安装目录顶层名称以 `.DS_Store` 开头的文件或目录；只有空白的 `name`；根目录来源所列路径是否必须在安装目录之内。

### 不计入意见的观察

1. **Claude 自己的两份清单在重叠时不一致（实测）**。同一个目录先作为子目录、后被直接声明时，`plugin details` 用目录名（`dirname`、`onedir`），会话启动事件用的却是说明头里的名称（`fm-direct`、`fm-subdirect`）。SkillDock 跟的是 `plugin details`，即 HLD 3.2 与 9.3 V23 定的口径。HLD 3.2 说会话提供的是清单中的一部分；在这种写法下，会话给的名称不在清单里。作者的 11 个插件没有这种写法，所以冒烟里“会话提供的都在清单中”成立。
2. **变化列表里多一行（实测）**。来源与安装目录有同字节的 `.DS_Store`、来源又另有改动时，变化列表会写“新增 `.DS_Store`”，尽管本机已有同样的文件。应用更新正常，之后不再提示。
