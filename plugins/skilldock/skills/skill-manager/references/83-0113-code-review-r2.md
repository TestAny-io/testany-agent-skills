### 对协调者几个问题的回答

- **“没有监听”这个判断，还有没有会结束一个正在写的服务的路径：没有发现。**

  | 情形 | `refused` 的回答 | 依据 |
  |---|---|---|
  | 没有人监听 | 是 | 实测 |
  | 监听着，答得慢、不答、答的不是 SkillDock | 否 | 实测（探针与作者的用例） |
  | 服务进程被挂起（SIGSTOP），默认大小的等待队列 | 否（连接照样接得上） | 实测 |
  | 等待队列满了 | 否（macOS 给的是 `ECONNRESET`，不是拒绝） | 实测 |
  | 沙箱不许连 | 否（`EPERM`） | 实测 |
  | 地址不是 IP 字面量、没有端口、IPv6 带方括号 | 否 | 实测 |
  | 连接超时 | 否 | 推断（代码）；本机造不出这种局面 |

  服务监听的只有记录里的那个地址（`127.0.0.1` 加端口，启动器写记录与服务监听用的是同一个值，推断）。“没有监听却还在写”要求监听关闭之后还有写操作开始：关闭之后新操作一律被拒绝（这次补上了 `agent.`、`settings.`）；0.11.2 及更早的服务在监听关闭之后，留着的连接上每个请求都得到 403（上一轮实测），开始不了任何操作。
- **逐字比较会不会让本该认出的认不出：没有发现。** 0.11.0、0.11.1、0.11.2 的启动器都是 `spawn(process.execPath, [入口])`，都把 `process.execPath` 写进 `execution.node`（实测：逐版本读了）。子进程的第一个参数就是传进去的那个字符串，所以两边是同一个值；真实 `ps` 下五种设置都逐字相同（实测）。`execution` 在记录被改写后还在：`refreshRecord`、`stoppedRecord` 都是整条展开，`restoreRecord` 从镜像整条写回（推断，代码）。记录里没有 `execution`、或写的是另一个 Node 时，拒绝，不结束进程（实测）——是保守的一侧。没有做的：没有读真机上的记录来比（规则不允许）。
- **`agent.`、`settings.` 要不要也看 `restarting`：不必为安全而加。** 执行重启的启动器在停服务之前要拿实例锁与 Codex 锁，这类操作运行时正持有它们：启动器等它做完，等不到就以“忙”结束这次任务，服务恢复，之后再试（推断，代码）。加上它只是让这类操作与其他操作在“准备重启”期间表现一致，可以留到以后。

### 不计入意见的观察

1. 收为就绪的失败任务若带着 `restored: true`，这个字段会留在就绪的记录里（推断，代码）。读取方对就绪的任务不看它。
2. `ps` 用的区域设置写的是 `en_US.UTF-8`。macOS 自带；Linux 上没有装这个区域设置时会怎样，未做。
3. 本机若有把回环连接直接拒绝的防火墙规则，`refused` 会把一个在监听的服务看成没有监听（推断）。这样的环境里 0.11.2 也起不了服务。
