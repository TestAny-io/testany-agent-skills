### 对 Owner 指示解读的核对

- **一致性**：第 3 轮给 Owner 的两个选项中，选项 A 保留“来源指向数据目录”，只登记残留；选项 B 让来源取插件缓存路径，换来已加载的 0.10.2 原生进程自动转交。按“用户体验更好”选 B，与最常见的情形一致：Codex 面板开着时本侧被更新。本轮实验 NB 也用正在运行的实例证实了转交和代理。**作者的解读与 PRD 登记一致，没有越权。**
- **取舍写得是否完整、诚实**：3.7 写明了“0.10.2 启动器会删除记录并尝试启动、因新格式计划文件失败”和“跨侧需重启”，这些属实。以下几点没有写，或写得不准确：
  1. 0.11.x 正在运行时，同一安装的 0.10.2 启动器会先**停止它**，然后启动自己。启动失败后，0.10.2 会按自己的回滚逻辑，用 0.10.2 的 Node 与环境重启 0.11.x 的运行目录（K2）；如果 0.10.2 校验不过该运行目录，就不恢复，最终没有服务（K1）。0.10.2 的 `stop` 会直接停止 0.11.x 并删除记录（R4-P2-01）。
  2. 回退路径不再在归属检查处立即拒绝。0.10.2 会先准备自己的运行目录；如果该目录不存在，还会先联网执行 `npm ci` 并构建，之后才失败。
  3. 删除或改写 `launcher.json` 本身就是写入 3.7 所列的“0.10.x 会读取的文件”。因此 8.3、8.4、9.1、6.6 中“不写共享状态”的说法不准确，应改为“不改写计划、绑定、历史等数据”。
  4. Claude 侧同一安装中仍加载 ≤0.10.2 代码的旧会话（包括 Claude 加载的 0.10.2 MCP 进程）无法转交（实验 M）。原因是 0.10.2 只把 Codex 插件缓存认作“插件安装”，所以“同一侧自动转交”只对 Codex 侧成立（DG-R4-01 (a)）。
  5. “跨侧无法转交”被写成不可避免，但实际上可以大幅缩小（实验 L1，R4-P2-02）。
  6. 第 10 节把“启动记录来源取插件缓存路径”写成用户决定的内容。这是作者依据 Owner 指示作出的技术选择，应如实区分（R4-P2-05）。

#### HLDR-SDX-R3-P1-01（剩余项）：一键更新不可执行时没有出路

- **当前设计**：
  - 3.1 第 561 行：Codex 环境以“配置根存在或 Codex CLI 可用”判定为已发现。
  - 3.7 第 671 行：命令行不可用时，用缓存与安装记录兜底判断版本。
  - 3.7 第 674 行与 6.6：门槛失败后的唯一出路是“用户确认后，启动器调用该 Agent 的插件更新”，没有写更新无法执行或失败时怎么办。
- **当前失败**（典型）：用户以前在 Codex 中用过 SkillDock 0.10.2，后来卸载了 Codex 应用，改用 Claude。`~/.codex` 中仍留有 `skilldock/0.10.2` 缓存与配置项，数据目录代号为 1。
  1. Claude 侧 0.11.0 打开时，文件兜底判定“Codex 装有 0.10.2”，门槛失败。
  2. 一键更新需要 Codex 命令行，但已找不到。
  3. 入口没有其他指引，Claude 侧 SkillDock 无法使用。PRD 2.3 的 Claude-only 用户正是这一类。

  另一种较少见的情形：Codex 用户的 Claude 侧装有旧版 SkillDock，而 Codex 入口找不到 Claude 命令行（9.1 已登记其目录结构不是公开契约）。
- **影响**：第 3 轮原失败（“无法确认即阻断”）已消除，但同一类“无路可走”在这条路径上仍然存在。数据不受影响。
- **最小修复（不改变边界）**：
  1. 在 3.7 与 6.6 中写明：一键更新不可执行或失败时，入口说明是哪个 Agent、为什么无法更新，并给出手动处理步骤，例如在该 Agent 中手动更新 SkillDock，或从该 Agent 卸载 SkillDock；宿主已卸载、只剩配置残留时，指出构成“已安装”判定的配置项与缓存目录。同时提供“重新检查”。不提供“确认后跳过”，与现有决定一致。
  2. 9.3 的“实现前补测”加入第 3 轮第 4 项用例：Codex-only 且 Claude 根存在但无法确认；Claude-only 且残留 `~/.codex`，分别覆盖含与不含旧版 SkillDock 的情况。
  - 如果作者希望把“宿主已卸载的残留安装”直接视为不可运行而放行门槛，需要先论证该残留不会再运行（例如 0.10.2 注册的 LaunchAgent 是否仍能启动），再交 Owner 决定。本报告不建议这样做。

#### HLDR-SDX-R4-P1-01：0.10.3 的“记录属于另一 Agent → 提示重载”分支

- **当前设计**（3.7 第 666 行，5.4 与 DEC-SDX-021 同义）：遇到 0.11.x 记录时，按以下顺序判断：
  1. 本安装已有不低于记录版本的较新缓存 → 转交；
  2. 记录指向另一 Agent → 提示“请重新加载插件或重启”；
  3. 本安装确实较旧，“才”提示“请更新本侧”。
- **逐情形推演**：
  - **情形 1：Codex 侧仍是 0.10.3，Claude 侧 0.11.0 已迁移。** 门槛只拦低于 0.10.3 的安装，0.10.3 可以通过，所以这是 0.10.3 的主要使用情形。Codex 入口不满足 1，命中 2，提示“重载或重启”。但本侧根本没有新版本，重启后提示依旧。PRD 第 5 条验收要求“明确提示更新本侧”。迁移后 0.10.3 的后台任务直接结束，后台注册已被 Claude 侧接管，因此 Codex 侧不会自行更新，错误提示会一直持续。
  - **情形 2：Claude 侧 0.10.3、记录来自 Codex 0.11.0。** 同理，提示错误。
  - **情形 3：Codex 已有 0.11.0 缓存、记录来自 Claude 0.11.1。** 按 1 不转交（0.11.0 低于记录版本），落到 2。提示重载在这里恰好有效，但其实可以直接转交给 0.11.0，由新代码处理。
  - **无记录、代号 ≥2**：例如记录被回退的 0.10.2 删除，或尚未重建。5.4 只写“不接管”，没有规定提示内容。
- **影响**：最常见的跨侧情形给出无效指引，违反已批准的验收。5.4 明确规定 0.10.3 的判定在发布后无法修改，所以必须在 0.10.3 编码前修正。
- **最小修复（不改变边界）**：
  1. 转交条件改为“本安装存在支持代号 2 的缓存（≥0.11.0）”，不要求不低于记录版本。满足则转交，或至少提示“本侧已更新，请重新加载插件或重启”。
