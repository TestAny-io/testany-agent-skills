#### HLDR-SDX-P1-01（剩余项）：没有启动记录时，0.10.2 仍会接管

- **有效依据**：REQ-SDX-007 v0.4 新增验收“同一 Agent 内从较新版本回退到较旧版本时，较旧版本不接管数据目录”；MR-SDX-002。HLD 3.7 写明来源路径方案“也覆盖同一 Agent 内回退到旧版本的情形”，8.4 写明“回退到 0.10.2 及更早时拒绝接管”。
- **当前失败**（0.10.2 源码与本轮实验）：
  1. 0.10.2 的 `checkOwner` 遇到空记录直接放行（`scripts/launch.mjs:114` `if (!record) return;`）；原生入口在没有记录时只按端口探测，端口上没有服务就调用自己的启动脚本（`native-backend.mjs:56`、`:149`）。两者都不读取数据代号。
  2. 现有 `stop` 在停止成功或进程已不存在时删除 `launcher.json`（`launch.mjs:45`、`:54`）；`stop` 是技能说明中公开的日常操作（`SKILL.md:40-43`）。v0.4 没有改变这一语义，也没有规定 0.11.0 的停止、重启失败回滚等路径保留记录。
  3. 本轮实验（`verify/r2-legacy-lab/r2-takeover.mjs`，真实 0.10.2 代码）：

     | 情形 | 0.10.2 启动器 | 0.10.2 原生入口 |
     |------|--------------|----------------|
     | A 来源指向数据目录内的运行位置 | 拒绝 | 拒绝（“未接管其后台”） |
     | B 没有启动记录，数据目录已有代号 2 标记和 version 2 的计划文件 | **放行**：`status` 正常返回，`start` 越过归属检查，一直执行到端口检查 | **放行**：调用了自己的启动脚本 |
     | C 来源为 Claude 插件缓存 | 拒绝 | 拒绝 |
     | D 同一 Codex 安装的较新缓存，身份字段加新字段 | 放行（与作者 V15 一致） | 放行 |
     | E 0.10.2 对自己拥有的记录执行 `stop`（进程已不存在） | 记录被删除 | — |

     A、C、D 与作者的 V15 一致，原生入口的结论由执行结果证实，而不只是代码阅读。B 是 V15 没有覆盖的情形。
- **影响**：用户先用 0.11.0 停止服务（或 0.11.0 的重启失败后未能恢复），再在同一 Agent 回退到 0.10.2，0.10.2 就会构建自己的运行目录并启动服务。服务启动时调用 `background.ensure()`（`service.mjs:1062-1065`），把后台入口和上下文改回 0.10.2，后台任务随之在代号 2 的数据上运行 0.10.2 代码，DEC-SDX-022 的接管被撤销。后果取决于 0.11.0 的共享文件格式，而 HLD 没有规定：如果计划文件的 `version` 不再是 1，0.10.2 的调度器会在加载时报错（`scheduler.mjs` 的 reload），服务起不来，相当于碰巧失败关闭；如果计划文件仍是 version 1 的形态，0.10.2 会正常读写。首轮建议的第二道防线（新代号数据不写入 0.10.x 会读写的文件，或明确依赖并测试 0.10.x 校验器的“直接失败”行为）没有被采纳。
- **最小修复（不改变边界）**：
  1. 在 3.7 与 5.3 中把启动记录定为跨版本契约：0.11.0 及以后的版本永远不删除 `launcher.json`。停止、重启失败、清理失效进程时，改写为“已停止”形态，保留 `state`、指向数据目录的 `source` 和新身份字段，只清除进程信息。0.10.2 的归属检查发生在任何动作之前（`launch.mjs:125`），保留的记录足以让它拒绝。
  2. 补第二道防线：规定代号 2 下 0.10.x 会读取的共享文件（至少 `local/updates.json`）让 0.10.x 的校验器直接失败，例如文件版本号不再为 1，并写入测试义务。
  3. 9.3 增加 V16：没有启动记录、0.11.0 执行 `stop` 之后、重启失败之后，三种情形下 0.10.2 启动器与原生入口均拒绝。
  4. 修正 3.7、8.3、8.4、9.3 中“0.10.2 及更早会拒绝接管”的表述，写明前提。
