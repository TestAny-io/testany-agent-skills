## 4. 新发现

### PH4ABR2-P3-01 显式作用域写入非决定层时，确认了别的规则就会静默覆盖写入层中的中间档，而且写入不生效

- **位置**：`claude-actions.mjs:111-116`。`expected` 只在 `decided === layer` 时设置；写入层中的中间档检查以 `!request.confirm` 为条件，而 `confirm: true` 可能只是对共享设置（`:103`）或同名技能（`:102`）的确认。
- **复现**（E-S3，导出副本、沙箱、临时世界）：项目技能 `p1`，项目共享设置中为 `name-only`，本地设置为 `on`（`decidedBy: local`，`visibility: enabled`）。请求 `{ action: "skill.toggle", agent: "claude", id, enabled: false, scope: "project", expectedRevision }`：
  1. 第一次只返回 `scope, reload`，没有提到共享设置中的“仅显示名称”会被取消；
  2. 带 `confirm: true` 重发：共享设置中的 `name-only` 被改为 `off`，随后返回 `READBACK_FAILED`（本地设置仍决定为开）。
  结果是：协作者共享的文件被改了，本项目里也没有生效，原来的中间档丢了，且从未提示。对照 E-S3b：不带作用域时写本地设置，共享设置不动。显式 `scope: "user"` 加同名技能（确认的是同名规则）同理。
- **影响范围**：当前界面切换技能不带 `scope`，走不到；但这是 36c 7.1 公开的请求形态。这正是 4b P3-08 第 3 条想关闭的情形，修复只覆盖了“没有其他规则”的情况。
- **建议**：① 显式作用域低于决定层时直接拒绝（例如 422“该技能当前由项目本地设置决定，写入项目共享设置不会生效”），不写入；或 ② 在第一次确认前读出写入层中该条目的当前值，若为中间档就把对应的 `visibility` 规则加入首批规则；`beforeWrite` 中的中间档检查改为“读到的中间档不在首批规则中时要求确认”，不再依赖 `request.confirm`。补用例。

### PH4ABR2-P3-02 新建设置文件的权限固定为 0644，不再受 umask 约束

- **位置**：`claude-settings.mjs:61`（新文件 `mode = 0o644`）、`:66`（`chmod(temporary, mode)`）。
- **复现**（E-S6）：umask 为 077 时，补丁新建的文件为 0644；同一 umask 下普通 `writeFile(…, { mode: 0o644 })` 得到 0600（即改动前的行为）。已有文件 0600、0664 改写后都保持原样（正确）。
- **影响**：使用严格 umask 的用户，SkillDock 新建的 `~/.claude/settings.json` 或项目 `.claude/settings.local.json` 对本机其他用户可读；Claude 之后往里写 `env` 等内容时多半沿用该权限。单用户 Mac 上影响小。
- **建议**：只对已有文件 `chmod`；新文件不 `chmod`（交给 umask），或直接用 0600。
