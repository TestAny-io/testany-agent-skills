## 4. 问题

### PH3U1R2-P2-01 标题计数改为跟随 Agent 后，技能、市场来源、操作记录三页的其他计数仍是两侧合计

- **位置**：
  - `App.tsx:705-708`：`titleObjects`、`titleCount`、`titleSplit` 对技能、插件、市场来源三页都生效，操作记录页的标题也改为 `visibleActivity.length`。也就是说，标题跟随 Agent 不只发生在插件页。
  - 技能页：左侧四个分类（全部技能、已启用、个人与项目、状态待确认）的计数来自 `counts`（`App.tsx:648-658`，用 `skills` 全量计算），渲染在 `:913-916`，不按 Agent 过滤。
  - 市场来源页：集合标题“已连接来源”用 `data.marketplaces.length`（`:1220-1221`）。
  - 操作记录页：集合标题“最近的变化”用 `data.activity.length`（`:1307-1308`）。
- **失败场景**（两个环境都在，顶部选 Claude）：
  - 技能页：标题与集合标题是 Claude 技能数（例如 12），左侧“全部技能”仍是两侧合计（例如 80）。这正是上一轮 P3-04 在插件页的情形，Owner 已就插件页提出过同样的反馈；插件页改了，技能页没改，两页的左侧分类含义也因此不同。
  - 市场来源页：标题是 Claude 的 marketplace 数（例如 3），紧下面的“已连接来源”是两侧合计（例如 10），列表显示 3 张卡片。改动前两个数都是 10（都不跟随），本提交让同一屏出现两个不同的总数。
  - 操作记录页：同上，标题与“最近的变化”不一致。
  - UAT 说明 `40` 第 3 节第 2 条请 Owner 核对“技能库……计数与你的实际情况相符”。
- **依据**：Owner 第二批反馈“计数跟随顶部 Agent 筛选”；PRD 5.2.2“筛选结果与标识一致”。
- **定级理由**：不影响数据与操作，只是计数不一致；但 Owner 已把同类问题作为 UAT 缺陷提出，下一轮试用很可能再次报告，且本提交在两页上制造了新的同屏矛盾，所以定为 P2 而不是 P3。
- **建议**：
  1. 技能页左侧分类的 `counts` 改为基于 `skills.filter(skill => matchesAgent(skill, effectiveAgent))` 计算（与插件页 `agentPlugins` 的做法一致）。
  2. “已连接来源”改用 `visibleMarkets.length`，“最近的变化”改用 `visibleActivity.length`；两页的空状态判断（`data.marketplaces.length ?`、`data.activity.length ?`）也改用过滤后的列表，否则选 Claude 且 Claude 一侧为空时既没有卡片也没有空状态（既有问题，顺手修）。
  3. 若只想让插件页跟随，就把技能、市场来源、操作记录三页的标题恢复为合计；但这样插件页与其他页的语义不同，不建议。
  4. 补测试，见 P3-02。

### PH3U1R2-P3-01 被忽略的目标记录若带有与目标对不上的字符串身份，读回与后台仍会误判

- **位置**：`cli.mjs:113-119`。`dropPlugin` 只要取到任意一个字符串身份就不算“身份不明”，但这个身份可能与目标对不上：`pluginId` 换了写法（或为空串）而 `marketplaceName` 缺失、不是字符串时，记下的只有那个对不上的 `pluginId`。
- **复现**（实验 E1，导出副本，沙箱；替身命令行没有真正卸载，变更后 `demo` 的记录被改成下表的形态）：

  | 情形 | `dropped.plugins` / `unidentified` | 卸载读回 | 后台判断 SkillDock（`resolveBackgroundSource`） |
  |------|-----------------------------------|----------|----------------------------------------------|
  | A 缺 `pluginId`（上轮 A） | `demo@market` | `READBACK_FAILED` | 抛错，不删任务 |
  | B `pluginId` 为 `market/demo`（上轮 B） | `market/demo`、`demo@market` | `READBACK_FAILED` | 抛错，不删任务 |
  | C 只剩 `name` | `unidentified.plugins = true` | `READBACK_FAILED` | 抛错，不删任务 |
  | **D** `pluginId` 为 `market/demo` 且缺 `marketplaceName` | `market/demo` | **报“已卸载插件 demo”** | **返回 `null`：判为已卸载** |
  | **E** `pluginId` 为空串且缺 `marketplaceName` | `""` | **报“已卸载插件 demo”** | **返回 `null`：判为已卸载** |

- **影响**：需要 Codex 命令行的输出同时出现两处变化，可能性比上一轮的 A、B 低得多，所以定为 P3。但后台的后果仍是破坏性的（停用更新计划、删除后台注册）。情形 E 的诊断还会显示为“CLI 返回了无法安全使用的插件记录 ，已忽略。”（身份为空）。
- **建议**（任选其一，改动都很小）：
  1. 只把形如 `<非空>@<非空>`（恰好一个 `@`，允许空格，以免把 Owner 那条名称带空格的记录变成身份不明）的字符串算作身份；一条记录的身份都不是这种形状时，置 `unidentified`。D、E 因此变为“无法确认”，Owner 的情形不受影响。
  2. 至少在后台判断（破坏性）中再加一条软匹配：被忽略记录的 `name` 等于 `identity.plugin` 时视为可能是 SkillDock。
  3. 补 D、E 两个用例。

### PH3U1R2-P3-05 Claude marketplace 副本仍有三种情形静默

- **位置**：`claude-catalog.mjs:282-300`。
- **复现**（实验 E4）：`plugins` 不是数组时插件数为 0、不列未安装插件、没有诊断；marketplace 没有 `installLocation` 时同样静默；marketplace 名不合规（例如带空格）时插件数照常计算，但一条未安装插件都不列，也没有说明。
