#### HLDR-SDX-R5-P1-01：旧“项目”字段的形态与真实转交路径冲突

- **当前设计**：
  - 3.7 第 699 行：旧项目字段“写成与健康检查返回值不一致的形态”。依据是“0.10.2 原生入口的健康核对不比较该字段，转交与代理照常（第 4 轮实验 K3）”。
  - 3.7 第 699 行同时写明代价：原生入口转交时会把该字段作为 `--project` 的兜底值传给 0.11.x 启动器，新启动器须识别并忽略。具体形态在 LLD 定。
  - 5.4 第 845 行④：`launch.sh start --project …` 可用，并识别、忽略旧项目字段的兜底值。
- **0.10.2 的实际逻辑**（`native-backend.mjs`）：
  - 第 113 行：项目取值顺序为 `SKILLDOCK_PROJECT_DIR` → `project.json` 的路径 → 启动记录的 `project` → 用户主目录。
  - 第 116～118 行：以该值为 `--project` 执行 `launch.sh`，**并以它为子进程工作目录**。
  - 第 132、149 行：只要本进程从未成功打开过（`prepared` 为假），或实例不在运行，就会走这条启动路径。
  - Codex 的 MCP 配置（`.mcp.json`）不设 `SKILLDOCK_PROJECT_DIR`；`project.json` 只在用户于界面中选择项目时写入（`service.mjs:939`）。因此多数用户走到的是启动记录的 `project`。
  - 第 123～124 行的错误路径从 `errors.mjs` 导入并不存在的 `redact`，会把真实原因吞掉。打包后的 `assets/native/server.mjs` 逻辑相同。
- **本轮实验**（真实 0.10.2 原生入口模块，不注入替身启动函数；实例由 Claude 侧运行，旧来源字段取 Codex 侧 0.11.0 缓存，即 L1 规则）：
  - E1：项目字段为不存在的路径，进程首次打开，没有 `project.json`。
    - 结果：失败，`TypeError: redact is not a function`；0.11.x 启动脚本根本没有被调用。
    - 根因：工作目录不存在，`spawn /bin/sh ENOENT`，已单独复核。
  - E2：项目字段为存在、但与健康检查不同的目录。结果：成功；启动脚本收到 `start --project <该目录>`，工作目录为该目录；请求被代理到新实例。
  - E3：同 E1，但有 `project.json`。结果：成功，启动脚本收到用户保存的项目。
  - E4：进程此前已成功打开过，之后记录改为不存在的路径。结果：成功，不再调用启动脚本。
- **当前失败**：
  - Q9 的主要情形是：Claude 侧一键更新 Codex 侧之后，打开仍加载 0.10.2 代码的 Codex 面板。只要该面板在本次 Codex 运行期间还没打开过 SkillDock，且用户从未在界面中选过项目，就会命中 E1。
  - 实例已停止或机器重启后，从任何 0.10.2 面板打开，也会命中 E1。
  - 结果都是无法转交，并显示无法理解的错误。
- **影响**：
  - 与 PRD 0.6 已登记的行为（Codex 侧 0.10.2 原生入口进程自动转交，包括一键更新另一侧之后）以及 HLD 8.3 的表述相冲突。
  - 0.10.2 已冻结，无法修补。数据不受影响。
  - 5.4 是 0.10.3 编码前要定稿的兼容约束清单，V19 指定的种子实验又都绕过了这条路径。因此按现有 HLD 写 LLD、建矩阵，这个问题都发现不了。
- **最小修复（不改变边界）**：
  1. 5.4 兼容约束增加一项，或改写④：旧项目字段必须是**存在、可进入的绝对目录**，且不等于 0.11.x 健康检查返回的 `launchProject` 与 `project`。例如数据目录内由 0.11.x 创建并保持存在的固定子目录。0.11.x 启动器收到该目录作为 `--project` 时忽略它，并能以它为工作目录正常运行。
  2. 3.7 第 699 行改为如实说明：“转交与代理照常”在上述形态下成立；第 4 轮 K3 只验证了代理与健康核对，没有验证真实子进程。
  3. 5.4 中 0.10.3 的判定写明：0.10.3 转交时不以旧项目字段作为 `--project` 或工作目录（0.10.3 发布后同样无法修改）。
  4. DEC-SDX-027 与 V19 写明：原生入口用例必须走真实子进程路径，覆盖“首次打开 / 已打开过”“有无 `project.json`”“实例存活 / 未运行”。
- **责任说明**：
  - 这项形态约束出自第 4 轮 R4-P2-01 的建议。第 4 轮的 K3、NB、L1 实验给原生入口注入了替身启动函数，没有覆盖子进程的工作目录。

## Decision Gates

- **DG-R5-01（产品 Owner，知悉并确认表述）：PRD 0.6 收窄后的 Q9 仍比设计宽**
  - **背景**：PRD 7.3、Q9、1.2 与 HLD 8.3 写的是“Codex 侧仍在运行的 0.10.2 原生入口进程与 0.10.3 入口自动转交（包括一键更新另一侧之后）”。按 v0.7 的旧来源规则（Codex 侧有 ≥0.11 缓存才指向 Codex，否则指向当前运行安装），以下情形不成立：
  - **(a) Codex 侧缓存只到 0.10.3，但 Codex 面板仍加载 0.10.2 代码**（实验 E7a）。
    - 如何发生：SkillDock 在 Codex 中自更新到 0.10.3，但 Codex 应用没有重启，之后 Claude 侧 0.11.0 完成迁移。门槛允许 0.10.3 通过，因此不会触发一键更新。
    - 结果：旧来源字段指向 Claude 缓存，Codex 面板报“SkillDock 数据目录属于另一个安装来源”，直到重启 Codex；重启后 0.10.3 提示更新本侧。数据不受影响。
    - 发生频率：0.10.3 与 0.11.0 之间正是用户自更新到 0.10.3 的窗口期，而 Codex 应用常常长时间不重启，所以这一情形并不罕见（取决于 V17）。
  - **(b) “0.10.3 入口自动转交”只在本侧已有 ≥0.11 缓存时成立**，否则提示更新本侧（符合 REQ-SDX-007 第 5 条验收）。这是措辞问题。
  - **(c) 旧来源字段指向的缓存被删除后**（实验 E6），尚未打开过的面板会转交给自身的 0.10.2 启动器并被拒绝。发生条件很少见，按 R5-P2-01 加维护规则即可，不需要 Owner 处理。
  - **可选方案**：
    - A：登记 (a) 为已知残留，并把 Q9 与 HLD 8.3、3.7 改为如实表述，例如“Codex 侧已有 0.11 或更高版本缓存时，仍在运行的 0.10.2 原生入口进程自动转交；0.10.3 入口在本侧已有 0.11 或更高版本时转交，否则提示更新本侧”。
    - B（由作者在 0.10.3 编码前评估）：旧来源字段在 Codex 侧没有 ≥0.11 缓存时，改取 Codex 侧最高版本缓存（例如 0.10.3）。
      - E7b 证实：已打开过的 0.10.2 面板会代理到新实例。
      - 尚未打开过的面板会调用 0.10.3 启动器。按现有 0.10.3 规则它会提示“更新本侧”并失败，而 0.10.2 的错误路径会把提示吞成“redact is not a function”，比现状更难懂。
      - 若要让这类面板也能工作，需要 0.10.3 启动器在被旧入口调用、且能核实存在更新的运行实例时，返回该实例而不接管。这会修改 0.10.3 规则，必须在 0.10.3 编码前定。
  - **推荐**：至少采用 A；B 由作者评估，采用后 Q9 表述随之调整。
  - **缺少的授权**：Owner 对 (a) 的知悉记录，以及对 Q9 新表述的确认。

  - HLDR-SDX-R5-P1-01 的形态约束出自第 4 轮建议。
