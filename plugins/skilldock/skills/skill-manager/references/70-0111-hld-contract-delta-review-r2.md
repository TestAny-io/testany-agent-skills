#### D28-P2-01 插件自带的技能只读默认的 `skills/`：条目或 manifest 声明了技能路径的插件，列出的集合与 Claude 实际加载的不同

- **位置**：`35`:590-591（3.2 新条文）；`36c`:183；`server/claude-catalog.mjs:144-163`（`pluginSkills`）、`:319`；对照 `server/cli.mjs:301-328`（`discoverSkillRoots`）与 `docs/plugin-development.md:30`。
- **问题**：新条文写“取自插件安装目录默认的 `skills/`……manifest 另行声明的技能路径不读”。实现确实如此，但它有两个方向的后果，条文只写出了半个：
  1. **漏列**。技能放在别处、由 marketplace 条目的 `skills` 声明的插件，一条也不列，`skillCount` 为 0。条文只说了“manifest 另行声明的”，没有说条目声明的；没有 Claude manifest 的插件，条目就是它的 manifest。
  2. **多列**。条目的 `source` 指向 marketplace 根目录、并用 `skills` 列出其中几个子目录的插件（一个仓库拆成几个插件、共用根目录下的 `skills/` 时就是这种写法），安装目录里是整个根目录，实现会把 `skills/` 下的全部技能都列在这个插件名下，`enabled` 跟随插件，`skillCount` 也是全部。按仓库自己的规则文档，这种条目列出的路径是“完整集合”，Claude 只加载声明的那几项。
- **证据**：
  - 实测（探针，放在导出目录之外，只调用导出目录里的 `claudeCatalog` 与 `discoverSkillRoots`，不运行任何真实命令行）：一个 marketplace 里两个根目录插件各声明 `./skills/x`、`./skills/y`，根目录下另有 `skills/z`；第三个插件的技能在 `./tools`。Claude 一侧的清单对前两个插件都列出 `x,y,z`、`skillCount` 为 3，对第三个列出 0 项。同一份 marketplace 副本交给 SkillDock 自己用于 Codex 一侧的规则，得到的技能根分别是 `skills/x`、`skills/y`、`plugins/custom/tools`。
  - 已核对：`discoverSkillRoots` 读默认 `skills`、manifest 与条目声明的路径，并对“条目位于 marketplace 根目录且列出了实际存在的子目录”做限定（`cli.mjs:312-318`）；`pluginSkills` 只读 `skills/`。两侧对同一种声明的处理不一样。
  - 推断：Claude 对这种条目只加载声明的子目录，依据是 `docs/plugin-development.md:30` 对上游规则的记述（“这些路径才按官方例外成为完整集合”）。本轮没有用真实的 Claude 命令行验证，也没有读真实的 Claude 配置去看这台电脑上有没有这样的插件。
- **影响**：只影响只读条目与数量的显示，不产生写入，也不影响 Claude 自己的行为。但多列时，界面会把 Claude 并不提供的技能显示为该插件的、已启用的技能；REQ-SDX-002 的验收标准要求清单“与 Claude 自身插件列表读回结果一致”，PRD 的原则是“不伪造”。0.11.0 的技能数同样是这样数出来的，只是那时只有一个数字，现在成了逐条的条目。Owner 是为了满足“已安装插件及其技能”才改定这条的，这个出入应当让 Owner 知道。
- **建议**：
  - 先用隔离环境确认 Claude 的实际加载（本地目录 marketplace，两个根目录插件各声明一个子目录，读 `claude plugin details` 的 `Skills (N)`），做法与分发冒烟相同。
  - 属实的话二选一：① 实现改为按条目与 manifest 的声明取技能根（清单读取时已经拿到 marketplace 副本的位置，`claude-catalog.mjs` 的 `copies`；规则可以与 `discoverSkillRoots` 共用），HLD 3.2 与 36c 相应改写并复审；② 暂不改实现，把这两种情形写成已知限制（HLD 3.2、36c 第 6 节、CHANGELOG），并请 Owner 知悉。
