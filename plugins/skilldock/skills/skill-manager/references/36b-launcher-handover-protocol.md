## 3. 命令行语法（冻结，沿用 0.10.2）

```
/bin/sh <skillRoot>/scripts/launch.sh [start|restart|status|stop|doctor|cli …] [--project <绝对路径>] [--migrate-from testany-eng]
```

- 第一个参数为动作，缺省为 `start`。其后为成对的选项；`--project` 至多一次，值须为绝对路径。
- `<skillRoot>` 为安装中的 `skills/skill-manager` 目录。
- 成功时 stdout 输出一个 JSON 对象，诊断写 stderr；失败时退出码非 0，原因写 stderr。
- shell 层前提：`launch.sh` 先在固定候选中找能运行引导程序的 Node（22.12+），找不到时在进入引导程序之前就以退出码 1 结束（0.10.2 行为，0.10.3 不变）。转交链只在引导程序启动后运行。

## 4. 0.10.3 的转交链（冻结）

### 4.1 触发条件

以下任一成立即触发（36a 第 4、5 节）：
- 数据代号 ≥ 2（含标记文件不可读或无法解析的情况）；
- `<state>/launcher.json` 可以解析，且其 `format` 为整数且 ≥ 2。

不触发时，0.10.3 的行为与 0.10.2 相同（加上第 7.3 节的退避与第 9 节的缺陷修正）。特别地，代号为 1 而 `launcher.json` 不可读或无法解析时不触发，沿用 0.10.2 的“启动记录不可读”报错并以 1 退出；两种处理都不接管。

**重入防护**：0.10.3 启动时环境中已有 `SKILLDOCK_HANDOVER=1`（说明它是被某次转交调起的），则第 1、3 步不可用，只可能走第 2 步或第 4 步，不再转交。

### 4.2 判定时点

- `bootstrap.mjs` 解析参数后、解析工具链（选择或下载 Node、查找 npm）与查找 Codex 命令行之前；
- `launch.mjs` 在核实归属、准备运行目录之前再判定一次（覆盖直接运行 `launch.mjs` 的情形）；
- `launch.mjs` 取得 `<state>/launcher.lock` 之后、停止任何实例或写任何其他文件之前**再判定一次**；此时触发则释放锁、改走转交链。这一条覆盖“0.10.3 读到代号 1 之后、取锁之前 0.11.0 完成迁移”的窗口。
- 0.10.x 的锁不等待：0.11.0 迁移持有 `launcher.lock` 期间，0.10.3 取锁即以“另一个启动操作正在运行，请稍后重试”退出 1，不写任何文件。
- 信号：运行转交链的进程（`bootstrap.mjs`，或在判定点 2、3 触发时的 `launch.mjs`）在等待被调用方期间把收到的 SIGINT、SIGTERM 转发给被调用方（6.2）。`bootstrap.mjs` 不改变 0.10.2 对 `launch.mjs` 子进程的信号处理：未触发转交链时，原生入口 600 秒超时只终止 `bootstrap.mjs`，`launch.mjs` 继续完成构建与启动，与 0.10.2 相同。

不触发的动作：`doctor`（只读诊断）、`cli`（Codex 命令行透传）按 0.10.2 原样执行。

### 4.3 步骤

记号：`P` 为本次收到的 `--project` 值（可能没有）；“有效项目”见 4.4；“运行实例的项目”指健康检查返回的 `project`。

**`start`**：
1. **本安装有 ≥0.11 缓存**：在本安装所在的缓存目录 `<缓存根>/<本 marketplace>/skilldock/` 下，找出满足 36a 第 10.2 节条件 1～5 的最高版本（≥0.11.0）安装。找到即按第 6.2 节调用它，结果见 4.7。
2. **已有核实的运行实例**（4.5 全部成立）：
   - 没有 `P`、`P` 不是有效项目，或 `P` 的规范路径等于运行实例的项目：以退出码 0 交还，stdout 输出第 10.2 节的“沿用实例”结果。**启动记录逐字节不改。**
   - `P` 是有效项目且与运行实例的项目不同（Owner 决定 DG-RUNNING-PROJECT）：不交还，进入第 3 步并转发 `P`，由较新启动器切换项目。第 3 步没有可用目标，或被调用方失败时，按 4.7 回落交还，结果带 `projectNotSwitched`。
3. **调用首选启动目标或兜底安装**：按 4.6 选出目标，按第 6.2 节调用，结果见 4.7。
4. **都不可行**：不启动任何进程，退出码 3，输出第 10.3 节的“需要更新”结果。

**`restart`、`status`、`stop`**：依次尝试第 1 步、第 3 步（转发同一动作；`restart` 同时转发 `P`）；都不可行则按第 4 步处理。这三个动作不走第 2 步，也不回落。

0.10.3 在任何情况下都不自己接管：不启动自己的服务，不停止任何实例，不写启动记录、计划、绑定、历史或后台文件。

### 4.4 有效项目

一个路径是“有效项目”，当且仅当：绝对路径、长度 ≤ 4096、不含控制字符；`realpath` 成功且是目录；规范路径既不等于 `<state>` 的规范路径，也不位于其中。

0.10.3 只在第 2 步比较时使用这一判定；转发时一律原样转发收到的 `P`，由被调用的 0.11.x 自己过滤（第 6.3 节）。

### 4.5 第 2 步的核实

以下全部成立才算“核实的运行实例”：
1. 启动记录 `format ≥ 2`、`status` 为 `"running"`、`running` 为对象；
2. `url` 符合 `http://127.0.0.1:<端口>` 形态；
3. 对 `<url>/api/health` 发一次 GET（2 秒超时、不跟随重定向、响应不超过 1 MiB）返回 200 与 JSON，且：
   - `app === "skilldock"`，`instanceId` 为字符串；
   - `pid`、`state`、`sourceDigest` 分别等于记录中的 `pid`、`state`、`digest`，且 `state` 等于本次解析的 `<state>` 规范路径；
   - `appVersion` 为 `x.y.z` 且 ≥ 0.11.0；`dataGeneration` 为整数且 ≥ 2（36c 第 4 节）。

第 2 步不要求 `running.appPath` 仍然存在（另一侧清理旧目录不影响交还），也不要求“运行中的安装”与“首选启动目标”一致。

### 4.6 第 3 步的目标选择

1. 启动记录 `format ≥ 2` 且 `preferred` 为对象时，按 36a 第 10.2 节条件 1～6 自行核验 `preferred.appPath`（不信任记录中的 `version` 与 `sourceKey`）。通过即为目标。
2. 否则（没有记录、没有 `preferred`，或核验不通过），在第 5.1 节列出的全部缓存根下枚举 `<缓存根>/*/skilldock/*/skills/skill-manager/assets/app`，取满足条件 1～6 的最高版本。版本相同时，本安装所在 Agent 优先，再按 `appPath` 字典序取第一个。
3. 本安装的来源标识不可核实（例如开发目录、本 marketplace 是本地目录）时，第 3 步不可用。

### 4.7 下游结果与回落

| 情形 | 0.10.3 的退出码与输出 |
|------|----------------------|
| 被调用的启动脚本退出 0 | 退出码 0；stdout 写出被调用方的 stdout |
| 第 1 步的被调用方失败，且重新读取启动记录后 4.5 全部成立（仅 `start`） | **回落第 2 步**：退出码 0；stdout 输出“沿用实例”结果，带 `warning`，以及按下文规则的 `projectNotSwitched` |
| 第 1 步的被调用方失败，且没有核实的运行实例 | 退出码 1。不再尝试第 3 步 |
| 由第 2 步例外转入的第 3 步：没有可用目标 | 回落第 2 步：退出码 0；带 `projectNotSwitched` |
| 由第 2 步例外转入的第 3 步：被调用方失败 | 重新读取启动记录并执行 4.5（被调用方可能已重启实例、换了 `pid` 或端口）：成立则回落第 2 步（退出码 0，带 `warning`，以及按下文规则的 `projectNotSwitched`）；不成立则退出码 1 |
| 其他情形下第 3 步的被调用方失败 | 退出码 1 |
| 第 4 步 | 退出码 3；见第 10.3 节 |

`projectNotSwitched` 只在 `P` 是有效项目、且其规范路径不等于回落时健康检查返回的 `project` 时给出。

被调用方失败时，它已写出的 stdout 不转出到 0.10.3 的 stdout（保证 0.10.3 的 stdout 只有一个 JSON），改为截取末尾不超过 4 KiB 写到 stderr 供诊断；被调用方 stdout 超过 64 KiB 视为被调用方失败（不截断转出），超限后 0.10.3 继续读取并丢弃，等待被调用方自行退出，不主动终止它；被调用方的 stderr 始终实时透传。

## 6. 调用约定

### 6.1 0.10.2 原生入口调用启动脚本（冻结代码的事实，`native-backend.mjs`）

| 项 | 0.10.2 的行为 |
|----|--------------|
| 实例地址 | 进程环境有 `PORT` 时取 `http://127.0.0.1:<PORT>`；否则取启动记录 `url`；都没有时取 `http://127.0.0.1:4771`。Codex 启动 MCP 进程时环境中通常没有 `PORT` |
| 何时调用 | 进程内首次打开界面时，即使实例健康也会调用一次；之后实例不可用时再调用。调用期间持有 `<state>/native-start.lock` |
| 调用谁 | 启动记录 `source` 所指版本高于自身时，调用 `<source>/../../scripts/launch.sh`；否则（包括没有启动记录、`source` 所指缓存已被删除而读不到版本）调用自身的 |
| 命令 | `/bin/sh <skillRoot>/scripts/launch.sh start --project <P>` |
| `P` 与工作目录 | 取同一值：`SKILLDOCK_PROJECT_DIR` → `<state>/project.json` 的 `path` → 启动记录旧 `project` → 主目录 |
| 环境 | 自身进程环境，加 `SKILLDOCK_STATE_DIR` 与 `PORT`（取上面的实例地址的端口） |
| 超时与输出 | 600 秒；stdout、stderr 各不超过 1 MiB，超出即视为失败 |
| 成功判定 | 只看退出码 0；随后重读启动记录并做健康检查。连接不上报“后台尚未就绪，请重试”；端口上的服务与记录不符报“端口上的服务与 SkillDock 启动记录不匹配” |
| 失败表现 | 非 0 退出时因自身缺陷显示 “redact is not a function”（PRD 0.9 Q9 已登记） |

### 6.2 0.10.3 调用 0.11.x 启动脚本（冻结）

| 项 | 约定 |
|----|------|
| 程序 | `/bin/sh`，参数数组为 `[<目标 skillRoot>/scripts/launch.sh, <动作>, …]`，不经 shell 拼接 |
| 动作 | 与收到的动作相同（`start`、`restart`、`status`、`stop`） |
| `--project` | 收到 `P` 且动作为 `start` 或 `restart` 时原样转发 `--project P`；否则不带。`--migrate-from` 不转发 |
| 工作目录 | `<state>` 的规范路径（不沿用收到的工作目录） |
| 环境 | 0.10.3 自身的进程环境，另外：设 `SKILLDOCK_STATE_DIR=<state 规范路径>`；删除 `SKILLDOCK_RESTART_JOB`；设 `SKILLDOCK_HANDOVER=1`、`SKILLDOCK_HANDOVER_AGENT=<本安装 Agent：codex / claude / unknown>`、`SKILLDOCK_HANDOVER_FROM=0.10.3`。其余变量（含 `PORT`、`CODEX_HOME`、`SKILLDOCK_PROJECT_DIR`、`SKILLDOCK_NODE_BIN` 与宿主会话变量）原样保留 |
| 标准流 | stdin 关闭；stderr 实时透传；stdout 由 0.10.3 缓存（上限 64 KiB，超出视为被调用方失败），按 4.7 处理 |
| 超时与信号 | 0.10.3 不另设超时；收到 SIGINT、SIGTERM 时转发给被调用方 |
| 0.10.3 自身输出 | 调用前在 stderr 写一行转交说明（第 10.1 节），不超过 1 KiB |

### 6.3 0.11.x 对启动脚本调用方的义务（冻结；只要声明与 0.10.2、0.10.3 共存就必须满足）

**调用形式**：任一侧的 0.11.x 启动脚本，必须能被 0.10.2 原生入口按 6.1、被任一侧的 0.10.3 按 6.2、被 0.10.x 自更新协调器按 7.1 调用，并正常完成。进程环境可能来自任一 Agent，可能带有、也可能不带 Claude 会话变量（`CLAUDECODE`、`CLAUDE_CODE_*`、`CLAUDE_CONFIG_DIR` 等）。

**调用链防护**：
- 0.11.x 不调用低于 0.11.0 的启动脚本；
- 被调用期间不获取 `<state>/native-start.lock`（调用它的原生入口正持有这把锁）。

**环境与根目录**：
- 服务与命令行子进程的环境仍按白名单构造（HLD 7.2），不继承会话变量。
- Codex 主目录、Claude 根目录、Node 路径一律使用保存值。
- 没有保存的 Claude 根目录时：`SKILLDOCK_HANDOVER_AGENT` 为 `claude` 且环境中有 `CLAUDE_CONFIG_DIR` 或 `CLAUDE_CODE_PLUGIN_CACHE_DIR`，按 DEC-SDX-024 第 2 级（会话值）取值并保存；否则取默认值。

**项目回退**：被 0.10.3 调用（`SKILLDOCK_HANDOVER=1`），或收到的 `--project` 不是有效项目（4.4 的判定，固定子目录必然无效）时，按以下顺序取第一个有效项目：

| 级 | 来源 | 性质 |
|----|------|------|
| ① | 收到的 `--project` | 显式 |
| ② | 继承的 `SKILLDOCK_PROJECT_DIR` | 显式 |
| ③ | `<state>/project.json` 的 `path` | 保存值 |
| ④ | 启动记录 `actualProject` | 保存值 |
| ⑤ | 主目录 | 兜底 |

- 每一级都按 4.4 判定有效性，无效即跳过；此时**不得**把工作目录当作项目。五级都无效时以非 0 退出并说明原因。
- 在 stderr 写一行说明最终采用的项目及其级别；跳过的显式值（①②）一并注明，不另弹提示。
- 项目来自 ①②（显式）且与运行实例的项目（健康检查 `project`）不同：切换运行实例的项目（重启或进程内切换均可），成功后健康检查的 `project` 与启动记录的 `actualProject` 反映新项目。
- 项目来自 ③～⑤：已有运行实例时沿用，不改变其项目。

**完成条件与输出**：
- 退出 0 之前：启动记录已按 36a 第 5 节写好（`format: 2`、`status: "running"`、`url` 为实际地址），且实例通过健康检查。沿用已在运行的实例时同样退出 0。
- 新实例可以换端口，以启动记录的 `url` 为准；调用方不得假设端口。
- 单次调用 stdout 不超过 64 KiB、stderr 不超过 256 KiB；依赖安装与构建的输出写入 `<state>` 下的日志文件，stderr 只写摘要。非 0 退出时不写 stdout。在 590 秒内结束（为调用链上的 0.10.3 留出余量）。
- `status`、`stop`、`restart` 按 0.11.x 自身语义执行；`stop` 把启动记录改为“已停止”形态，不删除。

**补写启动记录**：代号 ≥ 2 而 `<state>/launcher.json` 不存在时（被 0.10.x 启动器删除，PRD Q8），0.11.x 的启动器、服务与后台检查在锁内补写一份反映实际状态的启动记录（实例未运行时为“已停止”形态），旧字段按 36a 第 5.2 节。

## 7. 0.10.x 自更新协调器与后台入口调用 0.11.x

### 7.1 自更新协调器（冻结代码的事实，`server/self-update.mjs`）

| 项 | 0.10.x 的行为 |
|----|--------------|
| 运行位置 | 0.10.x 服务进程内，每 1 秒轮询一次 |

### 7.2 后台入口（冻结代码的事实，`server/background-entry.mjs` 与 `refreshBackgroundRuntime`）

- 0.10.x 后台刷新把 Codex 命令行报告的“已安装且启用”的同一插件版本的应用目录准备为运行目录（第一次切到 0.11.x 运行目录由 0.10.x 工作进程完成，此后的刷新由已加载的 0.11.x 工作进程执行）：只物化 0.10.2 `scripts/source-bundle.mjs` 允许列表中的文件（`APP_FILES`、`APP_TREES`、`ROOT_FILES`；不含链接；总量 ≤ 64 MiB、≤ 10000 个文件），执行 `npm ci --ignore-scripts` 与 `npm run build`，再按 `dist/skilldock-source.tar.gz`、`dist/LICENSE.txt` 核验；随后把新运行目录与摘要写入 `background/context.json`。
- 0.10.x 的 `background/entry.mjs` 读取 `version: 1` 的上下文，加载 `<runtime>/server/background-worker.mjs` 并调用其 `runBackground(context)`。因此迁移之前，0.10.x 后台可能已经在运行 0.11.x 的工作进程代码。

### 7.3 0.10.3 新增的自更新退避（冻结）

Owner 决定（2026-10-08）：0.10.3 的自更新协调器在重启任务失败后退避，避免另一侧仍有低于 0.10.3 的安装、0.11.0 门槛不通过时反复重试。

- **失败**：本次处理待办的结果为失败即计入，不论 `failed` 由谁写入（被调用方已写 `failed` 时 0.10.x 不再改写），包括启动器非 0 退出，以及发起前的核验或摘要计算失败。
- **触发键**：每个轮询周期观察到的 `background/context.json` 的 `digest`（文件不存在或不可读时为空）。安装变化通知不作为触发键的取值。
- 失败后，连续失败次数加 1，下一次处理待办不早于 `min(60 秒 × 2^(失败次数 − 1), 30 分钟)` 之后；等待期间不刷新清单、不写 `restart.json`、不暂停写操作。等待判断放在完整刷新清单之前。
- 以下任一发生即清零重来：触发键变化（出现了新的待更新版本）；服务收到安装变化通知；任务成功（服务会被替换）。
- 计数只保存在服务进程内存中，服务重启后从零开始（不新增持久化文件）。门槛通过后迁移失败、恢复出旧服务时的反复重启由 0.11.x 的义务兜住（7.4）。
- 0.10.2 无法修改，仍按 7.1 每秒重试。

### 7.4 0.11.x 对自更新协调器与后台入口的义务（冻结）

- **源码布局**（以 0.10.2 冻结代码的 `prepareRuntime` 与 `verifyRuntime` 实测为准，G-10）：
  - 0.10.2 `source-bundle.mjs` 的 `APP_FILES`、`APP_TREES`、`ROOT_FILES` 列出的文件与目录必须全部存在（缺任何一个，0.10.2 的 `captureSource` 都会失败）；
  - 0.11.x 运行所需的全部文件都在允许列表内（列表之外的文件不会进入运行目录）；只用普通文件与目录（`.env*`、`.DS_Store` 会被跳过）；
  - 每个文件的路径满足 tar 格式限制：文件名不超过 100 字节，目录前缀不超过 155 字节（否则 0.10.2 的 `materializeRuntime` 失败）；
  - 能用 7.2 的方式（`npm ci --ignore-scripts`、`npm run build`）在 0.10.x 选用的 Node 下构建，构建不得在允许的目录树内新增或修改文件与权限；
  - 0.11.x 的构建脚本接受 0.10.2 写入运行目录的 `.source-snapshot/manifest.json`（`format: 1`、`runtime: true`），并原样复制源码归档与许可证，使产物通过 0.10.2 的运行目录核验。
- **后台工作进程**：保留 `server/background-worker.mjs` 并导出 `runBackground(context)`，接受 `version: 1` 的上下文。代号为 1 时只按代号 1 的格式工作（不迁移、不写新格式文件）；代号 ≥ 2 时按 0.11.x 规则工作。
- **重启任务**：`launch.sh restart` 收到 `SKILLDOCK_RESTART_JOB` 时，读取 0.10.x 格式的 `restart.json`，核对 `id`、`source`（等于自身应用目录）与 `previousPid`（等于当前启动记录的 `pid`）；不要求 `sourceDigest` 与 0.11.x 自身的摘要算法一致。接受任务后必须写终态，不得停在 `preparing`、`restarting`：成功记为 `ready`（0.10.x 格式，含 `pid`、`completedAt`），否则 0.10.x 原生界面会一直显示“重启中”；之后的任何失败记为 `failed`，`restored` 按是否已恢复旧实例取 `true` 或省略。0.11.x 健康检查的 `restart` 由 `restart.json` 派生，不使用 0.10.2 的“摘要相等即 `ready`”捷径。
- **门槛失败的非交互路径**：在解析工具链、下载 Node、准备运行目录与停止旧实例之前判定并拒绝，以非 0 退出并在 stderr 写出可读原因；不弹窗；先用只读文件证据快速判定，只有文件证据显示可能通过时才调用宿主命令行确认；不写 0.10.x 读取的任何文件（包括 `restart.json`，任务状态由 0.10.x 协调器自己记为失败）。
- **门槛通过**：按 HLD 3.7 的固定顺序迁移；迁移完成前写 `restart.json` 的进度沿用 0.10.x 格式。
- **迁移失败后的快速拒绝**：门槛通过后迁移失败、已恢复旧实例时，0.11.x 在 0.10.x 不读取的位置（`<state>/compat/migration-failure.json`，记录目标应用目录、版本与失败时间）记下这次失败。此后对同一目标的非交互重启任务，在解析工具链、下载 Node、准备运行目录与停止旧实例之前直接拒绝（非 0 退出，不写 0.10.x 读取的任何文件），不按时间解除，避免确定性的失败让实例被反复停止和恢复。以下任一发生才删除该记录：交互入口重试成功；目标应用目录或版本变化。交互入口不受此限制。

## 8. 0.10.3 后台任务（冻结）

- 后台入口（`background/entry.mjs`）在读取上下文之前，先用环境变量 `SKILLDOCK_STATE_DIR`（`run.sh` 设置）读取数据代号与计划文件版本：代号 ≥ 2，或计划文件存在且 `version` 不为 1，本次直接结束，退出码 0。工作进程 `runBackground` 开头再检查一次。

## 11. 安全与信任假设

- 0.10.3 只执行满足 36a 第 10.2 节条件的安装中的 `launch.sh`；启动记录中的路径一律先核验再使用。
- 信任假设：启动记录与用户账户同等可信（它位于用户自己的数据目录，权限 `0600`）。从记录派生的缓存根会让 36a 第 10.2 节条件 1 对 `preferred` 自证成立；条件 2～6（废弃标记、包名与版本、manifest、脚本为普通文件、同名同源）仍逐项核验。
- 不经 shell 拼接命令，不把任何读到的字符串作为命令或参数之外的东西执行。
- 读取宿主文件只取 36a 第 9.1 节列出的键，单个文件不超过 1 MiB；任何输出中的 URL 凭证替换为 `[redacted]`。
- 不联网（健康检查只访问 `127.0.0.1`），除 0.10.2 原有的临时锁文件外不写任何文件，不改变后台注册。
