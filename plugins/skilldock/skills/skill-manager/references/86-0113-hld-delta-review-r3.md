## 4. 新发现

没有发布前应处理的发现。以下 3 项都可留到下一版。

**D36-P3-01　3.7 新加的那段“已知残留”并不存在：83 是对的，84 D35-P3-03 第一点是本评审的错**

- 条文（`35`:766）：“这句话对 0.11.0～0.11.2 的服务差一类操作：它们的 Agent 管理状态与设置两类操作不看关闭标记，监听关了以后仍可以经留下来的那条连接开始（84 D35-P3-03）……作为已知残留。83 第 2 节据探针里那条连接上的请求都得到 403 推断旧服务开始不了任何操作，探针的请求是否带着页面的会话令牌没有交代，这里不据此排除。”
- 事实：0.11.0、0.11.1、0.11.2 的入口处理每个请求的第一步是核对 Host，允许的值用监听端口拼出来（三个版本的 `server/index.mjs:60`–`61`，已核对）。监听一关，取不到端口，这一步对**每个**请求都回 403——在核对会话令牌之前，更在分派操作之前。所以留下来的连接上什么操作都开始不了，与请求带不带令牌无关。
- 实测（一个普通的 Node 服务，Host 核对照入口那两行写；隔离沙箱）：关闭之后、连接还在用时，服务已经取不到自己的地址；关闭前在途的读取照常结束；此后同一条连接上的健康检查与带着令牌的操作请求都得到 403。81 第 5.2 节在 0.11.2 的真实入口上看到的 403 正是这个。
- 本评审上一轮只看了服务层的关闭标记，没有看入口处的这一步，提了一条不存在的残留；作者照它写了，并对 83 的推断存了疑。83 的结论成立，“已经没有监听，说明它过了写操作”对三个旧版本同样完整成立。
- 影响：条文比实际更保守，不会让人低估风险。建议下一次修订把这段残留删掉，改写为上面的理由。顺带一提：留下来的旧服务对健康检查回的也是 403，页面看到的是“后台不可用”，而连接照样被占着——与 V28 的推断不矛盾。

**D36-P3-02　7.1 有三处可以写得更全**

- `35`:1111“安装官方目录插件之后的读回……过期时等读取结束，与 0.11.1 相同”：有了存在本机的那一份之后差一种情形。服务重启后，存下的结果不满 10 分钟时，这次读回直接用它、不向 Codex 读（实测）；0.11.1 与 0.11.2 重启后的第一次总是重读。年龄仍在 10 分钟之内，性质没有变，但“与 0.11.1 相同”不再是全貌，`35`:1108“它没有改变的”里也把这两处列为没有改变。
- 失败只在本次运行里记着。`35`:1104 的“上一次读取失败之后的那一次要等”与 `35`:1108 的“失败的显示方式”没有改变，都只在一次运行之内成立：上一次运行的最后一次读取失败了，重启之后仍先用存下的那一份（上一次成功读到的），再在后面重读（实测）。

## 6. 与 36a、PRD 的关系

**与 `36a`。** 作者的判断成立。

- 第 8 节：表里列的是 0.10.x 会读的文件，这个文件不在表里；末段“门槛通过前只允许写……0.10.x 不读取的位置”，`cache/` 属于这一类。数据代号为 1 时服务若在运行（代码允许，`server/service.mjs:137`），写这个文件与第 8 节相容：0.10.x 不读它，回退到 0.10.x 也不受它影响（推断）。门槛失败时服务不会启动，谈不上写。
- 契约不需要改：HTTP 接口的字段与取值都没有变。

**与 PRD。** 不需要动，作者的判断成立。PRD 对官方目录插件只说它是 Codex 专有的概念（第 5.6 节），没有约定它的名称、图标与连接状态要多新；与这件事有关的要求是 7.1 的“首屏清单可用 < 3 秒”，这项改动是朝它去的。存到本机的数据落在“数据目录只属于 SkillDock”之内。显示可能是旧的这一性质 0.11.2 起就有，这次是加了上限并延伸到重启之后，由 Owner 同意（DG-0113-2）。
