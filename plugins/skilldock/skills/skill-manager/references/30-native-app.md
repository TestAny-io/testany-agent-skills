## 工程边界

原生界面与浏览器共用 React 页面和业务 API；仅替换传输层。MCP Apps bridge → app-only MCP tools → 受约束的 loopback HTTP API。既有后端继续执行权限、来源、互斥、CSRF 和文件事务检查，不扩大 CORS / iframe 访问。

插件携带可复现构建的 MCP server / 单文件 UI，发现入口不联网、不构建、不启动网页后台。实际打开界面后才调用既有 launch.sh；编译及数据写入用户数据目录，禁止写入插件缓存。使用 Codex 解析的插件根相对 cwd 和脚本路径，不含开发者绝对路径。

MCP 仅代理固定 GET 路由和 `/api/actions` POST；拒绝任意 URL、任意请求头和超过 32 KiB 的操作。会话 token 保留在 MCP 进程，UI 使用后台 instanceId 绑定操作。数据仅放入工具结果 `_meta`；写工具限 app 可见并标注可能修改本机数据。POST 失败后不重试，避免双重安装/删除。

外链与许可/源码下载通过宿主 openLink 打开；仅声明 clipboardWrite 权限供用户点击复制路径，不申请剪贴板读取。宿主拒绝复制时沿用手动选择路径的提示。

启动复用现有 launcher 的身份核实、runtime 构建、回滚和数据接续。跨 MCP 进程启动加锁，不按端口杀进程；服务身份错误或来源不匹配时拒绝接管。网页服务生命周期与 macOS 独立定时更新分离。

公开文档支持 MCP UI；侧栏 global entrypoint 仍为当前宿主实测扩展。已验证原型宿主 26.924.22138 / build 11645；跨宿主版本需继续验证。

## 原生 UAT：浅色混入深色（2026-09-28）

用户截图显示浅色已选中，但弹窗、卡片和表单部分为深色。读取当前宿主包的样式后，在隔离 MCP 宿主注入同类 `:root.dark { color-scheme: dark }`，复现了同样的画面：应用偏好为 light，弹窗的计算 color-scheme 却为 dark，背景为 rgb(34, 34, 34)。此前的隔离宿主只传 theme 元数据，没有注入这类样式，因此未覆盖此冲突。

修复将完整主题变量和 color-scheme 同时定义在应用根容器，通过 `data-skilldock-theme` 更新，避免继承宿主的文档主题；diff 的显式深色选择器也使用应用自己的主题。现有浅色、深色调色值不变。

验证：
- 实际分发 UI / MCP / 后台的隔离宿主增加 `?hostTheme=dark`，默认 light；注入独立的文档主题 CSS。
- 宿主深色、应用浅色：弹窗计算背景 rgb(255, 255, 255)，卡片/表单/根容器均为 light。宿主后续改成浅色并覆盖文档主题时，应用手选的 dark 仍保持一致。
- 跟随系统随模拟系统 light/dark 正确切换；修复前、修复后的浅色及深色截图已查看。
- `uat-round1` 与 `source-links-diff` 共 17 项浏览器回归通过；类型检查、网页/原生构建、2 项原生协议/产物检查通过。
- 本机 Preview 通过版本 cachebuster 和 CLI 重装刷新资源，仍需用户重新加载原生页面确认最终宿主效果。未提交或发布。
