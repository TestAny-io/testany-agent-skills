## 4. 新发现

### 发布前应处理

**D34-P2-01　启动器强制结束进程的两条规则：判断“监听已关”的条件，实现比条文宽**

条文（`35`:766–767）的安全论证是一条链：记录的地址上“不再应答”或“没有任何应答” → 监听已关 → 服务关监听在收尾写操作之后 → 已过了写操作 → 可以强制结束。链的第一环在实现里是 `probe`（`scripts/launch.mjs:34`–`40`）：向记录的地址取一次健康检查，1.5 秒超时；连不上、超时、答的不是 200、答的不是 JSON，一律返回空。两处强制结束都只看这个结果（`:104`、`:119`）。所以“连接被拒绝（确实没有监听）”与“在监听但 1.5 秒内没答出来”“在监听的是别的程序、答的不是 200 的 JSON”在实现里是同一种情形。

实测（探针，替身服务，隔离沙箱，每个场景有时限并清掉了自己启动的进程）：

| 场景 | 条文 | 实际 |
|------|------|------|
| A　记录的服务**仍在监听**，只是答得慢（4 秒），收到通知后还要 6 秒才写完；另一次 `start` 到来 | “已过了写操作”才结束 | 6.5 秒后被结束（SIGTERM，3 秒，SIGKILL），它的写没有完成 |
| B　经健康检查核实的服务收到通知后仍在监听、还在写，期限到时答得慢 | “仍应答的是在收尾写操作……不强制” | 被 SIGKILL，它的写没有完成 |
| C　留下来的旧服务（监听已关）之外，地址上有别的程序在应答 404，或 200 的非 JSON | “地址上有别的程序在应答时，照旧拒绝” | 旧服务被结束；随后 `start` 以“端口已占用……未停止现有服务”失败（这句提示此时也不对）。别的程序答 200 的 JSON 时才拒绝，入库用例只测了这一种 |
| D　进程表给出的命令行是“某个编辑器加该文件”，或 Node 与该文件之间还有别的参数 | 命令行正是“某个 Node 加 `<记录的运行目录>/server/index.mjs`” | 都被认作记录的服务（`:89` 只比结尾，不看是哪个程序） |

发生的条件：A、B 需要服务在被探测的那 1.5 秒里答不出健康检查——事件循环被长时间占住、机器极忙、进程被暂停。平时健康检查是毫秒级的，这种情形少见；但后果是写到一半被 SIGKILL，而条文把“不会这样”写成了确定的事。另一种没有验证的情形：启动器自己连不上本机地址（受限的沙箱禁了回环），而进程表读得到，这时一个健康的服务也会被这样结束；条文“没有验证的”只考虑了“读不到进程表就照旧拒绝”这一半。

没有用例覆盖的：A、B、C 的两种应答、D，以及“0.10.x 格式的记录不做这一步”——把这个排除条件去掉，全部单元测试照样通过（变异 K2 存活，实测）。

处理办法二选一，都要改 HLD：

1. 改实现：两处都把条件换成“记录的地址上确实没有监听”（对该地址做一次 TCP 连接，被拒绝才算；连得上而答不出、或答的不是 SkillDock 的，都不算），命令行同时核对程序是 Node；补上表四种情形与 0.10.x 记录的用例。条文基本不用动。
2. 不改实现：把 `35`:766–767 照实现写——“1.5 秒内没有拿到合格的健康应答”——去掉“说明监听已关”“已过了写操作”的确定口气，把 A～D 写进“没有验证的”或登记为已知残留，并改掉“地址上有别的程序在应答时照旧拒绝”一句。

选哪一种是作者与 Owner 的事；无论哪种，Owner 确认这条规则（D34-P3-02）时应当知道上表。

**D34-P3-02　“核实不了就不结束任何进程”改成了“有两种情形强制结束”，第 10 节没有登记，Owner 没有单独表态**

- 这条规则自 0.10.2 起就有，写给使用者与 Agent 的 `SKILL.md` 里原话是“仅停止启动器记录且健康检查确认匹配的服务”（本批已改，`SKILL.md`:54）。0.11.3 让启动器在两种情形下 SIGKILL，其中一种不经健康检查核实、凭进程表的命令行认定。
- 性质与 DG-0112-2（改 0.4.2 的“替换安装目录须重新选择”）相同，比它更重：那一条决定的是计划是否沿用，这一条决定的是结束用户机器上的哪个进程。HLD 里与“停止实例”有关的取舍此前也登记过（`35`:1381）。
- 按作者的记录：向 Owner 说明过规则的变化和两种限定条件，Owner 之后的答复是关于另外两件事的。没有答复不等于同意（80 第 9 节对 0.11.2 的同类情形就是这样写的）。`35` v1.39 对 4.2 写了“Owner 2026-10-13 同意改”，对 3.7 什么也没写，读者看不出这一条尚未得到确认。
- 建议：第 10 节登记一行（例如 DG-0113-1），状态照实写“作者的做法，已向 Owner 说明，Owner 尚未就此表态；合并前由 Owner 定”；3.7 那一条的括号里指向它；请示合并时请 Owner 明确确认，并把 D34-P2-01 的事实一并说明。合并即发布，这一步不能放到合并之后。

**D34-P3-03　新增的启动器用例每跑一次留下一个仍在监听的替身进程**

- 位置：`tests/launcher.test.mjs:145`。这个用例最后启动的实例用 `launch('stop')` 清理，而清理排在夹具删除状态目录之后——启动记录已经没有了，`stop` 回答“没有本启动器管理的运行实例”，进程留下。
- 实测：单独跑这一个用例，结束后临时目录下留有一个 `node …/runtimes/<摘要>/server/index.mjs` 进程，仍监听着一个本机端口；全量单元测试每跑一次留下一个。本评审每次都清掉了自己留下的。
- 本评审第一次跑完单元测试时，这台机器的系统临时目录下另有一个同样的进程，已经运行了 7 分多钟（启动于 15:45:53，早于本评审的运行，不是本评审启动的），评审结束前它已经不在。评审期间这台机器上还有别人的测试在跑，同类进程时有时无；这些都不是本评审启动的，本评审没有动。跑过这组用例的地方，都可能留有这样的进程。
- 建议：像同一文件第 112、119、127 行那样，对这个实例登记一条直接结束进程的清理。

**D34-P3-05　3.7 开头把 V28 里的推断按事实写了**

- `35`:764：“通知到达时若有一个慢读取在途，那条连接就留着，页面每 1.5 秒一次的健康检查又继续用它，旧服务于是‘不监听、也不退出’”。V28（`35`:1229）把“健康检查继续用这条连接”“旧进程因此不退出”“13:42 前后连接空闲下来、旧进程退出”都列在“推断”里，并写明没有直接看到。
- 机制本身站得住。本评审用一个普通的 Node 服务按 0.11.0～0.11.2 的写法关闭（实测，Node v24.21.0，不涉及 SkillDock 的进程）：关闭时有一个慢请求在途；它结束后，同一个客户端在同一条连接上每 0.3 秒发一次请求，12 次都被照常应答，新连接被拒绝，关闭的回调一直不触发，直到客户端放开这条连接。事故当时走的是不是这条路，仍只有推断。
- 同样按事实口气写的还有 `CHANGELOG.md:198`、`37`:286、应用 README 第 220 行与 `server/index.mjs:115`–`118` 的注释；“约 8 分钟后旧进程才自己退出”里的“自己退出”也没有人看到。
- 建议：3.7 开头加“按 9.3 V28 的推断；机制可用替身复现”一类的限定。

**D34-P3-06　三处“30.0 秒”的写法，以及 47.0 与 47.5**

- V26 新加的一句（`35`:1227）：“③ 的三组例子两行之差都是 30.0 秒左右，与 V27 量到的 30.0 秒相合”。两行同时结束，它们 `codex-list` 用时之差等于两次请求**发起**的间隔，不是官方应用目录读取的用时；80 提这一点时说的也是“后到的请求像是在先到的请求发出 30 秒后发起的”。两者数值相同，可能有关联，也可能是两处各有一个 30 秒；写成“相合”，读起来像前者印证了后者。
- `CHANGELOG.md:209` 写“慢的是官方应用目录，固定 30 秒”，`37`:285 与 `41`:29 写“得到证实”。直接量到的只有一行（`app-directory` 30000 毫秒）。V26 自己就有反例：`codex-list` 整段“多为 24～38 秒”，其中低于 30 秒的不可能含一次 30 秒的目录读取；10 分 15 秒那一次目录只用了十几秒。“固定”说过头了。
- 恰好 30000 毫秒更像某处的超时而不是读取本身的用时（推断），V27 没有交代；若是超时，那一次拿到的目录是否完整也值得看。
- V27 ③ 写“一次 47.0 秒的清单读取”，V28 写同一时段的那次读取是 47.5 秒，没有说明是不是同一行的两个数。
- 建议：下一次修订改掉“相合”一句或写明两者各是什么；定稿 CHANGELOG 时把“固定 30 秒”改为“那一次 30.0 秒”。

**D34-P3-07　几处新规则没有被用例钉住**

本评审做了 8 项变异（第 5 节末），3 项存活：K2“0.10.x 格式的记录不做这一步”（全部单元测试通过）；K5 服务收尾后对新到的请求加 `Connection: close` 的那一行（只在收尾开始时响应头已经发出的连接上起作用，用例没有这种情形）；K8 启动器对“失败、目标不是本实例”的任务应当原样不动（去掉条件后它的失败说明被换成“重启任务未完成。”，用例只看状态）。CHANGELOG 与 `37` 说“各条规则做了变异检查”，K2 这一条对不上。

## 5. 3.7 新条文与实现的对照（`35`:764–770）
