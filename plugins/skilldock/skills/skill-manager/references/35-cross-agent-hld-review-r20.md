### 死路修正是否完整

| 委托核对点 | 结果 |
|-----------|------|
| `status` 路径 | 过期记录：按同族处理，报告旧实例的真实状态（E1 `status` 为 running）。仍在使用：退出 1 并给出原因与步骤（E4），与 v1.12 一致 |
| `stop` 路径 | 过期记录：停止存活的旧实例，删除 0.10.x 记录（E3，之后 `start` 正常迁移）。仍在使用：退出 1，不停止、不改文件（E4） |
| 来源目录存在但 `package.json` 不可读 | 归属判为 `family`；`start`、`restart` 由门槛以“无法读取 …package.json”退出 4，文件不变（E5）；但 `stop` 会停止这个可能仍在使用的旧实例并删除记录，`status` 报运行中（E5）。与门槛“读不出的证据从不通过”的口径不一致，影响只在 `stop`、`status`，记为代码复核 CR3-P2-01 |
| 同族判定所用的 Claude 配置目录与 `known_marketplaces.json` | 取包含该来源的那条 Claude 缓存所配对的配置目录（`agentRoots`：保存的 Claude 根目录、`CLAUDE_CONFIG_DIR` 与 `CLAUDE_CODE_PLUGIN_CACHE_DIR`、默认 `~/.claude`），与 `discoverInstalls`、`inspect` 取本安装来源标识的方式相同。自定义目录经环境变量可见时判为同族（U13）；同一缓存与两个配置目录配对时取默认配对，结果正确（U14）。配置目录对本进程不可见、清单中已无该 marketplace 或清单缺失时无法核实 → 拒绝（U10、U10b、U13b），见 R20-P2-02 |
| 存活的旧 Claude 侧 0.10.x 实例是否按迁移第 1 步先停止 | 是。`launch.mjs` 第 336～338 行：构建后取实例锁与 Codex 锁，锁内核对记录未变再停旧实例；E1 迁移后旧 pid 已退出、新实例健康；E1b 证实锁被占用时旧实例不被停止、六个相关文件逐字节不变 |
| 记录中的进程号被无关进程占用 | `start` 以“无法核实记录中的进程……”退出 1（E7）。这是 0.10.2 起即有、对全部 0.10.x 记录都成立的残留（代码复核 r2 第 4.4 节），不是本增量引入；增量第 2 条“否则清理记录后继续”没有覆盖这种情形，列为范围外观察 1 |

结论：**按提示更新（或卸载插件但保留 marketplace）之后重新打开即可继续**，第 19 轮范围外观察 1 的死路在这条路径上关闭。仍会阻断的是来源标识无法核实的少数情形，结果是退出 1 而不是循环提示更新，但提示不可执行（R20-P2-02）。
