## 重点问题逐项回答

### 1. HLDR-SDX-R5-P1-01 是否真正关闭

关闭。依据如下。

- **0.10.2 原生入口**（`native-backend.mjs:113、117-118、149`）：
  - 只要实例未运行，或本进程尚未成功打开过，就以“`SKILLDOCK_PROJECT_DIR` → `project.json` → 启动记录 `project` → 主目录”的顺序取项目，作为 `--project` 与子进程工作目录，执行转交目标的 `launch.sh start`。
  - 旧项目字段改为数据目录内保持存在的固定子目录后，G1（Codex 侧 0.11.0、实例未运行、首次打开、无 `project.json`）成功：启动脚本收到 `start --project <state>/legacy-project`，工作目录相同，请求代理到新实例。
  - G1b 补充一个第 5 轮未覆盖的事实：已打开过的面板在实例停止后再次读取，同样会重走启动路径（第 149 行 `!ready || !prepared`）。所以“已打开过”只在实例运行时免于调用启动脚本。HLD 3.7 第 706 行“未打开过或实例未运行时”的写法正确；6.6 第 1017 行漏了“且实例运行中”（R6-P2-03）。
- **0.10.2 启动器**（`launch.mjs:33-37、39-47`）：`matches` 以字符串全等比较 `(launchProject || project)` 与记录的 `project`，与目录是否存在无关。G2 中实例运行时：
  - start、restart、stop 均报“无法核实记录中的进程属于此 SkillDock 实例；未停止任何进程”，实例存活、记录不变；
  - status 报 stopped，也不改记录。
  - 即使 0.11.x 的健康检查不再返回这两个字段，比较结果仍为不等，拒绝依旧成立。
- 结论：0.10.2 启动器“因无法核实实例而拒绝”与 0.10.2 原生入口“能转交”在固定子目录形态下同时成立。

### 2. 方案 B 与 0.10.3 转交链

**自洽与不越权**：

- 0.10.3 从不自己接管，第 1 步不改记录，第 3 步把启动交给较新安装自己的启动器，与“不接管、不改写计划数据”一致。
- 第 3 步是本轮唯一的新能力：Codex 侧 0.10.3 按记录新字段核实并执行 Claude 侧 0.11.x 的启动脚本。它不是跨 Agent 的**管理**功能（不发现、不读写 Claude 技能与插件、不涉及计划），但与 3.7 第 675 行“不含任何跨 Agent 功能”及 8.4“只含识别与提示”字面冲突，DEC-SDX-021 已删去该短语。需要统一表述（R6-P2-04）。

**可由设计与 0.10.2 代码推断的部分**（已用桩验证）：

- 0.10.2 原生入口对它调用的启动脚本只看退出码：
  - 退出 0 后，重读 `launcher.json`，再用健康检查核对 pid、state、sourceDigest；
  - 非 0 一律进入错误路径，被吞成 `TypeError: redact is not a function`（第 123～124 行）。
- 因此：
  - 第 1 步只需“核实后退出 0、不动记录”。G3：0.10.3 桩走第 1 步，0.10.2 面板首次打开即代理成功，记录未变。
  - 第 3 步只需“较新安装的启动器写好符合 3.7 旧字段规则的记录后退出 0”。G4：Claude 侧 0.11.0 桩被 0.10.3 桩调用并启动实例，0.10.2 面板代理成功，新记录的旧来源仍指向 Codex 侧 0.10.3。G4b：新实例换了端口，0.10.2 也能跟随新记录（Codex 的 MCP 配置不设 `PORT`）。
- 0.10.2 调用时还有几项硬约束，须写进 5.4（R6-P2-02 (a)）：
  - `PORT` 取自旧记录地址；
  - 超时 600 秒；
  - stdout、stderr 各不超过 1 MiB（`maxBuffer`；0.10.2 的构建把 npm 输出写到 stderr，`runtime.mjs:11`）；
  - 传入的 `--project` 与工作目录是旧项目字段。

**“第 1～3 步保证不走失败路径”不成立的部分**：

- 3.7 第 683 行的括注是无条件表述。它只在第 1～3 步之一可行、且被调用的较新启动器成功时成立。
- G5：实例未运行、新字段所指安装已不存在，0.10.3 走第 4 步，以非 0 退出，0.10.2 面板显示 `TypeError: redact is not a function`。
- G5b：同情形改为退出 0，0.10.2 面板显示“SkillDock 后台尚未就绪，请重试。”
- 0.10.2 面板显示的只能是它自己的固定文字，任何 0.10.3 提示都传不到。这是冻结代码的限制，没有不越权的替代设计。
- 第 5 轮 DG-R5-01 方案 B 已向 Owner 说明“0.10.2 的错误路径会把提示吞掉”。所以这里只需如实登记，并缩小第 4 步的发生面（R6-P2-01）。

**必须待 0.10.3 写成后实测的部分（V20）**：

- 0.10.3 是否在转交链判定之前就做工具链解析：0.10.2 的 `bootstrap.mjs` 会在 `launch.mjs` 之前调用 `resolveToolchain({ allowInstall: true })`，缺 Node 时可能下载私有 Node。

- 以上 G 系列都只能用桩代替。

### 3. 5.4 兼容约束 ①～⑦ 与 3.13A 是否完整、可测

- **可测性**：①～⑦ 都能用真实 0.10.2 代码在隔离目录中断言。G1～G4 已示范原生入口真实子进程、实例存活与未运行、换端口、启动器四个子命令的断言方法，不需要联网或改动真实环境。
