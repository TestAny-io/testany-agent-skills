#### IF2-P2-01 Claude 一侧“无法确认”时，每个插件技能都成为“状态待确认”，各带一条警告

- 位置：`assets/app/server/claude-catalog.mjs:156`（`enabled: plugin.enabled`）；`assets/app/src/AgentUI.tsx:16`（“状态待确认”的判断）；`assets/app/src/App.tsx:2238-2251`（`SkillReason`）。
- 问题：插件技能的启用状态取所属插件的状态。找不到可用的 Claude 命令行时，插件清单来自 Claude 的安装记录，记录里没有启用状态，于是每个插件的 `enabled` 都是 `null`，它带的每个技能也都是 `null`。技能库把 `enabled === null` 当作这一个技能需要留意：计入“状态待确认”，卡片上显示警告色的“安装或启用状态尚未核实。”一行。原因其实只有一个，在整侧。
- 证据：
  - 实测（服务端探针，命令行不可用、有安装记录的世界）：Claude 环境为“无法确认”；7 个插件技能的 `enabled` 全部是 `null`，原因都是“未找到可用的 Claude 命令行，无法确认 Claude 中的插件状态。”；Claude 自己的个人技能不受影响（它们的状态来自设置文件）。
  - 实测（界面探针，按上面的形状构造清单）：选 Claude 时“全部技能 6、已启用 0、状态待确认 6”，6 张卡片每张都有一条警告色的整行，带“查看路径与状态证据”与“详细原因”；截图中整页都是警告。同一状态下插件页已经把这句原因在列表上方说了一次（上一轮 IF-P2-01 的处理），技能库页没有。
  - 对照：命令行可用而 Claude 只读时没有这个现象（探针：插件技能的 `enabled` 是真或假，卡片上没有原因行，原因在开关的悬停提示与详情里）。
- 影响：功能不受影响，写操作照常被拒绝。但这一状态并不罕见——没有可用的 Claude 命令行就会进入，不论管理是否启用（`assets/app/server/agents.mjs:83-91`）；这时“状态待确认”从 0 变成全部插件技能的数量，几十到几百张卡片各带一条相同来由的警告，这个分类原本要提示的“这一个技能需要留意”（状态未知、同名）被淹没。这是新功能带来的：此前这一侧只列个人与项目技能。
- 与既有做法的关系：插件页在同一状态下也是每张已安装卡片一条“尚未核实”（早于本批）；Codex 一侧的缓存技能也按逐项未知处理。所以这是把既有口径原样用到了新条目上，只是数量乘上了每个插件的技能数。是否接受由 Owner 定。
- 建议（任选其一）：
  1. 插件技能的状态未知时不作为逐项警告：不计入“状态待确认”，卡片上不出警告行，详情里照常写明“所属插件的状态尚未核实”；所属插件的卡片已经带着这条提示。
  2. 保持逐项标记，但在技能库列表上方像插件页那样把整侧的原因说一次，并把卡片上的警告行降为普通说明。
  3. 保持现状，登记为已知表现。
  - 取 1 或 2 时，在 `agent-ui.test.mjs` 或两个 Agent 的端到端用例里加一个“无法确认”的情形。

## 4. 实验与结果

### 4.1 基线

见文首。全量单元在没有 Git 历史的目录中会跳过 103 项兼容矩阵而显示“0 失败”，这一点与上一轮相同。

### 4.2 探针

**（一）插件技能的服务端探针**（实测）。5 种临时世界（Codex 有自己的技能根；Codex 的技能根链接进插件；Claude 只读；Codex 只读；Claude 命令行不可用），共同的内容：Claude 配置目录中一个从 marketplace 安装的插件 `a`（用户与项目两个作用域，共用一个缓存目录）、一个停用的插件、一个没有安装目录的插件、一个安装路径不是绝对路径的插件、两个技能目录插件（其中一个 Claude 尚未加载）；`a` 的 `skills/` 里放了正常技能、与个人技能同名的技能、指向目录外的目录链接、悬空链接、没有 `SKILL.md` 的目录、没有 frontmatter 的 `SKILL.md`、指向外部非技能文件与外部技能文件的两个文件链接、权限为 000 的 `SKILL.md`、只在第二层有 `SKILL.md` 的目录、隐藏目录、普通文件，以及一个 `commands/` 文件。Codex 一侧有自己的技能根（含一个指向插件技能目录的链接），或者整个技能根链接到插件的 `skills/`。

- 列出：正常技能、同名技能、两种指向外部技能的链接各一条，每处安装各一份，ID 互不相同；停用插件的技能 `enabled` 为假、原因是“所属插件已停用”；未加载的技能目录插件的技能 `enabled` 为 `null`。悬空链接、没有 `SKILL.md` 的目录、只在第二层有的、隐藏目录、普通文件、`commands/` 文件都不列出；没有 frontmatter、指向非技能文件、读不了的三种各记一条诊断（每处安装各一条）。没有安装目录或路径不是绝对路径的插件：技能数 0，不列出。
- 插件的 `skillCount` 等于列出的条数；插件的更新项在 `affectedSkillIds` 中列出它的技能；没有以插件技能为目标的更新项。1 版快照中没有任何 Claude 对象，技能上也没有 `agents` 字段。
- 写路径（对用户作用域的 `a-skill`，结果是返回的错误码）：

## 5. 对委托列出的六点的直接回答

1. **写路径**：没有发现能经插件技能改动任何东西的路径（4.2（一），实测）。遍历 `skills` 并假定“Claude 技能就是个人或项目技能”的地方逐处读过：`decorateClaudeSkills`、`claudeUpdateItems` 原来就按 `scope` 限定在个人与项目技能；`claudeSkillRecord` 先看能力标记、再看是否在两个技能根下；`mergeClaude`、可见性的同名规则、`claudeUpdateMaps`、`migrateTarget`、`assertRemovalIsolation` 是本批补的；批量移除的 ID 校验不接受插件技能的 ID 形状；计划的目标规范化只处理不带 `agent` 的目标，带 `agent: claude` 的插件技能目标因为没有更新项而被拒绝。`scheduler.mjs`、`agents.mjs` 不需要改（阅读）。没有发现漏改。停用的计划可以存下任意形状合法的目标（包括一个插件技能的 ID），这是既有的通用行为，启用时才校验（阅读）。
2. **共用与跨侧**：见 4.2（一）“同一处”与（二）。同名分组对话框正常（4.2（三））。

## 7. 其他观察（不计入问题数）

- 同一插件装在两个作用域时，技能库里是两张一模一样的卡片（名称、类型、版本、来源都相同），同名分组对话框里是两条路径相同的条目。各列一份是 HLD 3.2 写明的做法；卡片上没有所属插件与作用域，用户分不出哪张属于哪处安装。属于界面整体重新设计的范围。
- 技能详情的“所属插件”显示的是 Claude 插件的内部 ID（`claude:plugin:名称@市场:作用域[:项目摘要]`）。Codex 一侧的插件 ID 本身就是“名称@市场”，读得通；Claude 一侧可以改为显示插件名与作用域。
- 插件技能的 ID 含安装目录，而缓存目录以版本命名，所以插件每更新一次，它的技能 ID 都会变。目前没有任何持久记录引用插件技能的 ID（标签不支持，计划不接受，操作记录不产生），不构成问题；以后若要让它们带标签或进入记录，需要先换一种身份。
- 探针里顺带看到一种早于本批的情形：当前项目的 `.claude/skills` 若是指向某个技能目录插件 `skills/` 的链接，经 SkillDock 安装到项目范围的技能会写进那个插件的目录，之后对它的移除与更新也会改写插件的内容，而“改写插件”的确认只针对另一侧的插件，同一侧不询问（`claudeProtectedRoots` 只保护 Claude 的 `plugins` 目录与插件缓存，`service.mjs:373-376`）。布局少见，与本批无关，记录备查。
- 可见性开关的“同名技能共用条目”不再把插件技能算进去，依据是代码注释里的一句“插件技能在 Claude 中以插件命名，不共用这一条目”。这个前提本轮无法核实（见第 6 节）。
