## 3.3A 新增的隔离区副本：是否在已批准边界内

新内容（第 633～634 行）：

- 原地覆盖的 npm 插件，更新前把当前安装内容（排除 `node_modules`）复制到 SkillDock 数据目录的隔离区，只供手动恢复；
- 每个插件只保留最近一次更新前的副本，在操作记录中可见、可清理；
- 只读宿主目录、只写 SkillDock 自己的数据目录，不自动写回 Claude 插件缓存（若要自动恢复，须另行决定）；
- 更新确认中说明：更新后无法经 Claude 回到旧版本，SkillDock 保留更新前副本。

| 检查项 | 有效依据 | 判断 |
|--------|---------|------|
| 写入边界 | PRD 第 1219 行：插件的安装、更新等经 Claude 命令行执行，不直接改写其记录文件。契约索引第 2 节：`<state>` 只属于 SkillDock，宿主插件缓存 SkillDock 只读 | 只读插件缓存、只写 `<state>`，不碰 Claude 记录与缓存。在边界内 |
| 是否沿用已有机制 | PRD 第 7.4 节“对象更新沿用可恢复机制”。0.10.2 的 Codex 插件更新先把当前包复制到 `quarantine/<操作 ID>-plugin-backup`，再调用宿主命令行（`service.mjs` 第 591 行）；结果说明“旧包备份已保留；包级回退通过所属管理器执行”（第 619 行） | 新步骤就是把同一做法用于 Claude 的一类插件，属“沿用”，不是新的产品承诺 |
| 是否新增职责、权限主体或依赖 | — | 没有。不新增常态依赖，也不新增宿主写入 |
| 是否改变失败语义或数据处置 | — | 新增了 SkillDock 自身数据的保留规则（“最近一次”）与清理入口，属 SkillDock 自有数据的生命周期，在工程授权内；但写法有缺口（R16-P2-01） |
| 自动写回 Claude 插件缓存 | 第 15 轮报告 Decision Gates：自动写回越出已批准的写入边界 | 第 633 行明确排除，并写明“若要自动恢复，须另行决定”。与第 15 轮口径一致 |

结论：

- 在已批准边界内，**不需要 Owner 决定**。
- 仍可让产品 Owner 知悉（可选，知悉级）：这类插件只能手动恢复。这与 0.10.2 对 Codex 插件“包级回退通过所属管理器执行”属同一级别；差别在于 Claude 无法按版本重装未声明版本的 npm 包，副本是唯一回退来源。
- 如果以后要求一键或自动恢复，才需要 Owner 决定。
