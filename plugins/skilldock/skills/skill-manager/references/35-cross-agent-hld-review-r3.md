### HLDR-SDX-P1-01 剩余项的复核细节（含对 V16 的回答）

1. **“已停止”记录（第一道防线）**。实验 F1：记录不含 pid、url，`state` 一致，来源指向数据目录内存在的 `runtimes/…/app`。0.10.2 启动器的 `status`、`start`、`stop`、`restart` 全部在动作前被归属检查拒绝（`launch.mjs:125` 先于 `:126-133`），记录保留；原生入口拒绝（“数据目录属于另一个安装来源”）且不尝试启动；数据目录与临时 HOME 文件无任何变化。与作者 V16-F 一致，并补充了“只清除进程信息”的形态。
2. **没有启动记录 + 新格式计划文件（第二道防线）**。作者 V16-G 只在进程内调用 `createService`（`background: false`、替身适配器），不覆盖启动器与原生入口。本轮补测：
   - H（真实启动器 `start`）与 N（真实原生入口）：服务进程在 `createScheduler` 处以“更新状态文件格式无效”退出，启动器报“未能启动”；文件变化只有新增 `server.log`。
   - I：计划已启用时，后台注册替身调用次数为 0；version 1 对照组中替身被调用 1 次，证明替身能捕获调用。原因是 `service.mjs:1048` 的 `createScheduler` 先于 `:1065` 的 `background.ensure()`。
3. **委托方提出的问题：0.10.2 启动器在服务失败之前是否写入共享状态？** 依据源码与 H、N、I：

   | 对象 | 是否写入 | 依据 |
   |------|---------|------|
   | `launcher.json` | 否 | 只在健康检查匹配后写入（`launch.mjs:79-81`） |
   | `restart.json` | 否 | 只在带重启任务时写（`:143`），任务核对在写入前失败（`:149-150`）；成功路径才删除（`:185`） |
   | `project.json` | 否 | `resolveProject` 只读（`project-context.mjs:24-34`）；写入只在界面切换项目时（`service.mjs:934`） |
   | 后台注册（`background/`、LaunchAgent） | 否 | 见第 2 点；H、N 中模拟的后台上下文与 plist 未变 |
   | 其他写入 | 是，均非共享状态 | 临时锁文件 `launcher.lock`、`runtime-build.lock`、`native-start.lock`（释放即删）；`server.log` 追加；若数据目录中没有 0.10.2 的运行目录，会生成运行目录并联网执行 `npm ci` 与构建（`runtime.mjs:25-45`），约 35 秒后才失败（本轮对照实验 B 意外触发，见附录） |

   结论：两道防线在 DEC-SDX-022、3.7、6.6 中的使用成立。V16 的“数据目录内容不变”应限定为“共享状态不变”，并注明生成运行目录与日志的例外（R3-P2-06）。
4. **前提条件**（实验 J）：0.10.2 在计划文件缺失时按 version 1 默认值加载（`scheduler.mjs:39`），没有启动记录也没有计划文件时会正常启动并写入自己的启动记录。由于 0.11.0 永不删除启动记录，这一情形只在迁移中途中断或记录被外部删除时出现，因此不阻断关闭；但需写明前提（R3-P2-01）。
5. **“0.10.2 及更早”**：静态核对 0.2.0～0.10.2 各发布提交与 testany-eng 内嵌末版，空记录放行、同一安装比较、计划文件 `version !== 1` 校验三处逻辑均存在；0.4.0 起 `createScheduler` 均先于 `background.ensure()`。结论可延伸到更早版本（静态证据，未逐版执行）。

#### HLDR-SDX-R3-P1-01：“清单无法确认”即失败关闭，没有出路

- **有效依据**：
  - REQ-SDX-007 第 6 条验收：门槛由“检测到任一 Agent 中仍有低于 0.10.3 的 SkillDock 安装”触发；
  - PRD 4.5 与 5.1.4：某环境记录不可读或格式未知时，“该环境清单降级为‘无法确认’，禁用写操作”，只影响该环境；
  - MR-SDX-001：未启用 Claude 管理时，Codex 的清单、操作、原生入口、后台更新与 0.10.2 一致；
  - PRD 2.3：Claude-only 首次可用。
- **当前设计**：
  - 3.7（第 669 行）、DEC-SDX-022、6.6：“任一 Agent 的安装清单无法确认”即门槛失败，不接管、不启动；出路只有“一键更新该侧”。
  - 3.1：配置根存在即发现该 Agent。3.2：Claude 的主证据（命令行列表）不可得或格式未知即为“无法确认”。3.7：安装登记按各 Agent 的“官方清单”复核。
- **当前失败**：
  1. Codex 用户本机有 `~/.claude`，但从 Codex 入口找不到 Claude 命令行（9.1 已登记桌面应用自带命令行的目录结构不是公开契约），或 Claude 升级后记录格式变化（RISK-SDX-002）。此时 Claude 环境“无法确认”，门槛一直失败。Codex 侧一旦被更新到 0.11.0，Codex 入口运行的就是 0.11.0：不接管、不启动服务，只提示“更新另一侧”；但另一侧可能根本没有 SkillDock，一键更新也找不到可用的命令行。
  2. Claude 用户本机残留 `~/.codex`（卸载过 Codex 应用），找不到 Codex 命令行，Codex 环境“无法确认”，Claude 侧 0.11.0 从第一次打开就无法使用。没有数据目录的新用户同样受影响：无记录视为代号 1，也要过门槛。
- **影响**：PRD 只让该环境降级，HLD 却把它放大为整个 SkillDock 不可用，且无出路，违反 MR-SDX-001，并影响 Claude-only 首次可用。
- **责任说明**：该分支来自第 2 轮评审 R2-P2-06 第一条“清单无法确认时门槛应失败关闭”的建议措辞；第 2 轮没有同时要求给出出路，属评审遗漏，不归咎于作者。
- **最小修复（不改变边界）**：

#### HLDR-SDX-R3-P1-02：0.10.3 入口把“本安装已升级、进程未重载”当成“本侧需要更新”

- **有效依据**：
  - MR-SDX-001（原生入口行为与 0.10.2 一致）；
  - REQ-SDX-007 陈述“较旧入口仍能打开或明确提示更新入口”，以及第 4 条验收“一侧更新 SkillDock 后自动切换到新版本”；
  - 0.10.2 的现有行为：原生入口是长连接进程，本安装被更新到较新缓存后，它不降级，而是转用较新版本的启动脚本（`native-backend.mjs:58-69` 的注释与逻辑；[30](30-native-app.md) 第 42 行记录了“旧缓存被自更新删除后启动新版”的验证）。本轮对照实验 B 也证实：来源为同一安装的较新缓存时，0.10.2 原生入口会转交给较新版本。
- **当前设计**：5.4（本轮新增）与 3.7 第 664 行规定，0.10.3 遇到 0.11.x 写入的启动记录（含“已停止”形态）一律“拒绝接管，提示请把本侧更新到 0.11 或更高”。
- **当前失败**：
  - 在 Codex 中打开着 SkillDock 原生面板（0.10.3 代码的长连接进程）时，本侧被更新到 0.11.0：0.10.3 服务的自更新协调器会调用 0.11.0 的启动器（`self-update.mjs:18`），0.11.0 迁移并写入新形态启动记录。
  - 面板所在的 0.10.3 进程下一次读取时，按 5.4 拒绝并提示“请把本侧更新到 0.11”，而本侧已经是 0.11.0。用户照提示去更新，只会得到“已是最新”，直到重启 Codex 才恢复。今天 0.10.x 之间的自更新是无感的。
  - Claude 侧未重载会话中残留的旧技能路径同理。
- **影响**：
  - 0.10.3→0.11.0 这一次跨版本自更新中，开着原生面板的 Codex 用户普遍会遇到错误提示和面板失效。这是 MR-SDX-001 的回归，数据不受影响。
  - 5.4 本身写明 0.10.3 的判定发布后无法再改，所以必须在 0.10.3 编码前修正，不能留到实现阶段。
- **最小修复（不改变边界）**：
  - 在 5.4 与 DEC-SDX-021 中规定：0.10.3 的入口遇到 0.11.x 记录时，先判断本 Agent 的同一安装是否已有不低于记录版本的较新缓存（读记录中新增的真实安装来源字段，或本安装的缓存目录）。
  - 若是，沿用 0.10.2 已有的转交逻辑，交给较新版本的启动脚本（不接管、不降级）；至少也要改为提示“本侧已更新，请重新加载插件或重启 Codex”。只有本安装确实较旧时，才提示“更新本侧”。
  - 9.3 增加验证（V17）：真实 Codex 中，插件更新后原生入口长连接进程是否保留，以及转交是否生效。

## Decision Gates

- **DG-R3-01（产品 Owner）：已加载的 0.10.2 旧入口在本侧被更新到 0.11.0 后报错，属于非主动回退的残留。**
  - **现象**：Codex 原生面板的长连接进程，或未重载的 Claude 会话，如果仍在运行 0.10.2 代码，那么本侧被更新到 0.11.0 后，它会显示“SkillDock 数据目录属于另一个安装来源；未接管其后台。”，不会转交，也不会提示更新（实验 F1）；重启 Codex 或重载会话后恢复。
  - **原因**：0.10.2 代码无法修改，而“来源指向数据目录”正是为了让 0.10.2 拒绝接管（回退防线）。
  - **与已有登记的关系**：BRIEF-SDX-005 只登记了“主动回退”，这一情形不在其中，与 REQ-SDX-007 陈述冲突。
  - **影响面**：从 0.10.3 发布前起一直没有重启 Codex（或重载 Claude 会话）的用户，持续到其重启为止；数据不受影响。
  - **选项 A（推荐）**：保留当前设计，Owner 知悉并登记为已知残留。缓解措施：0.10.3 的发布说明与 README 提示“更新后重新加载插件或重启 Codex”；保持 8.4 中两次发布之间的间隔；HLDR-SDX-R3-P1-02 修复后，加载 0.10.3 的进程不再受影响。
  - **选项 B（不推荐）**：Codex 安装运行时，把记录来源仍写为该安装的 0.11.x 缓存路径。对照实验 B 证实，已加载的 0.10.2 原生进程会因此转交；但 0.10.2 启动器会把“已停止”记录当作同一安装的记录删除，并尝试启动自己。这样回退防线只剩新格式计划文件，而它有前提（R3-P2-01）。
  - **缺少的授权**：Owner 对该残留的知悉或接受记录。Owner 按选项 A 登记后，本项关闭，`scope_status` 回到 WITHIN_APPROVED_SCOPE。
- **条件性决定（产品 Owner）**：仅当作者在修复 HLDR-SDX-R3-P1-01 时，希望在“文件证据也无法判断”时允许用户确认后继续。届时需要说明：如果该侧其实装有旧版 SkillDock，它的入口会报错，即 Q1 类限制。由 Owner 接受或否决。
- **评审者责任披露**：
  - HLDR-SDX-R3-P1-01 的触发分支来自第 2 轮 R2-P2-06 的建议措辞。

- **撤回 / 更正**：无。前两轮没有需要撤回的“已批准”表述。
