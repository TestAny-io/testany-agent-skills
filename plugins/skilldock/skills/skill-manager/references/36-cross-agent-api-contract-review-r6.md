- **结论：APPROVED（通过）**。P0 0 项，P1 0 项；P2 7 项，均为本轮新发现，不阻断。

**APIR6-P2-01 多目标修订号规则改变了批量移除的整批语义（最值得先处理）**

- 7.1 第 219 行要求多目标操作“执行前按目标重新读取并核对预览基线，不一致的目标单独记为失败并说明原因，不影响其他目标”，并把 `skill.removeSelected` 列入其中。
- 0.10.2 的 `skill.removeSelected` 是整批原子操作（第 5.1 节）：任何一项或整组成员变化，都整批返回 `REMOVAL_CHANGED`，一份都不移，中途失败全部回滚。这样做也保护了用户选择保留的那几份。按逐项语义实现时：
  - 某一项变化，其余照样移除；
  - 保留项被外部删除时，逐项核对只看“被移除的目标”，可能把同名技能全部移走。这些移除都可以恢复，所以不是数据丢失，但“保留 N 份”的保证失效。

  - HLD 4.2 规定 0.11.x 前端始终以多 Agent 客户端身份请求，即使只用 Codex，写请求也是 2 版。

  - `schedule.configure` 只保存计划，没有预览基线，也不执行任何目标；
  - 第 252 行“所有 Claude 写操作……与 `expectedRevision` 比较”没有豁免多目标操作。
- **建议**：
  - `skill.removeSelected` 保持 0.10.2 的整批失效：整组签名与任一项的核对失败都整批拒绝，Claude 对象与共用技能的核对并入这一步；

**APIR6-P2-02 `SOURCE_CONFLICT` 与 1 版错误码的规定冲突**

- 第 198、245 行：关联来源时，另一侧已有指向不同来源的记录就返回 `SOURCE_CONFLICT`，没有区分 1 版与 2 版请求。
- 第 5 节第 89 行与第 8 节第 305 行规定，1 版客户端只可能收到三个新错误码（`AGENT_READ_ONLY`、`AGENT_UNCONFIRMED`、`DATA_GENERATION_NEWER`），且这三个错误码的 `message` 必须能独立理解。
- 0.10.x 界面通过 1 版请求对共用技能关联来源时，契约同时给出两种结论：按第 6 节返回 `SOURCE_CONFLICT`，或按第 5、8 节保持 0.10.2 行为、照常写入。若照常写入，就会形成“两侧来源不同、两侧都不可更新”的状态（第 197 行能兜住，但 0.10.x 用户刚关联完就看到不可更新）。

  - 一是 1 版请求不做冲突检查，照常写入，冲突状态由第 197 行处理；

  - 同时把第 305 行改为“只在 2 版请求（带 `agent`）或新增操作上出现”。
