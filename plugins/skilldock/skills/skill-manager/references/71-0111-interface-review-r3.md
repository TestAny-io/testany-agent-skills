### P2

#### IF3-P2-01 声明路径本身就是技能目录时，Claude 用说明头里的 `name` 取名；SkillDock 一律用目录名

- 位置：`assets/app/server/claude-catalog.mjs:211`（`name: path.basename(folder)`）、`:163-176`（`skillFolders` 不区分一个目录是“声明路径本身”还是“声明路径的子目录”）；证据脚本 `assets/app/tests/claude-plugin-skills-smoke.mjs:25-32`。
- 问题：提交说明与实现都按“Claude 以目录名给插件技能取名”处理。对照真实命令行，这只在技能是某个技能目录的**子目录**时成立。**声明的路径本身就是技能目录**时，Claude 用说明头里的 `name`，说明头没有 `name`（或整个没有说明头）才退回目录名。
- 证据（实测，Claude Code 2.1.295，第 4.2 节第 2、3 次对照；“Claude”一列取自 `claude plugin details`，与会话启动事件里提供的名字相同）：

  | 写法 | 目录 | 说明头的 `name` | Claude | SkillDock |
  |------|------|----------------|--------|-----------|
  | 根目录来源，条目列出 `./skills/dirname` | `dirname` | `fm-direct` | `fm-direct` | `dirname` |
  | 子目录来源，条目追加 `./tools/onedir` | `onedir` | `fm-subdirect` | `fm-subdirect` | `onedir` |
  | manifest 声明 `./custom/onedir` | `onedir` | `fm-mandirect` | `fm-mandirect` | `onedir` |
  | 默认 `skills/` 自身带 `SKILL.md` | `skills` | `whole` | `whole` | `skills` |
  | 插件目录就是技能（子目录来源，`skills: ["./"]`） | 版本目录 | `fm-subroot` | `fm-subroot` | `35bcfba182d3` |
  | marketplace 根目录就是技能（`skills: ["./"]`） | 版本目录 | `root-skill` | `root-skill` | `cba7e43153fe` |
  | 同上，写成 `skills: ["."]` | 版本目录 | `fm-rootdot` | `fm-rootdot` | `e1768fa6b9f5` |
  | 对照：默认 `skills/` 下的子目录 `d1` | `d1` | `fm-d1` | `d1` | `d1` |
  | 对照：条目列出的技能目录的子目录 `child` | `child` | `fm-child` | `child` | `child` |
  | 对照：声明路径本身是技能，说明头没有 `name` | `noname` | 无 | `noname` | `noname` |
  | 对照：插件目录就是技能，说明头没有 `name` | 版本目录 | 无 | `35bcfba182d3` | `35bcfba182d3` |

- 为什么作者的冒烟没有发现：它的六个插件里，声明路径本身是技能的只有 `./skills/x`、`./skills/y`、`./tools/t1`，这三个目录的名字都与说明头的 `name` 相同；名字不同的 `renamed` 放在默认目录之下，属于“子目录”一类。冒烟的断言都成立，只是没有覆盖到这一类。
- 影响：
  - “整个插件就是一个技能”是常见的发布方式（仓库根目录放 `SKILL.md`，条目写 `"source": "./", "skills": ["./"]`）。这种插件在技能库里的名字是一串提交摘要或版本号，用户认不出它是什么，也搜不到。
  - 条目逐个列出技能目录是技能合集的常见写法。目录名与 `name` 相同时（Agent Skills 规范要求如此）看不出差别；不同时，SkillDock 显示的名字与 Claude 里看到、调用的名字不一样。
  - 名称还用于搜索与同名分组。没有写路径受影响，条目本身、数量、所属插件都是对的。
- 建议：`skillFolders` 记下每个目录是不是声明路径本身；是的话名称取说明头里非空的 `name`，否则取目录名（子目录一律取目录名）。改动在两三行。冒烟里补一个“声明路径本身是技能、目录名与 `name` 不同”的插件和一个“根目录就是技能”的插件，单元用例照此补断言；HLD 9.3 V23 与契约里“名称取目录名”的说法随之改（文档另由他人评审）。

#### IF3-P3-01 以点开头的技能目录 Claude 会加载，SkillDock 不列；用例把相反的预期写成了断言

- 位置：`assets/app/server/claude-catalog.mjs:173`（`!child.name.startsWith('.')`）；`assets/app/tests/claude-catalog.test.mjs:82` 一带（“a hidden folder”不列出）。
- 证据（实测，两次对照各一个插件）：`skills/.hidden`、`skills/.hid` 里有 `SKILL.md` 时，`claude plugin details` 把它们列为技能（`.hidden`、`.hid`），会话里提供的名字是 `-hidden`、`-hid`；SkillDock 都不列。以下划线开头的目录两边都列。只在第二层才有 `SKILL.md` 的目录两边都不列。

#### IF3-P3-02 两种少见的写法与 Claude 不一致

- 位置：`assets/app/server/claude-catalog.mjs:158`（只判断“存在且在安装目录内”，不判断是不是目录）；`:187-191`（技能目录插件也读安装目录里的 marketplace 文件）。
- 证据（实测，第 2 次对照）：
  1. 根目录来源、条目的 `skills` 列的是一个**文件**（`./skills/x/SKILL.md`）：Claude 按默认列出 `x`、`y`；SkillDock 把它当作“所列的具体目录存在”，结果一个技能也不列，技能数为 0。探针里列一个普通文件、或列一个技能在第二层的目录也是 0（后一种 Claude 同样是 0，一致）。
  2. 技能目录插件（`名称@skills-dir`）的目录里带着一份 marketplace 文件，其中有同名条目、来源为根目录并列出 `./skills/x`：Claude 按 manifest 列出 `m1`、`x`、`y`（技能目录插件不经 marketplace 条目）；SkillDock 套用了根目录来源的例外，只列 `x`。同一个插件不带那份文件时两边一致。
- 影响：都是少列。第 2 种在“用 SkillDock 从本地目录安装一个既是插件、又自带 marketplace 文件的仓库”时可能遇到，前提是那份文件的条目里另外列了 `skills`。
- 建议：例外里“所列的存在”改为“所列的是存在的目录”；`名称@skills-dir` 的插件不读安装目录里的 marketplace 文件。

#### IF3-P3-03 `.DS_Store`：来源与安装两处各有一个、字节相同时，检查说有更新而应用说没有；另有一处只在理论上出现的误报

- 位置：`assets/app/server/service.mjs:624-628`、`:639`；`assets/app/server/files.mjs:102-107`。
- 证据（实测，探针）：
  1. 来源目录后来多了一个 `.DS_Store`，安装目录里也有一个记录之外的、内容相同的 `.DS_Store`，其余文件没有变化：检查返回“1 个文件有变化（新增 `.DS_Store`）”，因为比较时安装一侧的那个被忽略了；应用时按磁盘上的实际指纹核对，候选内容与磁盘完全相同，返回 `NO_UPDATE`“没有需要更新的内容”；再检查，又是“有更新”。两处的 `.DS_Store` 字节不同时没有这个问题（应用成功，之后这份 `.DS_Store` 成为记录里的内容）。
  2. 来源记录没有 `files` 字段、而记录的指纹里含有 `.DS_Store` 时：未改动的技能被判为本地修改（改动前是“一致”）。从第一个发布版本（`7c37780`）起，安装与关联来源都写 `files`（阅读，查了历史），所以实际不会遇到；记在这里是因为委托点名问到。
- 影响：第 1 种需要两个 `.DS_Store` 逐字节相同，访达各自生成的一般不同，手工或工具整目录复制时才会相同；遇到时界面上是一个点了就报错、再查又出现的更新，自动应用的计划每轮记一次失败。
- 建议：检查时若候选内容与磁盘上的实际内容指纹相同，直接按“一致”返回；没有 `files` 的记录按原样比较，不做忽略。

### 4.3 探针

**（一）列法，53 种写法**（实测，替身清单，临时目录）。与第 4.2 节互相印证的不再重复，另外确认了：

- 来源的写法：`./`、`.`、`.//`、`./skills/..`、`skills/..` 都认作根目录；空串不认。
- `skills` 的写法：字符串与数组都接受；数字、对象、数组里的非字符串、不以 `./` 开头的、绝对路径、`./../…` 与 `../…` 都被忽略，按默认处理；同一个目录写三种形式只列一次；`./skills/../skills` 与默认等价。
- 越界：声明的路径在字面上越出、或经链接越出安装目录的不算；技能目录或 `SKILL.md` 链接到安装目录外的不列出并记诊断；悬空链接静默跳过；安装目录本身是链接时正常。
- 安装目录里的 marketplace 文件：没有、读不了、里面没有这个插件、里面说它不是根目录来源——这四种都按 marketplace 副本里的条目处理；两者都说是根目录来源而 `skills` 不同时，以安装目录里的为准（这是有意的，单元用例覆盖）；副本里的条目不是根目录来源时不看安装目录里的；marketplace 里已没有这个插件时用安装目录里的。
- 技能目录插件：按 manifest 与默认目录列出；自带 marketplace 文件时见 IF3-P3-02。

**（二）`.DS_Store`**（实测，演练环境与两侧共用的临时世界）。

- 哪些文件算本地修改（技能安装时没有任何 `.DS_Store`，来源不变）：

  | 多出来的东西 | 结果 |
  |--------------|------|
  | 顶层、已有子目录里、新建子目录里的 `.DS_Store` | 一致，不进差异 |
  | `x.DS_Store`、`.DS_Store.txt`、`docs/a.DS_Store`、`._.DS_Store` | 本地修改 |
  | 名为 `.DS_Store` 的目录，里面有一个文件 | 本地修改 |
  | 名为 `.DS_Store` 的链接（指向技能内的文件） | 一致（被当作访达的文件；少见，无害） |
  | 一个新的空目录 | 一致（指纹本来就不含空目录） |
  | 别的文件 | 本地修改 |

- 记录里有的 `.DS_Store`（随来源装进来的）：原样时一致；改写顶层那个、删掉子目录里那个都是本地修改；别处再多出一个记录之外的，仍然一致。
- 检查与应用之间：检查后访达才写入一个，应用返回“技能在预览后发生变化，请重新检查”；重新检查后应用成功，旧目录（连同 `.DS_Store`）进可恢复区，新目录里没有它，来源记录里也没有它；恢复后 `.DS_Store` 回来，再检查仍按记录比较。预览里逐个文件的差异照常。
- 更新页的 `update.check` 结果相同。计划：保存计划之后才出现 `.DS_Store` 时，这一轮记“跳过，绑定已变化”（已知，按委托的说明不算问题）；手动检查正常。
- 两侧共用的技能、两侧各有一份来源记录：Codex 一侧先关联（当时没有 `.DS_Store`），访达写入一个之后 Claude 一侧再关联——Claude 的记录把它记成了内容，两份记录的指纹不同；由 Codex 主导检查与更新，访达改写它不受影响；更新后两份记录同步为相同的指纹，都不含它；恢复后两份记录各自回到原样，`.DS_Store` 回来。
- 来源一侧的 `.DS_Store`：见 IF3-P3-03 与第 7 节。

**（三）`metadata` 改写前后**（实测）。把 `0b77954` 的 `files.mjs` 临时放在旁边，对 18 种 `SKILL.md`（合格的几种写法、带 BOM、CRLF、超长字段、没有说明头、空文件、说明头没有结束、YAML 错误、重复的键、缺 `name`、缺 `description`、空白的 `name`、`name` 是数字、说明头是标量或列表或为空、超过 2 MB）以及没有 `SKILL.md` 的目录各调用一次：返回的字段与值、抛出的状态码、错误码与文字，18 种全部相同。

**（四）技能详情与名称**（实测）。没有说明头的插件技能能读出正文；Codex 技能的正文与原来一样；一个 Codex 技能在列出之后被去掉说明头，再读返回“未找到”（它已不在清单里，与改动前相同）。Claude 的个人技能与某个插件技能同名（不论那个名字来自目录还是说明头）时，改可见性不需要确认。

## 7. 其他观察（不计入问题数）

- 来源目录里后来出现的 `.DS_Store` 仍算来源的变化：只因为用户在访达里看过来源目录，就会出现一个内容只有“新增 `.DS_Store`”的更新；应用之后它成为记录里的内容，访达以后再改写安装目录里的那一个，又会被判为本地修改。这与本次的决定并不冲突（决定针对的是记录之后才出现在安装目录里的），早于本批，记录备查。
- “关联来源”把当时磁盘上的全部文件记为内容，包括已经在那里的 `.DS_Store`（4.3（二）共用技能一段）。所以先在访达里看过、再关联来源的目录，仍然会因为访达改写它而被判为本地修改。同样在本次决定的范围之外。
- Claude 对“声明路径本身是技能、说明头没有 `name`、而这个路径是插件根目录”的技能，自己也用版本目录名取名（两边都显示一串摘要）。这是 Claude 的行为，SkillDock 照样显示是对的。
- 作者的冒烟里 `git` 没有用临时 HOME，会读到运行者的全局 Git 配置。只读，不影响结果；若全局配置里有改写地址或强制签名之类的设置，冒烟可能在别人的机器上失败。可以像给 Claude 那样给它一个干净的环境。
