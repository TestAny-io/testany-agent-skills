## 2 六项改动逐项判定

### 2.1 计划：Codex 自己更新插件之后沿用原计划 —— 实现与写下的规则一致

`server/scheduler.mjs:34-41`（`bindingIdentity`）、`:205-224`（`reconcileBinding`）；`server/service.mjs:2311-2317`（`verifySynchronized`）、`:1338-1427`（核实）。

- **有没有接管不该接管的对象：没有发现。** 沿用要同时满足：同一个插件 ID；来源身份逐字段相同（marketplace 的来源与类型、包在其中的路径、ref、代次）；同一设备；新旧目录在同一个父目录下；新目录名按版本比较确实更高；是 Codex 的插件（`verifySynchronized` 对 Claude 的目标一律返回否，`:2312`）；计划处于启用；装入的版本等于来源声明的版本，且内容逐文件一致；核实之后重读的签名没有变；绑定没有被别处改过。每一条去掉都有用例失败（变异 S1、S1b、S3、S5、S6、S14、S15，实测）。0.4.2 的第 6 条“不把旧安装认作任意新版内容”仍然成立：认的只是与来源副本逐文件相同的那一版。
- **`'same'` 分支是否与原来等价：是。** 原来比较除内容指纹外的整个对象；现在把 `real` 与 `ino` 单独拿出来比，其余照旧（推断，逐字段推演）。同一路径、不同 inode 仍不算同一对象（变异 S4 被杀，实测）。
- **`real` 的最后一段是否总是版本号：正常情况下是。** Codex 插件绑定的是 `…/plugins/cache/<marketplace>/<插件>/<版本>` 的真实路径（`service.mjs:1855`）。实测：

  | 旧 → 新 | 结果 |
  |---|---|
  | `2.4.1` → `2.4.2`、`v2.4.2`、`2.5.0-rc.1`、`2.4.1.1`、`10.0`；`2.4.1-rc.1` → `2.4.1`；`1.9` → `1.10` | 沿用 |
  | `2.4.1` → `2.4.1+build7`（构建号不分先后） | 不沿用 |
  | `abc1234` → `def5678`（提交摘要） | 不沿用 |
  | `8477` → `9912`（纯数字，会被当成版本） | 沿用——但仍须装入版本等于来源声明的版本且内容一致 |

  版本目录本身是链接时，最后一段是链接目标的名字，比不出先后就不沿用（推断）。
- **核实通过到改写绑定之间的并发：有三道。** 核实内部在暂存之后重读清单、来源、安装指纹与签名；调度器在核实后再读一次签名，确认计划没有被关掉、绑定还是原来那份，才改写；自动应用之前再比一次签名。单独去掉其中一道，别的仍然挡得住（变异 S6b、S6c、S16 各自存活；这三道都是既有代码，不是这次改的）。
- **与手动检查的配合（实测）：** 手动检查先改绑（计划启用时），再取 `beforeOwnUpdate`，再做带刷新的检查；刷新期间 Codex 又装了新版本时走原有的 `afterOwnerRefresh`。计划关闭时手动检查不改绑，重新开启时按当时的目录重新绑定。
- **按设计不沿用的（实测）：** 新版本目录里有访达写的 `.DS_Store`（Codex 插件照旧按原样比较）——删掉后下一轮沿用；来源副本又往前走了一版。
- **代价（实测）：** 沿用的那一轮多读 3 次 Codex 清单（4 次变 7 次），只此一轮。

### 2.2 `.DS_Store` 一律不算独立技能的内容 —— 实现与写下的规则一致，两侧都成立

`server/files.mjs:103-105`；`server/service.mjs:620-631`（检查与差异）、`:683-687`（恢复）、`:1831-1835`（计划绑定）；`server/scheduler.mjs:196-204`（旧绑定）。

- **有没有漏掉真实的本地修改，或覆盖用户的改动：没有发现。** 排除的只是文件名正好是 `.DS_Store` 的条目；名称以它开头或结尾的文件、叫这个名字的文件夹照常算内容（变异 F3、F9、F9b 被杀，实测）。更新仍然把整个旧目录移入可恢复区；恢复时被换下的那一份也留在可恢复区（实测）。
- **恢复那一处的三个条件：足够。** “记录的指纹正是那次装入的内容”这一条挡住了“更新后改了文件、再关联来源、再恢复”（变异 R1 被杀）；“不是链接”这一条实测有效——把更新后的目录换成指向同样内容的链接，恢复以 `LOCAL_CHANGES` 拒绝——但没有用例（R2 存活，C12-P3-06）。
- **`bound()` 只在内存里改写：没有发现问题。** 同一轮里随后的持久化会把它写盘（用例读文件验证；变异 S8、S9、S10、S13 被杀）；写盘之前进程退出，下次按同样的算法得到同样的结果。旧绑定算进去的那份 `.DS_Store` 此后被访达改写过的，仍要重新选择一次——这是分辨不出来的情形，用例里有。
- **Claude 一侧（实测，探针）：** Claude 的技能与技能目录插件，两侧都有访达文件时检查为“一致”、计划照常运行、来源另有改动时差异里不列它、更新后只多出访达文件时可以恢复、多出别的文件时拒绝恢复。两侧共用的技能未做（走的是同一段代码，推断成立）。
- **没有跟着改的一处：** “关联来源”的预览（C12-P3-04）。
- **仍会停下来的（实测，HLD 3.3A 已写明前一种）：** 检查与应用之间访达改写了安装目录里的那一份，应用以 `LOCAL_CHANGES` 停下；改写的是来源目录里的那一份，以 `SOURCE_CHANGED` 停下。再检查一次即可，没有循环。

### 2.4 Claude 报告的加载问题 —— 取舍合理

`server/claude-catalog.mjs:139`、`:220`、`:358-370`。

- **残留：** 技能目录插件不在其内（C12-P3-02）；两处新文字没有翻译（C12-P3-03）。另：插件卡片和技能卡片上没有任何标记，要打开插件详情、技能详情或诊断才看得到（观察）。

## 4 新发现

### C12-P3-01 根目录来源的条目把默认目录列在它里面某个技能之后，名称与 Claude 不同（可留到下一版）

- **位置**：`server/claude-catalog.mjs:166`。
- **现象（实测）**：`skills/x` 的说明头里 `name` 是 `fm-x`。

  | 条目所列 | Claude（`plugin details`） | SkillDock 0.11.2 |
  |---|---|---|
  | `["./skills/x", "./skills"]` | `x y z` | `fm-x y z` |
  | `["./skills/x", "./skills/"]` | `x y z` | `fm-x y z` |
  | 同上，根目录自带 manifest | `x y z` | `fm-x y z` |
  | `["./skills/x", "./"]`、`["./", "./skills/x"]`、`["./skills/", "./skills/x"]` | 目录名 | 目录名（一致） |

- **原因（推断）**：Claude 在所列的含默认目录时先读默认目录，所以 `x` 先以子目录的身份到达。实现只在所列的含根目录时把默认目录放到最前。
- **影响**：只是名称不同，清单里的技能是同一批。要“默认目录排在它自己的某个技能之后”且“说明头的名称与目录名不同”才出现。
- **来历**：这次改动带来的。0.11.1 把“列了 `./skills`”与“列了根目录”同样处理，这种写法当时是一致的（上一轮实测）。
- **测试**：单元用例钉不住这一处的顺序——把默认目录改到所列的之后（K3c），或者列了 `./skills` 时也放到最前（K3b），全部用例照样通过。

### C12-P3-02 技能目录插件的加载问题不显示（可留到下一版）

- **位置**：`server/claude-catalog.mjs:327-330`、`:372-390`。`名称@skills-dir` 的插件不走读 `errors` 的那个循环，清单里的那一条只用来取启用状态。
- **现象（实测）**：技能目录插件的 manifest 声明了一个不存在的目录时，`claude plugin list --json` 给出 `path-not-found`；SkillDock 没有提示、没有说明、没有诊断。清单本身一致。

### C12-P3-03 两处新文字没有英文、日文翻译（可留到下一版）

- **现象（实测，翻译函数的探针）**：技能上的说明“Claude 报告所属插件有加载问题……”和插件提示的前缀“Claude 报告这个插件有加载问题：”，在英文、日文界面下原样显示中文。同一组的另外三句说明都有翻译。那条诊断同样没有翻译，但诊断本来就只有一部分有。
- **测试**：`tests/claude-catalog.test.mjs` 的新用例没有把这两句交给翻译检查。

### C12-P3-04 “关联来源”的预览仍把 `.DS_Store` 算作差异（可留到下一版）

- **位置**：`server/service.mjs:593`。
- **现象（实测）**：安装目录里只多一份访达文件、其余与来源相同时，预览给出“与本机不一致”，差异里列“删除 `.DS_Store`”；关联之后检查更新，结果是“当前内容与来源一致”。
- **影响**：两处说法不一致；关联与之后的检查、更新都不受影响。HLD 3.3A 列的四处比较不含这一处。

### C12-P3-05 沿用核实不过时，每一轮多留一条失败记录（可留到下一版）

- **现象（实测）**：Codex 把插件装到 2.4.2、来源副本已是 2.4.3 时，计划每一轮照旧以 `TARGET_BINDING_CHANGED` 跳过，同时操作记录里多一条失败的 `plugin.checkUpdate`（“无法确认安装内容与来源一致，原定时计划绑定保持不变。”）；连跑 3 轮是 3 条，手动检查再加一条。新版本目录里有访达文件时走的是同一条路（推断）。
- **来历**：0.11.1 在这种情形下不做核实，也就不留这条记录（推断，代码差异）。同版本内容漂移而核实不过时本来就有这条记录，这次是把它带到了新的情形。
- **影响**：只是记录变多、带错误状态；平时每一轮检查也会留一条成功记录，数量没有增加。若真实 Codex 装入的目录与来源副本并不逐文件一致（未验证），这会是每个计划内插件在 Codex 自行更新之后的常态。

### 不计入意见的观察

1. **恢复一次更新之后，计划跳过这个技能（实测）。** 手动更新、再从操作记录恢复，下一轮以 `TARGET_BINDING_CHANGED` 跳过。恢复那一段没有改绑的步骤，这次也没有动它，是既有行为（推断）。
2. **退回 0.11.1（推断）。** 0.11.2 保存的绑定不计 `.DS_Store`；目录里有这种文件的技能，退回后会被 0.11.1 判为绑定已变，需要重新选择。是跳过，不是误接管。
